The project's current development plan, not a promise of delivery dates. Evidence for P0 is in [docs/evidence-p0.md](docs/evidence-p0.md). Documentation validation does not prove an agent follows the skill.

Installation, discovery and explicitly requested skill use were checked on several hosts; automatic activation, behavior on long-running projects and independent user feedback remain open.

### P4 — Usability and delegation
**Status: OPEN (planned 2026-11-11).** A `roadctl` command on PATH (`~/.local/bin/roadctl`, a small launcher for the installed copy) was set up on the owner's WSL machines on 2026-11-11.

- **P4.1 — Clear help for people and agents:** `roadctl help` and `roadctl help <command>`: what each command is for, whether it only reads or changes files, examples for one project and for all projects, and a short section for agents (what they may run without asking, what only the owner does). **Status: DONE** (implemented and accepted by the owner 2026-11-11).
- **P4.2 — Orchestration and delegation through the board:** one provider-neutral mechanism for handing a card or a criterion to another agent (Claude Code, Codex, Hermes, a script or a scheduled job) and taking the result back, based on Anthropic's orchestrator-workers guidance and the hosts' own sub-agent mechanisms. Replaces the parked P2.4b. Design agreed with the owner on 2026-11-11: any agent can orchestrate for a given task; the delegation lives in the card itself (flat header fields plus a `Delegation` section, one delegation per card at a time); hand-off by push (the delegating agent starts the worker with its host's mechanism) or by pull (a worker or a scheduled job claims open delegations through git, with a lease); a script or a scheduled job can delegate but cannot accept; only an agent that verifies the evidence moves a card to `review`, and only the owner marks it `done`. **Status: PARTIAL.** Implemented and tested without a model (2026-11-11): `delegate`, `undelegate`, `tasks`, `claim`, `report`, `accept`, `return`, an optional executor registry, Claude Code subagents through `agents-install`; remaining: the owner's check in live sessions.
- **P4.3 — Subscription limits and the owner's reserve:** `roadctl limits` reads each provider's remaining limits without a model where possible (Codex: `codex app-server` `account/rateLimits/read`; Claude Code: the `rate_limit_event` of one minimal request to a light model, checked 2026-11-11) and through a configurable command for other providers (Hermes, Kimi, Z.ai and others later). Default reserve for subscriptions, configurable: keep 10% of the weekly and 15% of the five-hour limit for the owner. An unknown limit is first checked by one light-model request; if it stays unknown, nothing starts automatically until the owner confirms. Every automatic start is recorded with the limits seen before it. **Status: DONE** (checked live on both WSL machines and accepted by the owner 2026-11-11).
- **P4.4 — Scheduled orchestrator:** `roadctl tick` run by any scheduler (Hermes cron, systemd timer, Windows Task Scheduler) for any agent in the registry. A model-free first step pulls the board, collects work (open delegations this agent can take, results to accept, expired leases, approved ready cards) and checks the limits; a model is started only when there is work and the reserve allows it, with a short JSON input and turn, time and effort limits. One orchestrator at a time; never `approve`, `done` or external actions outside the approved scope. **Status: PARTIAL.** `roadctl tick` implemented and tested without a model (2026-11-11); remaining: the owner sets up a scheduled job and checks it.
- **P4.7 — Autonomous or personal work:** the owner decides what goes to unattended work and what stays personal, through `roadctl` or by asking an agent (which then uses `roadctl` or edits the files): a per-board switch (off by default, optionally limited to some agents), an approval scope `auto` for cards that may start without the owner, and an ordered queue; `tick` offers only the first eligible queued card; an overview shows which projects and cards are open to autonomous work and what an agent would take now. **Status: PARTIAL.** Implemented and tested without a model (2026-11-11); remaining: the owner sets the rules per project with an agent.
- **P4.8 — Finding the board:** `where` explains when a folder has no board and lists the boards it knows; `--project NAME` picks a board by name; the skill tells an agent working from a parent folder to record on the board of the project it actually worked on; users without a central workspace register project boards in a user-level list so that `--all`, `tick` and the registry work for them too. **Status: PARTIAL.** Implemented and tested without a model (2026-11-11); remaining: the owner's check in a live session started from a parent folder.
- **P4.9 — Recurring project routines:** routines kept on a project's board (for example: collect the state of merge requests, issues and messages and update the cards; watch servers and support requests), each with a schedule, an on/off switch, the model tier it needs (a light model is enough for most), what it may read and write, and when to hand over to an orchestrator, a stronger model or the owner. `tick` lists routines that are due, under the same limits and autonomy rules; a routine's run is recorded with its result. The agent, model and environment are required fields of a routine; without them it does not run. **Status: PARTIAL.** Implemented and tested without a model (2026-11-11); remaining: the owner creates and checks a real routine.
- **P4.10 — Routines without a model:** a routine that only runs a script and evaluates its result mechanically; a model is involved only when the result needs attention. **Status: IDEA** (after P4.9).
- **P4.11 — Before the first scheduled runs:** `tick --routine <id>` so that a scheduler can run one routine as its own job (Hermes cron with its own model); an optional time window for routines (`hours`, for example weekdays 9-19); a working directory recorded with a claim, and a warning when an expired claim is taken over while that directory still has uncommitted changes. **Status: DONE** (accepted by the owner 2026-11-11).
- **P4.12 — Quiet monitor and the laptop routine:** the Hermes monitor script keeps printing its last output while there is nothing new, so Hermes does not wake the model once more after finished work; a routine's prompt names its previous run so that the next due run is still a change; the routines script starts a routine of another machine (Claude on the laptop) over ssh without a Hermes model. **Status: DONE** (done by Codex through a board delegation; accepted by the owner 2026-11-11).
- **P4.5 — Hermes as orchestrator and launcher:** how Hermes's subscriptions and API keys report limits and how it starts other agents. **Status: IDEA** (separate discussion).
- **P4.6 — Research: a general launcher:** whether `roadctl` should grow into a scheduler with a TUI and scenarios that may run without any model, or reuse an existing tool. Candidates to review: Dagu (cron and DAG workflows in YAML, one binary, web UI), Backlog.md (Markdown task board with TUI, web UI and MCP), ORCH and 5dive (agent task queues and scheduled agents), Claude Squad and agent-deck (TUI for several agent sessions), ccusage (local usage reports). **Status: IDEA.**

### P5 — Reliable orchestration and routines
**Status: OPEN (planned 2026-11-13).** Scheduled runs and routines (P4.4, P4.9, P4.12) work, but a run leaves no record of its outcome, a lost result or a hung model is not noticed, the scheduler lock is released before the model starts, and "read only" is promised by the prompt rather than enforced. This track adds well-known practices of agent schedulers (a run ledger with outcomes, a whole-run lock with a timeout, a kill switch, a read-only `doctor`, rules first and the model only on a deviation, tests on fakes) to `roadctl` itself, fitted to a text board, a dependency-free Node tool, several agents and several machines. No external framework is required. Our own strengths stay: subscription limits and the owner's reserve, provider neutrality, a git board as the contract.

- **P5.1 — Run ledger with outcomes and run summaries:** every run of a routine, the duty orchestrator or a delegated task records its start, end, outcome, reason and structured summary fields; runs that never finished are found and marked. **Status: IMPLEMENTED (2026-11-13), awaiting owner acceptance.**
- **P5.2 — Run supervisor:** `roadctl supervise` (POSIX) holds a per-routine lock for the whole run with a heartbeat, enforces a timeout, can detach from the caller, finds an orphaned run after a kill, and records `failed: no result` when a run ends without reporting. **Status: OPEN.**
- **P5.3 — Permission boundaries, part A:** an unattended mode in which owner-only commands refuse, an always-on audit of owner commands shown in the summary, lint for broad permission rules. **Status: OPEN.**
- **P5.4 — Outcome policy:** repeated failures hold the routine until the owner resumes it; a started run that may have written outside is never retried automatically; retries are deferred until the pilot shows a need. **Status: OPEN.**
- **P5.5 — Local pause and resume:** stop everything unattended on one machine at once, without editing git (core: a state file, a dedicated `tick` exit code, `status`). **Status: IMPLEMENTED (2026-11-13), awaiting owner acceptance.**
- **P5.6 — Routines with a watchdog:** a script collects facts and `roadctl routine observe` compares them with the last snapshot by stable keys, without a model and without `roadctl` running anything from the board; continues P4.10. **Status: OPEN.**
- **P5.7 — Cheap runs, part A:** only the tools a routine needs, the prompt on stdin, turn and time caps. **Status: OPEN.**
- **P5.8 — Shadow mode and write gate:** a new routine first runs dry and shows what it would write; the owner promotes it. **Status: PARKED** until the watchdog and the pilot are done.
- **P5.9 — `doctor` and the installed version:** read-only environment checks (paths, state directories, environment passing, clock skew, version and checksum of the installed copy). **Status: IMPLEMENTED (2026-11-13), awaiting owner acceptance.**
- **P5.10 — Scheduler test foundation:** fake executors, a shared clock helper, a private-marker check, `tick --json` as the contract for its consumers, help and docs kept in step. **Status: IMPLEMENTED (2026-11-13), awaiting owner acceptance.**
- **P5.11 — Schedules:** time slots and routines that run after another one. **Status: PARKED** (the skipped-slot rule moves to P5.21).
- **P5.12 — Contract for an external routine runner:** **Status: MERGED INTO P5.10 and P5.21** (no separate runner field is needed; the contract becomes documentation plus a stub test).
- **P5.13 — Run summary and delivery to the owner:** a structured summary for every unattended run and delegated task, a model-free `roadctl digest`, a notification policy (problems at once, a daily overview with overdue routines). **Status: IMPLEMENTED (2026-11-13), awaiting owner acceptance.**
- **P5.14 — Version compatibility:** a `requires` field so that an older installed copy does not run a routine it cannot fully understand. **Status: IMPLEMENTED (2026-11-13), awaiting owner acceptance.**
- **P5.15 — Approval bound to routine content:** a routine changed after approval stops running until it is approved again. **Status: OPEN.**
- **P5.16 — Module layout for new parts:** new parts of `roadctl` live in separate modules and test files; old code stays untouched. **Status: IMPLEMENTED (2026-11-13), awaiting owner acceptance.**
- **P5.17 — Limits in the duty loop:** no polling before a known reset, a rule for what to skip first when a limit nears the reserve. **Status: OPEN.**
- **P5.18 — Routine resumption pilot:** a checklist for turning routines back on and closing the P4 leftovers, run by the owner. **Status: OPEN.**
- **P5.19 — Permission boundaries, part B:** an `allow:` field and a printed permission profile (Claude only), after approval by content hash. **Status: OPEN.**
- **P5.20 — Spending record and cap:** a defined unit and a daily cap. **Status: IDEA** (after the pilot).
- **P5.21 — End-to-end scenarios and the external runner contract:** the end-to-end half of P5.10, two-clone scenarios, the documented contract for any other scheduler. **Status: OPEN.**
- **P5.22 — Delegation lease renewal:** `claim --renew`. **Status: IDEA.**
- **P5.23 — Work environment separate from the executor's machine:** a routine or delegated task names the environment it works in; the registry may describe how an executor on another machine reaches it (ssh, MCP) and a local launch policy (`remote-access` or `on-host`), so a launcher can run the model at home and reach the work machine instead of starting an agent there. Both ways stay supported; without the registry section nothing changes. **Status: OPEN.**
- **P5.24 — Owner questions and decisions:** an agent asks the owner through `roadctl ask` in one of three forms (a confirmation, a list of points with options or free text, a free answer), the card waits blocked by the owner while the agent takes other work, and `roadctl inbox --json`, `roadctl answer` and `roadctl act` give any channel one model-free contract; answers land in the card Log and the audit of owner commands, `tick` offers `RESUME`. Without an answer the agent chooses nothing: a recommended option is recorded, an answer-by-default mode may come later as a configuration key. **Status: OPEN.**
- **P5.25 — Conductor service:** `roadctl serve`, a loop of `tick` and `supervise` that starts the agents for routines and tasks on one machine, reaching other machines through the environments of P5.23 (ssh, autossh, a private network); installers for systemd (Linux), launchd (macOS) and the Windows Task Scheduler; one instance per machine. Hermes and other schedulers stay supported as external runners (P5.21). **Status: OPEN.**
- **P5.26 — Owner channel plugin, Telegram first:** a bridge process outside `roadctl` that sends the digest, shows confirmations with buttons, walks through questions point by point, takes free answers and shows the metrics, using only the contract of P5.24 and P5.27; only the owner's account, one-time tokens with an expiry on every button, no arbitrary commands. Other channels (VK, a mobile app) are further bridges on the same contract. **Status: OPEN.**
- **P5.27 — Autonomy metrics:** `roadctl stats [--json]` computed from the run ledger, the audit of owner commands and the questions: the share of runs finished without the owner, how long work waits for the owner (question to answer, review to acceptance), escalation reasons, work returned from review, failures and time per run. Channels only show them. **Status: OPEN.**

Stages (approved one at a time, the first two first): 0 preparation (P5.16, P5.10, P5.14); 1 visibility (P5.1, P5.13, P5.5, P5.9); 2 no duplicates, hangs or excess rights (P5.2, P5.3, P5.15, P5.7, P5.6, P5.23, P5.27); 3 policy and savings (P5.4, P5.17, P5.19, P5.21, P5.24); 4 conductor and owner channel (P5.25, P5.26); 5 the pilot (P5.18). Unattended writes to external systems stay out of scope until the pilot ends.
