# Roadmap

This is the project's current development plan, not a promise of delivery dates. Evidence and decisions belong in linked notes when needed. Documentation validation does not prove an agent follows the skill.

## Current state

The public draft defines the portable skill, documentation and proposed evaluation scenarios. Scoped installation, discovery and explicitly requested skill-use checks have been performed; automatic activation, behavior on long-running projects and independent user feedback remain open.

## Items

### P0.1 — Verify real agent behavior

**Status: PARTIAL — short comparison complete; broader coverage deferred.** The owner considers the short three-host checks sufficient for the present stage and wants the project to focus on managing long-running work, rather than proving benefit on a brief status question. The [Claude](evals/results/2026-11-10-claude-second-attempt.md), [Codex](evals/results/2026-11-10-codex-text-control.md), and [Hermes](evals/results/2026-11-10-hermes-text-comparison.md) checks produced correct answers with and without the skill; Codex and Hermes used narrower text-only harnesses. These results do not establish reliability, native activation or effectiveness on long tasks. The remaining scenarios in [evals/scenarios.md](evals/scenarios.md) and live-payload verification are not complete and are deferred, not silently accepted as passing. Further short tests are not a prerequisite for discussing the next stages; any future evaluation should target long-running work and use a separately agreed scope and budget.

### P0.2 — Verify installation and discovery

**Status: DONE (limited) — closed on the owner's instruction of 2026-11-10 on the evidence below; the limits stay open and are not claimed.** A project-scoped Claude Code installation was tested in WSL. Global installation from the public repository and a no-change targeted update were tested on Windows (the `.agents` target) and WSL (Codex). Model-free WSL tests in isolated homes verified both a changed local-source update and an update from the public GitHub repository: an older source was installed, then the published version was installed with `skills add --copy` and its files matched the current source. This does not prove changed-version updates on other hosts. Installed copies may contain local additions and must not be overwritten without reconciliation. Codex app-server on WSL and Hermes on Windows have discovered installed copies; the latter warned that the symlink resolves outside its trusted skills directory, and the warning was not bypassed. A subsequent model-free native discovery probe found `road-map-journal` in Claude Code on Windows, WSL and a second WSL host, and in Codex on both WSL hosts. One explicitly invoked, short model session per installation used the native skill mechanism; Codex command events showed the user-scope file read, while Claude invocation events did not independently identify its resolved file path. All gave the basic existing-plan and optional-dependency guidance; one Claude answer incorrectly claimed the optional dependency was not relevant to adoption. Discovery and explicit invocation do not prove automatic activation or reliable long-task behavior. A per-host update script (`scripts/update-installed.mjs`: report by default, `--apply` backs up, updates and verifies) has model-free tests in isolated homes on WSL and Windows; a report-only run of the published script on the real Home WSL, Windows and laptop-WSL installs found each up to date (the laptop copy was fetched from the public repository); it has no schedule or session-reload handling, and does not cover copies the `skills` CLI does not manage. Windows needs Node 22.20 or newer (the default `npx skills` resolved to an old cached 1.5.18 under Node 20). An account-synced Claude copy of the skill with the same name was not updated by `npx` and loaded as `anthropic-skills:road-map-journal`; the owner deleted it in the Claude account UI, and after the next Claude Code start on Home WSL, the laptop and Windows its manifest entry and folder were gone and a short `claude -p` listing showed only `road-map-journal` (file state and listing only, not a behavior check; `glab` was untouched). Owner decision 2026-11-10: updating stays manual, run in a terminal or by an agent with this script or the targeted `npx skills` command. A coordinator, schedule, notifications, an approved-hash gate and waiting for running agent sessions were considered and are not planned (cancelled by the owner, not implemented); running sessions do not block an update. Accepted limits: a real changed-version update on the real hosts has not been performed (all three real installs were only checked report-only because nothing was outdated; the changed-version path was exercised only in isolated homes), and the Hermes layout on hosts not yet inspected is unverified. The first real update will be the next skill release. No long agent sessions are required for this stage.

### P2 — Long-running work and a text board (design stage)

Detailed plan: [docs/p2-design-plan.md](docs/p2-design-plan.md). **The owner will run a separate agent to review and correct this plan before any P2 work starts; nothing is implemented.** Owner decisions of 2026-11-10 (design only; none authorizes implementation): a card carries the status vocabulary `idea | ready | doing | review | blocked | done | parked | dropped`, where decision and external dependencies become `blocked` with a reason, and projects that already have their own statuses keep them through an optional mapping; `approved` is a separate field (a plan is not permission to start); `claim` is added only when agents really work in parallel; new projects use `board/` at the root, while an adopted project keeps its existing layout; header keys are English and text uses the project's language; any command-line helper (`roadctl`) is an optional layer under `scripts/`, outside `skills/`, and is not installed with the skill. Work modes (one item, a track, continuous) stay separate from permissions, budget and allowed external actions. A stop-type hook reminds the agent once and never blocks; only mechanical facts (for example from git) may be added to a journal automatically, while decisions and reasons are written by the agent. Open decisions: the primary freshness safety net (git pre-commit `lint` with agent hooks as reinforcement is recommended, not yet chosen), whether a Hermes Kanban bridge is part of the first version, which agent verifies hooks first, and the license route for any code generalized from a private tool (see P0.3).

- **P2.1 — Board specification.** **Status: OPEN.** `docs/board-spec.md` with a worked example: three levels (generated board, one card per file, notes), card header, invariants such as no `done` without evidence per acceptance criterion; no private material.
- **P2.2 — `roadctl` prototype.** **Status: OPEN.** `brief`, `show`, `log`, `done`, `lint`, `sync` on a synthetic project. Depends on P2.1 and on the P0.3 license decision.
- **P2.3 — Native use without reminders.** **Status: OPEN.** A short pointer for `AGENTS.md`/`CLAUDE.md`, a compact skill description by situation, and hooks as reinforcement where a host supports them (Claude Code first; Codex and Hermes equivalents are unverified).
- **P2.4 — Long-running work protocol specification.** **Status: OPEN.** Modes, pause/status/stop, checkpoints, handoff, recovery after an interruption with unknown outcomes, a delegation package for sub-agents, an owner-question queue, layered budgets and acceptance recorded separately from agent completion. Host capabilities are to be verified, not assumed.
- **P2.5 — Pilot.** **Status: OPEN.** One end-to-end scenario with one coordinating agent and a sub-agent on a disposable project (Hermes first, then Claude Code and Codex), compared with no skill and the current skill, with a separately agreed scope and budget.
- **P2.6 — Optional Hermes Kanban bridge.** **Status: OPEN, optional.** Only if it proves useful after P2.1–P2.5.
