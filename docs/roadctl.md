# roadctl

Optional helper for a board-format project (see [board-spec.md](board-spec.md)). The core is one file, [`scripts/roadctl.mjs`](../scripts/roadctl.mjs); newer parts are small modules in [`scripts/roadctl/`](../scripts/roadctl/) next to it (see [developing-roadctl.md](developing-roadctl.md)). Node standard library only (tests pass on Node 20, 24 and 26). It is **not installed with the skill**: copy the file into your project (for example `tools/roadctl.mjs`) and keep its version line; copy the `scripts/roadctl/` folder next to it (without `*.test.mjs`) to get the module commands, a lone file runs the built-in commands only. For hooks at user level (Codex, Hermes) it needs one stable path: `node scripts/update-installed.mjs --roadctl --apply` installs or refreshes `~/.local/share/road-map-journal/roadctl.mjs`. Files stay the source of truth; the skill and a person can edit cards by hand without it. It never sets `approved` on its own initiative and only checks that references exist, not that evidence is true.

Not sure where to start? `roadctl help` prints an overview grouped by task (what each command is for, and whether it only reads, writes board files or uses git), a quick start for all projects, one project and one card, and the boundaries for agents. `roadctl help <command>` (or `roadctl <command> --help`) gives purpose, usage, flags, examples, what the command changes and its exit codes; `--help` never runs the command and writes nothing.

Owner-only commands: `answer`, `undo`, `approve`, `auto`, `done`, `resume`, and for some calls only `queue` (add, remove, move), `pause` (every call but `pause status`), `mandate` (approve), `routine` (on, off, resume, promote), `autonomy` (on, off, routines), `limits` (--confirm), `boards` (add, remove), `inbox` (defer) and, with `--apply`, `hook-install`, `hook-uninstall`, `instructions-install`, `instructions-uninstall`, `agents-install`, `agents-uninstall` (see [Unattended mode and the owner audit](#unattended-mode-and-the-owner-audit)). An agent runs them only on the owner's explicit words in the current conversation; `roadctl help <command>` says so, and `roadctl help unattended` prints what an agent may do without the owner. Help topics (`roadctl help <topic>`): `unattended`; modules may add more.

Global flags: `--board <dir>` (default: search upwards for `board/config.json`, then the known boards, see [Finding the board](#finding-the-board)), `--project NAME` (a known board by project or `match` name), `--workspace DIR` (or `ROADCTL_WORKSPACE`), `--date YYYY-MM-DD`. Exit codes: 0 ok, 1 findings or refusal, 2 usage error, 3 limits unknown (only `limits --check`).

## Finding the board

Which board a command works on is decided in this order (the first hit wins):

1. `--board DIR`, or `--project NAME`: a known board by project name or `match` name (an unknown name exits 2 and lists the known projects).
2. The project board: `board/config.json` in the current directory or above it.
3. A known board whose **project folder name** (the folder above its `board/`) or one of its `match` names equals the name of the current directory or of an ancestor (case-insensitive, `_` and `-` equal). The central workspace is looked at first, then the user list.
4. None: commands exit 2 ("no board found ..."); `where` exits 1.

**Known boards** are the boards of the central workspace (`<workspace>/projects/<name>/board`, the first workspace root: `ROADCTL_WORKSPACE`, the pointer file, `~/projects/agent-workspace`) plus the **user list** for people without a central workspace: `${XDG_CONFIG_HOME:-~/.config}/road-map-journal/boards`, one absolute board directory per line, `#` comments. The name of a listed board is its project folder name. Everything that iterates over all boards (`--all` of `lint`, `status`, `list`, `next`, `tasks`, `tick`, `autonomy`; `--project`; the listing of `where`; discovery by folder name) uses the workspace boards and the listed ones together, deduplicated by real path (a symlink to a board is the same board). A project board in the project folder still wins over both.

`roadctl boards [list] [--json]` shows them (name, `workspace` or `list`, directory, `match` names; a listed directory that is gone is marked `MISSING` and not used). `roadctl boards add [dir]` records a board (default: the one found from the current directory; already known paths are not added twice) and `roadctl boards remove <dir|name>` forgets one (comments and other lines of the file stay; an ambiguous name is refused). Both only edit that one file; no board file changes.

**`roadctl where [path]`** prints the board for `path` (default: the current directory), so a session that started in a parent folder of several repositories can ask for the repository it actually works on. When nothing is found it exits 1, prints nothing on stdout and writes to stderr `no board for <dir>`, the known boards (name, directory, `match` names) and the ways out: `--project NAME`, `--board DIR`, adding the folder name to `match` in the board's `config.json`, or `roadctl boards add`.

**Registry lookup** (executors, limits, roles): `ROADCTL_REGISTRY` (a file that does not exist then means no registry) -> `<workspace>/agents/registry.json` -> `${XDG_CONFIG_HOME:-~/.config}/road-map-journal/registry.json`. The first that exists is used.

## Overview without an agent

`status`, `list` and `next` only read the board files; they need no model and write nothing. `--all` covers every known board: the boards of the central workspace (the first workspace root found) and the user list (see [Finding the board](#finding-the-board)), without duplicates, as for `lint --all`. `status` prints one row per project (counts per status, `oldest as_of` among doing, review and blocked cards, lint errors and warnings, whether autonomy is `on` or `off`) and one line per doing card. `next` is a view, not a decision: `ready` means defined, **not** permission to start, so a ready card without `approved` is marked as needing the owner's approval, and a ready card is "waiting" until every id in `depends_on` is `done`. Card titles in text output are sanitized like in `brief`; `--json` returns the raw values for scripts. What these commands cannot tell is whether a status matches reality: that still needs a person or an agent reading the evidence. How far a board is behind its server is not shown yet (P3.2).

## Synchronization with the server

Plans live in a git repository (a central workspace, or the project). `pull` and `save` keep a board in step with other agents and machines without anyone typing git commands.

- `pull`: `git fetch`, then `git rebase --autostash` on the upstream. Uncommitted changes are kept. If the rebase conflicts **only** in generated `BOARD.md` files they are regenerated from the merged cards and the rebase continues; any other conflict aborts the rebase, leaves the tree as it was and reports the files (status `conflict`): two agents edited the same text, so a person decides. If the server cannot be reached the status is `offline` and work continues on the local state.
- `save ["message"]`: regenerates a stale `BOARD.md`, runs `lint` (errors refuse the save, nothing is committed), commits **only the board's paths** (the project folder `projects/<name>` in a central workspace, `board/` in a project; other changed or staged files are left alone and counted in the message), rebases on the upstream like `pull`, lints the merged result, pushes. It never forces. If someone pushed in between it integrates once more and retries. If the server is unreachable the commit stays local (`saved-local`, exit 0) and the next `save` pushes it. It refuses to push when unpushed commits touch paths outside the board (`foreign-commits`), and when the merged board has lint errors (`lint-after-merge`). Without a message the commit is `board <project>: update <card ids>`.
- Statuses that are not failures (exit 0): `up-to-date`, `pulled`, `offline`, `no-remote`, `saved-local`, `nothing-to-save`, `pushed`. Everything else exits 1 with the reason.
- `status` shows an `origin` column (`in sync`, `behind N`, `ahead N`, `N uncommitted`, `no remote`) from the last known state; `status --fetch` asks the server first.
- `log`, `new` and `review` print a warning to stderr when the board is known to be behind origin (no network is used for that check).
- Network limits: `ROADCTL_GIT_TIMEOUT_MS` (default 15000); git never prompts (`GIT_TERMINAL_PROMPT=0`, ssh `BatchMode`).

**A clone of its own for the service, and the repository lock (P5.29).** The conductor service (P5.25) works in **its own clone** of the boards repository, never in the working clone of the owner: `git clone ORIGIN SERVICE_FOLDER`, start the service with `ROADCTL_WORKSPACE` (or `--board`) pointing there. The two clones share only the remote (a bare repository, or the server): the service `pull`s and `save`s in its clone, the owner in the working clone, and the usual `pull` joins the two histories (a conflict is handled by the rules above, never by overwriting). So an uncommitted edit of the owner is never taken into a service commit and a rebase of the service never stashes the owner's file. Inside one clone, the operations that read a board file and then commit, rebase or push it (`pull`, `save`, `claim`, `report`, `routine done`) take a **repository lock**: the file `roadctl-repo.lock` in the git directory of the clone (`.git/`, so never committed; a linked work tree has its own). Two processes of one clone, for example the service and an agent, or two agents, take turns: the second waits (up to 60 seconds, `ROADCTL_REPO_LOCK_WAIT_MS`; `0` does not wait) and starts from the board as the first left it, so no write is lost and `index.lock` is not fought over. If the lock is not free in time the command changes nothing, prints status `busy` and exits 1; the lock file holds the pid and host of its owner, and it is taken over **only when the owner is dead** (same host, the pid no longer exists); its age alone never opens it, because a push can take minutes. A lock of another host (a clone on a shared disk) cannot be checked: it is waited for, and taken over with a warning only after 6 hours; an unreadable lock file is waited for too. A short `index.lock` held by another git (an editor, the owner's shell) is waited out for about two seconds. `doctor` (`service-clone`) warns when the `service.workspace` of `conductor.json` is the working clone of the owner. This lock is not the build lock of [`roadctl lock`](#handoff-build-lock-and-worktrees-p541-slice-1-line-b), which orders test runs.

**Autosync (opt-in).** Hooks keep their rule of never changing anything unless the owner opts in, with `"autosync": true` in `board/config.json` (shared by every host and agent that uses this board) or `ROADCTL_AUTOSYNC=1` (`0` forces it off). Then the `SessionStart` hook runs `pull` before the brief, and the `Stop` hook runs `save` when the board has uncommitted changes or unpushed commits. Without autosync `SessionStart` only fetches (4 second limit, `ROADCTL_NO_FETCH=1` disables it) and adds one line to the brief ("behind origin by N commit(s)", "N local commit(s) not pushed", "origin unreachable", "up to date"). A successful autosave is silent; a problem (conflict, lint error, rejected push) is passed to the agent once so it can tell the owner. The reminder check runs before the autosave, and a successful autosave records the card's Log state so the reminder is not triggered for work that was already written down. Hooks have short timeouts (Codex kills a hook after 10 seconds); a kill during `fetch` or `push` is harmless, and the rebase itself is local and fast.

## Hooks

Hooks are reinforcement, never the only mechanism, and they never change statuses, set `approved`, block an agent or fail a session (an internal error becomes a no-op).

- `session-start`: prints the brief as `additionalContext`. Also useful after compaction.
- `pre-compact`: asks that the active card, open criteria and decisions be kept in the summary.
- `stop`: when exactly one card is `doing`, the working tree has changes outside the board and the board was not touched, it reminds the agent **once** until the card's Log changes (a marker file in `.git` records it). It stays silent when `stop_hook_active` is set, with zero or several `doing` cards, and outside git. Claude Code gets `additionalContext`; with `--host codex` it answers `{"decision":"block","reason":...}`, which Codex turns into one continuation prompt.
- `hermes-pre-llm`: Hermes only uses the return value of `pre_llm_call`, so this one hook gives the brief on the first turn of a session and the same one-time reminder on a later turn (`{"context": ...}`). Hermes hooks see only the session's working directory, so they work when Hermes runs inside the project.
- `hermes-api-error`: observes 429/402 or Hermes `rate_limit`/`billing`/`quota` reasons on every failed attempt, before retry, credential rotation or fallback. It records only an empty local sentinel, scoped by board and git state directory; no provider payload or card is written. `hermes-pre-llm` reminds on subsequent turns, including the same session, to reconcile actual work and identify its own card; an observation is neither a terminal outcome nor a checkpoint. The sentinel is not deleted by delivery: a failed model call may never receive the reminder. After reconciliation, an operator can remove the matching `roadctl-hermes-limit-<sha256 of absolute board path>` file from the current git directory (or `roadctl-<sha1 of board path, first 12 hex>` in the temp directory when no git exists); this manual operation can race with a new observation. Markers are local, may be lost, and different worktrees/state directories do not share them. They are not a durable handoff.
- **Reserve and checkpoint limitation:** the hook cannot compact, save the session's in-flight context or enforce a reserve while an API request is running. Before starting and at safe checkpoints, use the existing `roadctl limits --check <provider> --fresh --json`; inspect the measured state, not just the exit code (an owner confirmation can allow an unknown reading). Stop restricted work when the reserve is reached or the reading is unknown. The handoff is written by the limit checkpoint (see "Limit checkpoint") only to a card bound to this agent or session. Shared usage can change between checks; Claude's fresh probe spends a small request. A reliable mid-request threshold and acknowledged checkpoint need host/provider support and an explicit task-to-card binding.
- `limit-stop`: a proof that the work was stopped by the subscription limit; it exists for a host that has its own event for that and is wired by hand (see "Limit checkpoint"). The other events never treat a lone 429 as a stop.
- `pre-commit` (git): runs `lint`; errors block the commit, warnings never do.

Installers (dry run by default, backup before writing, existing hooks kept, idempotent, undone by `hook-uninstall`):

- `--claude`: the three Claude Code hooks into the project's **local, uncommitted** `.claude/settings.local.json`; with `--user` into `~/.claude/settings.json` (or `$CLAUDE_CONFIG_DIR`) instead, which is the right place when boards live in a central workspace. The hooks are silent in directories without a board.
- `--codex`: `SessionStart` (all sources, so it also runs after compaction) and `Stop` into the user-level `~/.codex/hooks.json` (or `$CODEX_HOME`), with `command` (plus `commandWindows` when installed from Windows) and a 10 second timeout. User level is used because the hooks are silent outside board projects and a project `.codex/hooks.json` would be committed. Codex does not run a new hook until you review and trust it in `/hooks`; roadctl never edits the trust state. `PreCompact` is not installed for Codex because Codex ignores its output.
- `--hermes`: one marked block (`# roadctl-managed begin/end`) appended to Hermes `config.yaml` with two entries: `pre_llm_call` -> `hook hermes-pre-llm` and `api_request_error` -> `hook hermes-api-error`; it refuses to edit a file that already has a top-level `hooks:` key and prints the entries to merge by hand. Hermes asks you to approve a new hook the first time it sees it (`hermes hooks list` shows the status; non-interactive runs need `--accept-hooks`, `HERMES_ACCEPT_HOOKS=1` or `hooks_auto_accept`, which roadctl does not set).
- `--git`: writes `.git/hooks/pre-commit` only if none exists; an existing foreign hook is never touched. With `--all` (run inside the workspace repository) the hook lints every board of the workspace.

## Delegation

Any agent or script can hand a card (or some of its criteria) to another executor and take the result back; the delegation lives in the card (`delegate` and `claim` headers, optional `## Delegation` section, format in [board-spec.md](board-spec.md#delegation)). One active delegation per card; parallel work means separate cards with `depends_on`.

1. `delegate <id> --to worker --by me@host [--host codex] [--criteria a2,a3] [--accept by]` requires `scope=implementation` or approval through the project mandate. It refuses `done` or `dropped` cards, and when a delegation is already active. It adds a Delegation template to fill in (allowed changes, checks, stop conditions, budget, report format) and a Log line. Fill it in, then `save`, so executors see it.

**Who takes the work (roadctl 0.14.0).** `--to` and `--as` (and `ROADCTL_AS`, set once per session; `--as` wins) accept three names beyond the plain executor: a **profile** from the registry's `agent_profiles` (the profile's `executor` and its `openbot.name`/`openbot_variants`, e.g. `pi-developer`, and its variant `pi-developer-small`), an **executor** (`claude-code@home-wsl`), and a pair **`orchestrator/profile`** (`openbot@home-wsl/pi-developer`). Matching at claim: a delegation to a profile is taken by that profile from any orchestrator or harness (or by its variant), or by that profile's own executor under its name (`--as pi-worker@home-wsl`, and `roadctl tasks --for pi-worker@home-wsl` lists it); a delegation to an orchestrator by any of its profiles (`--as openbot@home-wsl/...`); a delegation to an executor by the executor itself or by a profile whose `executor` is it. An unknown name is refused with a hint that lists the known profiles and executors; a name the registry does not know but that has the form of an executor (`x@host`) is read as an orchestrator, so the delegation is written and one warning on stderr says that a plain `claim --as x@host` will refuse and only `x@host/<profile>` can take it (the same warning names a role that no agent of the registry has). The claim stores the executor; the Log line writes both names (`pi-developer (pi-worker@home-wsl)`). The same names work where `--as` names the executor of a run: `roadctl tick --as pi-developer` offers the items of `pi-worker@home-wsl` and its text names both, `roadctl limits --check pi-developer` checks that executor's provider (`hermes@windows (profile pi-developer) (provider some-api)`), and `roadctl routine done ID --as pi-developer` records the run for a routine of `pi-worker@home-wsl` under the executor name. A name the registry does not know keeps the old behaviour there (a plain executor name; `limits` still refuses it as before). A direct harness without a registry works exactly as before. Boards using profiles or orchestrators must set `"requires": "0.14.0"`; an older copy reads the delegation as a role or an agent and refuses it (it never takes it wrongly).
2. The executor is started by the delegating agent (push: a Claude Code subagent `road-worker`, `codex exec`, Hermes's own delegation) or finds work itself (pull: `roadctl pull`, `roadctl tasks --for me@host`). Either way it runs `claim`, works, and ends with `report`; both publish themselves (see below), so the delegating side sees them after a `pull`.
3. `accept` or `return` by the allowed acceptor, then `roadctl save` to publish (these two only edit the card, because the acceptor is typically an orchestrator that saves its board work anyway). The result is data to verify; the owner alone marks the card `done`.
4. `undelegate` withdraws a delegation that is no longer wanted.

`tasks` shows every delegation with its state (`OPEN`, `CLAIMED`, `EXPIRED` when `until` has passed, `REPORTED`); `--for AGENT` keeps what that agent may take now: open or expired, `to` equal to the agent or a role the agent has in the registry, and the host matching (`any` matches all). `brief`, `status` and `next` show counts and one line per delegation (`--json` adds a `delegations` list; `status --json` also `delegated`).

**Claim and races.** `claim` accepts only open or expired delegations the agent is eligible for, requires the owner's approval (`scope=implementation`, or a current `by_mandate`), moves a `ready` card to `doing`, and refuses when a registry exists and the delegating agent (`by`) is not in it. It writes `claim` and `state=claimed` (lease `--lease`, default `2h`, at most `7d`), commits **only that card** (it refuses when the card file has other uncommitted changes: `save` first) and pushes. The push is the arbiter. If the server rejects it, `claim` integrates the upstream; when the same card was changed there (a conflict) or the merged card no longer shows this claim, the claim is **lost**: the local claim commit is removed, the card is left as the server has it, other work (including uncommitted changes) is kept, the message names the holder and the exit code is 1. If the server only has unrelated changes the rebase is clean and the claim wins. Outcomes: `claimed` (pushed, exclusive; exit 0), `claimed-local` (offline, no remote, no upstream, no git, or unpushed commits outside the board: the claim is local and **not yet exclusive**, another agent may take it; exit 0; the next `save` pushes it), `lost`, `refused`, `error` (exit 1). Run `pull` before `tasks` to see the server's state; without it a stale view only costs a lost claim, never two holders.

**Working directory of a claim.** `claim --workdir DIR` (an existing directory, stored as an absolute path) writes it into the header: `claim: <agent> at=... until=... workdir=/abs/path` (spaces and `%` in the path are percent-encoded, so the header stays one token per field; lint rule 17 checks that it is absolute). Autonomous code work belongs in its own git worktree, and the claim says which one. When an **expired** claim is taken over and the previous claim named a directory that exists on this machine and `git -C DIR status --porcelain` is not empty, `claim` prints a `WARNING` on stderr naming the directory and the previous holder (the claim still goes ahead and the exit code is unchanged; `--json` has the text in `warnings`), because the previous holder was probably interrupted (the PC was switched off) with unfinished changes that must be reconciled, not overwritten. `tick` marks such a `STALE` line with the stable suffix ` (workdir dirty)` (no counts and no paths in the text; the path and `workdir_dirty` are in `--json`), and the `--prompt` tells the orchestrator not to hand the card on before the changes are reconciled. A directory that is not on this machine, is not a git work tree or is clean gives neither warning nor suffix. `report`, `accept`, `return` and `undelegate` work as before and drop the claim with its `workdir`.

**Report publishes itself.** `report` (only the claimant) appends `REPORT: text` to the Log (up to 1500 characters), sets `state=reported`, removes the claim, then commits **only that card** and pushes it, like `claim`; it refuses when a criterion the delegation handed over has no Evidence line, when the card file has other uncommitted changes, and, with `--commit SHA`, when that commit does not exist in the claim's workdir (the project repository). Outcomes: `reported` (pushed; exit 0), `reported-local` (offline, no remote, no upstream, no git, or unpushed commits outside the board: the report is local and **not yet visible to others**, the next `save` pushes it; exit 0), `lost` (exit 1), `refused`, `error`. If the push is rejected it integrates the server's changes; when the card conflicts (for example the delegator added a Log line meanwhile) the report is applied again on the server's card as long as the claim there is still this agent's, and otherwise (the claim was taken over, for example after the lease expired) nothing is published, the card is left as the server has it and the command exits 1 with the holder named.

**Report and return text.** The text of `report`, `return` and `undelegate` goes into one Log line: control characters, newlines, backticks and angle brackets are removed, but `_ * [ ] #` are kept so paths and test names survive, and the cap is 1500 characters. Plain `roadctl log` cleans its text the same way (so names like `adcu_soc_sw!2576` survive) and caps it at 400. This is safe because only `show` prints Log text; the session brief, `status` and `next` inject header fields only (see [board-spec.md](board-spec.md)), and the entry is a single `- date [author] ...` line that cannot start a heading or a list item of its own.

**Who may accept or return.** `accept=by`: the delegating agent. `reviewer`: an agent with `can_accept: true` in the registry, or any agent that is not a script when there is no registry. An agent name: that agent. `owner`: nobody by command, the owner accepts by hand (`roadctl done` after review). A script (`cron:` or `script:` name, or `host: script` in the registry) can delegate and claim but never accepts or returns. `accept` removes `delegate` and `claim`, logs the acceptance and, when the card is `doing` and every criterion has evidence (`[x]` with an Evidence line or `[~]` with a reason), moves it to `review` with the same rules as `roadctl review`; otherwise the card stays as it was and the command prints which criteria lack evidence. `return` sets the state back to `open`, removes the claim and logs the reason. Both only edit the card: run `roadctl save` to publish.

**Withdrawing.** `undelegate <id> --by AGENT ["reason"]` removes `delegate` and `claim` and logs `UNDELEGATED`. Only the delegating agent (the `by` of the delegation; a script may withdraw its own) may; it works on an `open` delegation and on a `claimed` one whose lease has expired; any other state (a live claim, `reported`) needs `--force` and a reason. It only edits the card: run `roadctl save`.

**Registry (optional).** The file named by `ROADCTL_REGISTRY`, else `<workspace>/agents/registry.json`, else `${XDG_CONFIG_HOME:-~/.config}/road-map-journal/registry.json` (the first that exists, see [Finding the board](#finding-the-board)): `{"version": 1, "roles": {"worker": {"claude-code": "sonnet"}}, "agents": {"claude-code@home-wsl": {"host": "claude-code", "machine": "home-wsl", "roles": ["orchestrator", "worker", "reviewer"], "can_accept": true, "launch": "claude -p --model {model} \"{prompt}\""}}}`; a full example is in [`examples/agents-registry.example.json`](../examples/agents-registry.example.json). `roles` gives a model per host (used by `agents-install`); `agents` gives each agent's host, roles and `can_accept`; `launch` is a note for the delegating agent, roadctl never runs it. Without a registry everything works with fewer checks: a role in `to` is not verified (only the host is), `accept=reviewer` is open to any non-script agent and `claim` does not check `by`. The registry also carries optional `limits` and `providers` sections and a `provider` per agent (see [Limits and the owner's reserve](#limits-and-the-owners-reserve)). A registry that exists but is not valid JSON, or has a malformed `limits` or `providers` section, is an error (exit 2). Environment: `ROADCTL_NOW` (an ISO UTC time) replaces the clock, for tests.

**Subagents for Claude Code.** `agents-install --claude` writes `road-worker.md` (takes one delegation, follows the card's Delegation section, writes to the board only through `roadctl report`, never changes status, approvals or commits) and `road-reviewer.md` (verifies files and tests itself, runs `accept` or `return`, never `done`) into `~/.claude/agents` (or `--claude-home`), with the model from the registry roles (default `sonnet`). Dry run by default, backup before overwriting, idempotent, other files in that folder are never touched; `agents-uninstall` removes only files carrying the roadctl marker. For Codex and Hermes there is no file to install; see the delegating protocol in the skill's `references/long-running.md` (host commands there are examples to check against the host's current documentation).

## Orchestrator reconciliation and a closed limit (P5.41, slice 3, a10)

An orchestrator is an external system that runs agents (a chat platform, a scheduler, a bot); roadctl does not know its agents except through the registry (`agent_profiles`, `openbot`). Three hidden commands, `roadctl help orchestrator` describes each, let the orchestrator and the registry check each other. The orchestrator id is an instance, `system@machine` (`--orchestrator openbot@home-wsl` or `ROADCTL_ORCHESTRATOR`); `--orchestrator` takes a value only for `orchestrator` and `candidates` (`supervise --orchestrator` stays a switch).

- `roadctl orchestrator form --orchestrator ID` prints a JSON form: for every profile of the registry what roadctl expects (`expect`: executor, model, agent name, variants) and empty fields for what the orchestrator reports about itself (`name`, `id`, `model`, `available`), plus an empty `extra` list for agents it has that are not profiles.
- `roadctl orchestrator sync --orchestrator ID < filled-form.json` answers for each entry: `ok` (it matches the registry), `unknown` (the registry does not know the profile or name) or `mismatch` (the name, the id or the model differs; exit 1), and for each profile that was not reported: `not reported, kept`. A model matches when the two strings contain one another, ignoring case (`Claude Sonnet 5.5` matches `sonnet`); a variant of a profile may have its own `model`. `unknown` and a stale reconciliation are shown, not failures.
- `roadctl orchestrator status --orchestrator ID` shows the stored state: `none` (never reconciled), `stale`, `mismatch`, `unknown` or `ok`, with the age in hours and what to do.

**The cache** lives outside the board, in the roadctl state directory, one file per orchestrator id (`orchestrator-<id>.json`, mode 0600) with the time of the last reconciliation and the last answer per profile. A reconciliation older than **24 hours** is `stale` (registry `"orchestrator_sync": { "stale_hours": 24 }` changes the limit): a warning, **never a block**. What sync never does: change the registry, a card or a permission; create a profile, an executor or a link from an unknown name (such names are only listed as `unknown`, at most 20); delete a link because a list was short; widen a right (fields such as `roles`, `executor` or `can_accept` in the form are ignored). Nothing is written to git; the form is not a way to give an agent more access.

Example of a form for OpenBot (only an example: the core names no product; the fields are the same for any orchestrator). The orchestrator fills what it knows and sends it back:

```json
{ "form": 1, "orchestrator": "openbot@home-wsl",
  "agents": [
    { "profile": "claude-developer", "name": "claude-developer", "id": "agent-d9c5...", "model": "Claude Sonnet 5.5", "available": true },
    { "profile": "pi-developer", "name": "pi-developer-small", "id": "agent-362c...", "model": "Flash", "available": true }
  ],
  "extra": [] }
```

**A closed limit in `candidates`.** An executor whose provider has no limit left (the owner's reserve reached, or `closed_until` of the limits cache of P5.17 ahead) is refused, as before, and the answer now says which provider is closed and until when (`closed_until`, `provider`) and carries a `replacement` block: the first agent of the owner's list that passed every check and has an agreed profile (`agent_profiles`; with `--orchestrator`, one that the last reconciliation matched and did not report unavailable), `source: list`; if there is none, an executor of another profile that has the role and passes the same checks, `source: profiles`, **as advice only** (`advice_only`: outside the owner's list, never chosen, nothing launched; the owner or the mandate decides). A candidate with no profile, or a profile the reconciliation does not agree, is listed under `skipped` with the reason. With `--orchestrator` the answer also carries `orchestrator: { id, sync, age_hours, hint }`, and a `stale` or `none` state is one warning line on stderr. `chosen` and the exit code are still decided by the owner's list.

## Handoff, build lock and worktrees (P5.41, slice 1 line B)

Three small commands that replace what coordinators used to write by hand into every assignment. They are the same for every harness and every orchestrator; they send, start and write nothing on the board. `handoff --to` a profile prints that profile's registry row (`registry: profile pi-developer -> pi-worker@home-wsl; roles worker, reviewer, model flash`), not just the executor's name; the executor's own name keeps its row. They are hidden from the `roadctl help` overview (its line budget) but `roadctl help <command>` describes each. Who may take a delegation (`--as`, `ROADCTL_AS`, profiles and orchestrator/profile pairs) is a separate part of P5.41: see the section "Who takes the work".

**`roadctl handoff <id> --to WHO [--role worker|reviewer|fixer]`** prints the standard assignment for one card, built from the card and the registry: the goal, the criteria for the assigned role (all criteria for reviewers), the branch and worktree (the names `roadctl worktree add` makes), the test command under the shared lock (`--tests`, else the `Checks` line of the card's Delegation section; a template line is not copied), what the executor must not do (merge into main, push, tags, `approve`, `done`, another card's worktree, the installed roadctl and skill, and anything outside `Allowed changes`), the report format (`ROADCTL_AS` or `--as`, `roadctl claim ID --as WHO --workdir <worktree>` so the limit checkpoint of P5.43 can bind to the card, one Evidence line per criterion, `roadctl report` with SHA and test result) and the advice to save limits (short caveman style in work, `codegraph explore` for code questions, `rtk` for git and test output, where installed). `--role reviewer` makes it read-only and adds the review rule below; `--role fixer` lists the findings from `--note` and says to fix only those. `--to` is any name the coordinator uses; a name the registry knows adds its roles and model to the header line. `--json` gives `{ card, to, role, text }`. The text names no product.

**The review rule** (in the reviewer text and in the skill): return the work only for (1) a violated criterion of the card, (2) a failing test or an incompatibility, (3) a defect with a reproducible scenario (input, wrong result). Everything else (style, naming, a better idea, a risk without a scenario) goes to a "later" list in the verdict, not into a return. At most two review rounds per card; after the second, stop and escalate remaining blockers, and move only non-blocking follow-ups to another card. A second review looks only at the earlier blockers and the new diff. The first line of the verdict is `accept`, `accept with follow-ups` or `return`.

**`roadctl lock [--file PATH] [--wait SPAN] -- COMMAND`** runs COMMAND while holding the build lock of the project, so two test runs of one repository (two worktrees, two agents) never overlap. The second caller waits (default up to 2h; `--wait 30m`) and then runs; if the lock is not free in time it exits 73 and the command does not start. The exit code is the code of COMMAND. The lock file is `--file`, else the environment variable `ROADCTL_BUILD_LOCK`, else the optional key `build_lock` (an absolute path) in the board's `config.json` (a board without it is unchanged; older copies ignore the key), else `build.lock` in the roadctl state directory. With `flock(1)` on the machine the lock is a `flock` on that file, so `flock FILE command` written by hand and `roadctl lock` exclude each other; without it (macOS, native Windows) a lock file with a heartbeat does the same between `roadctl lock` calls (`FILE.roadctl`).

**`roadctl worktree add|list|prune <id>`** keeps one git worktree and one branch per card. `add` needs a card that exists on the board: it makes the branch `<id>-<up to three ASCII words of the title>` (else `<id>-work`; the id in lower case) from `--base` (default `main`, else `HEAD`) and the worktree `<repo>-<id>` next to the repository; a second `add` shows what exists and changes nothing, and an existing directory or branch is refused. `list [id]` shows each worktree of the repository with its branch, `clean` or `dirty`, and `merged` or `unmerged` into the base. `prune <id>` removes the worktrees and branches of that card and nothing else (never the main work tree, never another card's): a worktree with uncommitted changes, or a branch not merged into the base, is refused (exit 1) unless `--force`. The repository is the git work tree of the current directory, or `--repo DIR`.

```text
roadctl worktree add P5.41            # ../repo-p5.41 on branch p5.41-<words>
roadctl lock -- node --test scripts/  # the tests, one run of the project at a time
roadctl handoff P5.41 --to pi-developer --role reviewer
roadctl worktree prune P5.41          # after the merge
```

Slice 4 of P5.41 (events by webhook) is a design only: [webhook-events-design.md](webhook-events-design.md).
## Limit checkpoint (P5.43 a2, a3)

When work is stopped by the subscription limit, or the limit is near, the card in work gets a **handoff entry on its own**, and the next session continues from it without the owner retelling anything. No model is asked; roadctl writes it from data it already has.

**Signal ("near").** The limits cache of P5.17 (`roadctl limits --check` fills it; a tick or an orchestrator that probes at phase boundaries keeps it fresh): a window with at most `reserve + 5` percent left (`"limits": { "checkpoint_margin": 5 }` in the registry changes the 5), or `closed_until` in the future. A cache older than 6 hours that is not closed, a window that has already reset, an unknown reading and a lone 429 are **no** signal. The hooks `pre-compact`, `stop`, `hermes-pre-llm` and `hermes-api-error` only look at the cache; they never probe a provider. **Stop proof:** `roadctl hook limit-stop` (or `roadctl limit-checkpoint --stopped`) is the explicit "the host ended because of a limit"; it writes without cache data.

**Binding (nothing is written without it).** The entry goes only to a card that is `doing` and whose `claim` names this agent (`ROADCTL_AS` or `--as`; the executor name, or the last part of `orchestrator/profile`) and, when the claim has a `workdir` (`roadctl claim ID --as AGENT --workdir DIR`), the session's directory lies inside it. With no agent known, the claim's `workdir` alone must contain the session directory. No card or more than one fits: nothing is written (the command says why). The claim lease time is not asked; a takeover by another agent changes the name.

**The entry** is one Log line, `limit-checkpoint ep=ID near|stopped: <signal> // state: <status>, open <criteria>, branch B at SHA, N changed files // in-flight: <open runs of the run ledger for this card, process names in the work directory> // resume after <reset>: roadctl pull; roadctl show ID; cd DIR; roadctl limits --check PROVIDER; check what ran ... then continue with the open criteria`. It holds no provider text, no error text, no environment and no command line (process names only). One entry per limit episode (the id comes from the provider and the reset time; a new reset is a new episode), under a lock. The card is edited, not committed: `roadctl save` or autosync publishes it. `roadctl limit-checkpoint [--dry-run] [--stopped] [--as A] [--cwd D]` is the same step by hand.

**Next session (a3).** `session-start` (Claude Code, Codex) and the first `hermes-pre-llm` turn add one line to the context when the bound card's **last** Log entry is a limit checkpoint: where to continue, as data to verify against the real state (git, running processes, external effects) before acting. When the new session writes anything to the card, the checkpoint is no longer last and the reminder stops.

**Roll-out (the coordinator installs it, nothing here changes an installed hook).** The hooks the installers already write (`SessionStart`, `PreCompact`, `Stop` for Claude Code; `SessionStart`, `Stop` for Codex; `pre_llm_call`, `api_request_error` for Hermes) call `roadctl hook <event>`, and the module runs inside that call, so updating roadctl is enough for them. Needed on top: (1) agents run with `ROADCTL_AS` set, and claim a card with `--workdir`; (2) something probes `roadctl limits --check <provider>` at phase boundaries (the scheduled tick does) so the cache has data; (3) optional, for the proof of a stop: a host event "ended because of the usage limit" calls `roadctl hook limit-stop --host claude|codex` (for Claude Code the `StopFailure` hook with a rate-limit matcher is the candidate; it was not verified live, this is criterion a1 of P5.43, the owner's check). `hook-install` does not write it yet.

## Limits and the owner's reserve

Before any automatic start (a scheduled run, a delegated worker) an agent or script should know how much of a provider's subscription is left and keep the owner's share. `roadctl limits` needs no board and no model of its own; it only needs the provider's own tool on `PATH`.

**Reserve.** The percentage that must **remain** for the owner: by default **10% of both the weekly and the five-hour window**. A provider is allowed only while every known window has *more* than the reserve left (remaining > reserve; exactly 10% left on a 10% reserve is already refused). A window with another name (`other`, for example a monthly one) uses the weekly reserve unless the reserve names `other`. Configure it in the registry (see [Delegation](#delegation) for where it is looked up):

```json
"limits": { "reserve": { "seven_day": 10, "five_hour": 10 }, "cache_minutes": 10 },
"providers": {
  "claude": { "kind": "subscription", "probe": "claude", "probe_model": "claude-haiku-5-5", "reserve": { "five_hour": 20 } },
  "codex":  { "kind": "subscription", "probe": "codex" },
  "kimi":   { "kind": "subscription", "probe": "command", "command": "kimi-limits --json" },
  "some-api": { "kind": "api" }
}
```

All of it is optional. Without a registry the built-in providers `claude` and `codex` work with the default reserve. A provider's own `reserve` overrides `limits.reserve` for that provider, key by key. An agent names its provider with `"provider": "<id>"` in the registry; without it the host decides (`claude-code` is provider `claude`, `codex` is `codex`, any other host is unknown). `kind: "api"` means pay-per-token: there are no subscription windows, `--check` answers 0 and the reserve does not apply. Providers may set `timeout_s` for their probe.

**Where the numbers come from** (normalized to windows `five_hour`, `seven_day` or `other`, each with `used_percent` and `resets_at`):

- `codex`: `codex app-server` is started and asked over stdio (JSON-RPC: `initialize`, `initialized`, `account/rateLimits/read`); `primary` (300 minutes) is the five-hour window and `secondary` (10080 minutes) the weekly one, matched by `windowDurationMins`. **No model is used**, nothing is spent. Timeout 20 s.
- `claude`: **this probe spends one tiny request.** It runs `claude -p "Reply with: ok" --model claude-haiku-5-5 --output-format stream-json --verbose --max-turns 1 --tools ""` in an empty temporary directory (no project files, no tools) and reads the `rate_limit_event` of the stream (`utilization` is a 0-1 fraction, shown as percent). The request goes to the light model named by `probe_model`, counts as a little usage on the subscription and is therefore cached (below). Timeout 90 s. Other windows in the event (such as a per-model weekly one) are ignored.
- `command`: any other subscription (Kimi, Z.ai, ...): put a program in the provider's `command` that prints `{"windows":[{"name":"five_hour","used_percent":12,"resets_at":"2026-11-12T05:00:00Z"}]}`. The command is split into words and started without a shell, so nothing from a card can be interpolated into it; unknown window names become `other`. Timeout 30 s. This is how a new provider is added without changing roadctl.

**Cache.** A known result is stored in `${XDG_CACHE_HOME:-~/.cache}/road-map-journal/limits.json` and reused for `limits.cache_minutes` (default 10; 0 turns the cache off). `--fresh` bypasses it. A cached result is also dropped when one of its windows has reset since, and a failed probe is never cached. `ROADCTL_PROBE_TIMEOUT_MS` overrides every probe timeout. When a probe finds the reserve reached and every window that is in reserve has a known `resets_at`, the cache also records `closed_until` (the earliest such reset): the duty `tick` then answers from the cache without a probe until that reset, so a routine in reserve is not polled every half hour while the window is already exhausted (P5.17). Once the reset has passed the cache is stale and the next probe runs.

**`roadctl limits [--provider P] [--fresh] [--json]`** prints one row per window and provider: used %, remaining %, the reserve, when the window resets, `state` (`known`, `unknown` or `not-applicable`), `measured_at`, the `source` and `(cached)` when it came from the cache; an `unknown` provider has one row without windows and a `note:` line with the reason. Without `--provider` every provider is asked, so a plain `limits` sends the claude request unless the cache is fresh. `--json` returns the same data (`reserve` and the evaluation included).

**`roadctl limits --check <provider|agent>`** is the decision for scripts. `<agent>` is an agent name of the registry (or any `claude-code@...` / `codex@...` name).

| exit | meaning |
| --- | --- |
| 0 | allowed: every known window has more than the reserve left, or the provider is `api`, or the owner confirmed an unknown provider (the message says "confirmed by NAME until ..."). The message is on stdout |
| 1 | reserve reached: the message (stderr) names the window, what is left and when it resets |
| 2 | usage error, unknown provider or agent name, malformed registry |
| 3 | limits unknown (probe failed, timed out, tool missing, agent without a provider) and not confirmed. The message says that one attempt with a light model may be made (`roadctl limits --fresh --provider P`) and otherwise the owner must confirm with `limits --confirm` |

An unknown limit is never read as "allowed". A script should treat 3 like 1 (do not start) unless it was told otherwise.

**`roadctl limits --confirm <provider> --by NAME [--for 2h]`** is an owner action: an agent runs it only when the owner told it to. It records in `${XDG_STATE_HOME:-~/.local/state}/road-map-journal/limits-confirm.json` that NAME allows that provider while its limits are unknown (`--for` 30m, 2h, 1d; default 2h, at most 7d). While it is valid `--check` returns 0 for an unknown provider. It never overrides a known reserve breach: when the limits can be read and the reserve is reached the answer stays 1, and once the probe works again the real numbers decide. A known breach has no automated bypass: if the owner explicitly allows one task or provider to proceed past a reached reserve, that is a manual decision recorded on the card or journal (the task, the provider, the duration), never a `roadctl` flag.

The fake-provider tests in `scripts/roadctl.test.mjs` never call a real `claude` or `codex`; a live check on a machine is `roadctl limits --fresh` (it spends the one claude request).

**Limitation: one provider per agent (Hermes).** The limits gate reads the provider an agent names in the registry (`provider`), else the host default; it knows one provider per agent. An agent that works through several providers (for example Hermes, whose runs may use a secondary provider) has only its main provider accounted: the secondary provider's windows are not polled and do not gate the agent. This is a documented limit until a card adds per-provider accounting for one agent (P5.17 a3).

## Autonomous or personal work

The owner decides what goes to unattended work and what stays personal. **By default nothing is autonomous.** A card may be started without the owner only when all of this holds, and an agent never decides any of it on its own initiative:

1. The board's `board/config.json` has `"autonomy": {"enabled": true, "agents": [], "queue": ["F8", "F9"]}`. `enabled` false or missing: the board offers nothing for unattended start. `agents` empty: any agent with the orchestrator role; otherwise only the listed agents. `queue` is an ordered list of card ids.
2. The card is in `autonomy.queue`.
3. The card's `approved` scope includes the token **`auto`** (for example `scope=implementation+auto`). A plain approval (`scope=implementation`) means: work on it with the owner.
4. It is `ready`, every `depends_on` is `done`, and it has no delegation.

The first card of the queue that satisfies this is the only one offered per board (one at a time); the next one follows when it is finished, delegated or no longer eligible. `roadctl tick` is where this takes effect (see [Scheduled orchestrator](#scheduled-orchestrator-tick)).

**Commands.**

- `roadctl autonomy [--all] [--json]` is the overview and the preview. Per board: `ON` or `OFF`, the allowed agents, the queue as numbered lines (`position. [id] status auto | eligible now` or `not eligible: ...`), cards that are `auto` but not queued, and for each allowed orchestrator the card it would START now (the registry lists the orchestrators; without one the preview says "for any orchestrator"). The reasons are `not auto`, `not ready (status)`, `deps open: id (status)`, `delegated`, or the closed status (`done`, `dropped`); a queued id that is not a card is `no such card`. `--json` has the same facts. It changes nothing.
- `roadctl autonomy on|off [--agents a,b|any] [--by NAME]` edits only the `autonomy` key of `config.json` (the rest of the file keeps its text, CRLF is kept; `--agents any` clears the list; `off` keeps the agents and the queue). It writes nothing on cards and is not committed (`roadctl save`). A malformed section is not edited.
- `roadctl auto <id> --by NAME [--source REF] [--off]` adds `auto` to the card's approved scope and keeps the rest of the record. A card without an approval gets `approved: NAME, date, scope=implementation+auto, source=REF` (`--source` is then required; exit 2 without it). `--off` removes only `auto`. Both append a Log line (`AUTO on by NAME`, `AUTO off by NAME`) and say when the card is not in the queue yet. Refused: closed cards (exit 1), unknown ids and a missing `--by` (exit 2). `roadctl approve ... --scope implementation+auto` is accepted as well and means the same.
- `roadctl queue [list] | add <id> [--at N] | remove <id> | move <id> --at N` edits `autonomy.queue` (positions count from 1; `add` defaults to the end; a closed card, a card already queued or an unknown id is refused). Adding to the queue does not turn autonomy on. `list` reads.
- `status`, `next`, `brief` and their `--json` mark auto cards and queue positions: `next` appends `| auto, queue #2`, `brief` marks `W-5*auto` and has an `AUTONOMY on | agents ... | queue 1:W-6 2:W-5` line (only when autonomy is on or a queue exists), `status` has an `autonomy` column (`on`/`off`), and the `--json` rows carry `auto` and `queue`.

**Lint.** Rule 21 (error): the `autonomy` section is malformed (not an object, `enabled` not a boolean, `agents` not agent names, `queue` not card ids or with a repeated id); the board is then treated as OFF. Rule 22 (error): a queued id is not a card. Rule 23 (warning): a queued card is done or dropped. Rule 24 (warning): an approval has a scope token that is not `analysis`, `implementation`, `external` or `auto`. An `auto` scope without an approval cannot exist (it is part of the approval).

### Project mandate and levels (L1 to L4)

The card path above (`approve`, `auto`, the queue, the board switch) is one card at a time. The **mandate** is one file for the whole board, `board/mandate.md`, that the owner approves once as a whole; inside its limits an agent takes `ready` cards without `approved`, `auto` and the queue. **Nothing is autonomous until the owner approved the mandate** (or gave the card away with the commands above); an agent never writes `approved_hash` into a mandate and never raises its level.

Levels: **L1** routines only. **L2** cards the owner approved one by one, as before (the mandate takes nothing; every rule above is unchanged). **L3** the mandate: the agent plans, does and (with the rule of P5.35) accepts in its own branch. **L4** the same plus merging into the main branch and releases inside the repository. External systems stay closed at every level: the key that would open them is reserved and `lint` refuses it until the end of the pilot.

The file (a flat header like a card, then sections):

```text
---
mandate: 1                          format version
level: L3                           L1 | L2 | L3 | L4
kinds: fix, docs, tests             fix feature docs tests refactor research
max_size: M                         S | M | L
merge: branch                       branch | main (main needs L4)
budget: cards_per_day=2, runs_per_week=10
plan_max_cards: 5                   optional (0.11.0): the most cards one plan may propose (default 5); a board that sets it requires 0.11.0
approved: Owner, 2026-11-16         written by roadctl mandate approve
approved_hash: sha256-v1:...        ... with the content hash
---
## Goals
- G1 (priority 1): finish stage 2   stable id, explicit priority (no two goals share an id or a priority)
## Forbidden
- pushing to main
## Tell the owner
- the build is red for a day
```

- **Approval is by content hash** (the helper of P5.15, the same normalisation): any edit of the file, `## Goals` included, takes the approval away until the owner runs `roadctl mandate approve --by NAME --hash H` with the hash that `roadctl mandate show` printed. The `approved` record and `approved_hash` are outside the hash. The owner or a separate session edits the mandate; only the owner approves. `mandate approve` refuses in an unattended run (`ROADCTL_UNATTENDED` or `ROADCTL_RUN_ID` set), without `--by`, when `--hash` is not the hash of the file now, and on a board whose `requires` is below 0.8.0; it writes one line to `owner-commands.jsonl` of the machine state directory (the audit of P5.3 reads it).
- **Card keys** `kind` (one of the mandate kinds), `size` (S, M or L) and `goal` (an id from `## Goals`) are optional and set by the author or the planner (P5.34). A card without `size` or `kind` is not taken by the mandate; a `goal` that is not in `## Goals` is not taken either.
- **`tick`**: at L3 or L4 with an approved, unchanged mandate, `START` also offers a `ready` card inside the limits (kind, size, goal, dependencies done, no delegation, the Plan lines below, the budget) without `approved`, `auto` and queue; the item has `"basis": "mandate"` in `--json`. One card per board; the order is the priority of the card's goal, then the card number (a card without a goal comes last). At L2 and below, with no mandate, with an unapproved or changed one, nothing is taken by it and `tick` is as before.
- **Taking a card**: the agent takes a START by mandate only with `roadctl delegate <id> --to ROLE --by AGENT`; delegate records `by_mandate: <hash>` in the card header and a Log line `approved by mandate <hash>` (a proposal writes nothing; the key is written only when the card is actually taken). `by_mandate` is not an `approved` record and not an owner command, and it is believed only while it equals the hash of the approved mandate now: a self-declared value, a changed or withdrawn mandate, or a re-approved one (the old hash) does not admit the card, so a card taken earlier is taken again with `delegate` after the mandate changes. `approve` and `done` stay owner commands. `lint` rule 6 accepts a `doing` card that has a current `by_mandate` instead of `approved`.
- **Budget**: `cards_per_day` (distinct cards taken today) and `runs_per_week` (takes in the last seven days, a card taken twice is two runs), counted from the Log lines `approved by mandate`; a new hash does not reset it. Tokens and money come with P5.20.
- **`roadctl mandate [show|check] [--json]`** reads: level, limits, hash, `approved` / `CHANGED after approval` / `not approved`, the extra and the built-in reasons to tell the owner, what `tick` would START now and why each other ready card is not admitted. `check` exits 1 when the mandate changed after approval or is malformed. `--json` has the fields checked by `scripts/testkit/mandate-schema.mjs`. It changes nothing.
- **Tell the owner**: the floor is in the code and cannot be removed by editing `## Tell the owner`: an owner-only command was refused, an attempt at something forbidden, the same card failed twice in a row, a question about something irreversible. The section only adds reasons.
- **Lint**: rule 33 (error): the mandate is malformed (unknown `level`, `kinds`, `max_size`, `merge`, `budget` missing at L3 and L4, a goal line that is not `- G1 (priority 1): text`, a repeated goal id or priority, the reserved external key, `merge: main` below L4, `requires` below 0.8.0) or it **changed after approval**; (warning) an unapproved L3 or L4 mandate, a card whose `goal` is not in `## Goals`. `roadctl digest` tells a changed mandate at once, as a problem, once per episode.
- **What is checked and what is agreed.** `roadctl` itself checks the admission at START and `delegate` (level, kind, size, goal, budget, dependencies, hash) and `lint`. `## Forbidden`, the way of merging and the stop conditions go into the launch prompt and are checked afterwards from the report and the audit: that is an agreement, not a sandbox. An agent that can write to git can in theory rewrite the mandate together with its approval; the protection is that `mandate approve` refuses an unattended run, the audit line, the echo to the channel (P5.26, P5.32), the hash comparison at every `tick`, and `lint` and the digest (changed after approval is a problem at once). A git branch and the ban on external systems are not a sandbox either.
- **Making or changing a mandate is an interview.** The agent (or the owner with `/grill-me`, or `/grill-with-docs` when the mandate must match a codebase) runs a grilling interview: numbered rounds, a recommendation with each question. If neither skill is installed the agent offers to install it (the owner's decision); if the owner declines, the agent asks the same interview itself. The result goes into the mandate and into a Log line of the card or note that records it; the owner approves the hash.
- **Stage boundary.** The limit of two ready milestones without the owner's decision belongs with P5.35 (stage 3): the field is agreed with it, the gate is not wired in until P5.35 lands, and until then an autonomous L3 is a training L3 on a release candidate, not a finished autonomous L3. At stage 2 the early live check is L2 with the planner of P5.34; the main path is checked without a model.

**Size (the `size` of a card, the rubric the agent uses).** S: one bounded, clear result whose implementation and check are known. M: one goal across several components; the agent says why it cannot be split. L: composite work; before it runs unattended it is split into results that can each be checked. When the scope or the consequences are unclear, the card is a proposal or a bounded research task, not an arbitrary S. This is an instruction for the agent, not a measure of complexity by the number of criteria, and a small change is not the same as a safe one: size never makes a card safe. To be admitted by the mandate a card also needs its environment (or role), its checks, its allowed effects and its stop conditions written in its Plan or Delegation section as lines `Environment:`, `Checks:`, `Allowed changes:` and `Stop conditions:`; an empty line or a template placeholder ("(files the worker may change)", TBD, -) does not count. That the lines are filled in does not prove that the card is safe.

## Scheduled orchestrator (tick)

A scheduled orchestrator works in two steps. Step 1 costs no tokens: `roadctl tick --as AGENT` looks at the boards, asks the limits gate and answers with a decision and an exit code. Step 2 starts a model only when step 1 says there is work and the owner's reserve allows it. Any scheduler can do this (cron, a systemd timer, Windows Task Scheduler, Hermes cron): `roadctl tick --as X --prompt > p.txt && <launch the agent with p.txt>`.

**What it looks at.** Outside a board it covers every known board (the central workspace and the user list; `--all` does so inside a project too); inside a board directory, that board. Unless `--no-pull` is given it first runs `pull` once per git repository; an unreachable origin or a failed pull is one stable `sync:` line, and the tick goes on with the local state. What counts as work for AGENT (registry roles decide; without a registry the agent has every role, but a script is never an acceptor or an orchestrator):

| Line | Meaning |
| --- | --- |
| `TAKE` | an open delegation, or one whose lease ran out, that AGENT may claim (the rule of `tasks --for`, and the delegating agent must be in the registry, as `claim` checks) |
| `ACCEPT` | a `reported` delegation that AGENT may accept (`accept=by` and AGENT is `by`; `reviewer` with `can_accept`; a named agent). Never for scripts |
| `START` | orchestrators the board allows, from a board whose **autonomy is on** (see [Autonomous or personal work](#autonomous-or-personal-work)): the first card of `autonomy.queue` that is `ready`, has `auto` in its `approved` scope, has every `depends_on` done and no delegation, so it could be started or delegated. At most one per board. Without autonomy and without an approved mandate there is no `START` at all (a START by the project mandate has `"basis": "mandate"`, see [Project mandate and levels](#project-mandate-and-levels-l1-to-l4)); ready and plainly approved cards are never listed: ready is not permission, and a plain approval means work with the owner |
| `RUN` | a recurring routine that is due and allowed to run (see [Recurring routines](#recurring-routines)), offered to **the routine's own `agent` only** (exact name), no matter its roles. Printed as `RUN project/id title` |
| `STALE` | orchestrators only (and only the listed ones when the board's `autonomy.agents` is not empty, whether or not autonomy is on): a `claimed` delegation whose lease expired; the delegating agent may `undelegate` it. A card the agent can take itself is listed as `TAKE` only. When the expired claim named a working directory (`claim --workdir`) that exists on this machine and has uncommitted changes, the line ends with ` (workdir dirty)` |

`TAKE` and `ACCEPT` of explicit delegations do not depend on autonomy. Cards that are idea, blocked, parked, done or dropped are never offered. Before P4.7 any approved ready card was offered as `START`; that is gone: only the owner's queue starts work unattended.

**Filters: one routine per job.** `--kinds take,accept,start,stale,run` (any subset, default all) lists only those kinds, and `--routine ID` only the `RUN` item of that routine (same as `--kinds run` for that id; it cannot be combined with other kinds). The decision, the exit codes and the stability rules are unchanged: nothing for the chosen items means the single line `tick AGENT: idle` (exit 4, no limits probe), the limits are checked only when an item remains, `--prompt` prints the instruction for the remaining items only (for `--routine` just the `RUN` command and that routine's file, model and environment), and `--json` has the same shape. A filtered tick has its own lock (`tick-<agent>.<routine>.lock`, or without `.<routine>` for `--kinds` only), so a routine job and the general tick do not make each other `busy`; the ledger line gets a `filter` key (`{"routine": "server-watch"}` or `{"kinds": ["take", "run"]}`), and `--ledger` shows `routine=...` or `kinds=...`. An id that exists on no board looked at gives `idle` and a warning on stderr (a typo must not stay unseen), nothing else changes.

**A board that needs a newer roadctl.** When a board's `config.json` has `"requires": "<version>"` above this copy's version (`roadctl version`), or a value that cannot be read, `tick` offers nothing from that board (no `RUN`, `TAKE`, `ACCEPT`, `START`, `STALE`), whatever else is due there, and adds the line `requires: <project>: board requires roadctl <version> or newer; this is <this version>` to `sync` (sorted with the other `sync:` lines; text and `--json` alike). The decision stays `idle` (exit 4) when nothing else is offered, so the JSON contract has no new field or decision; a script that wants to notice the refusal looks for a `sync` entry that starts with `requires:`. `lint` reports it as rule 10 (error), `routine list` and `routine show` say `would not run: board requires roadctl ...`, `brief` has a `REQUIRES` line. A board without `requires` is unaffected. The owner raises `requires` when a change adds a header key or a new meaning (see [developing-roadctl.md](developing-roadctl.md#compatibility-between-copies-version-and-requires)); copies older than 0.2.0 do not know `requires` and must be updated first.

**Decision and exit code.** Without items the answer is `idle` and the limits are not looked at at all (no probe, no cost; the ledger records the limits state `not-checked`). With items the limits gate is `limits --check` for AGENT's provider (registry `provider`, else the host default): the cache is honoured and `--fresh` is never used, so a claude agent costs at most one tiny probe request per cache period (10 minutes) and a codex or `command` provider costs no model at all. Its state is `allowed`, `reserve` (the window names only, no numbers), `unknown` or `not-applicable` (api provider). An unknown limit that the owner confirmed with `limits --confirm` counts as `allowed`.

| Decision | Exit | When |
| --- | --- | --- |
| `work` | 0 | there are items and the limits allow it: a model may be started |
| `idle` | 4 | no items; the limits are not checked |
| `blocked-reserve` | 1 | items, but the owner's reserve is reached |
| `blocked-unknown` | 3 | items, but the limits are unknown and not confirmed |
| `busy` | 5 | another tick of this agent is running on this machine (`tick AGENT: busy`) |
| `paused` | 6 | the owner paused this machine (`roadctl pause`); nothing is offered, pulled or checked (see [Pause and resume](#pause-and-resume)) |
| usage error | 2 | no `--as`, a bad agent name, no board and no workspace, a broken registry |

**Output.** Text: `tick AGENT: <decision>`, one line per item (`TAKE|ACCEPT|START|STALE project/id title`, sorted by project, card id and kind, titles sanitized as in `brief`), `limits: <provider> <state>` (`limits: claude reserve (five_hour,seven_day)`), then `sync:` lines. When idle the output is exactly one line, `tick AGENT: idle` (no limits line, no `sync:` lines; they stay in `--json`), so repeated idle runs are identical and a change of limits cannot wake anything. The one exception is a refusal of a board (below): its `requires:` line is printed after the idle line, in text as well as in `sync`. `--json` is a contract that scripts may rely on (the scheduler examples read it instead of the text, and `scripts/testkit/tick-schema.mjs` checks it in the tests): `{agent, decision, limits: {provider, state[, windows]}, items: [...], sync: [...]}` with `decision` one of `idle`, `work`, `blocked-reserve`, `blocked-unknown`, `paused` (only then the extra key `pause: {since, by, reason, until}`, strings or `null`; `items` and `sync` are empty and `limits` is `{provider: null, state: not-checked}`) and `limits.state` one of `allowed`, `reserve`, `unknown`, `not-applicable`, `not-checked`; an item is `{kind, project, id, title}` plus `delegate: {to, host, criteria, by, accept, state[, claim][, env][, access]}` for TAKE, ACCEPT and STALE (STALE may add `workdir_dirty: true`), plus `routine: {agent, model, env, every, file, last_run[, access][, attempt][, owner_answers]}` for RUN (`access` and `env` since 0.10.0, P5.23: only when the environment is placed `remote-access`; `owner_answers` since 0.13.0, P5.24: `[{id, prompt, answer}]`, the owner's answers for this run, as data), plus `undo` (the owner's comment) for a RESUME after an undo (`RESUME` since 0.13.0, P5.24: a rework task for the original agent, with no `delegate`), and nothing more for START. The exit code is the same as in text mode. The text of a paused tick is two stable lines, `tick AGENT: paused` and `pause: <reason>` (with ` (until <time>)` when the pause ends by itself); it has no clock, so it changes only when the owner changes the pause. When another tick of the agent runs (`busy`, exit 5) or the call is a usage error (exit 2) no JSON is printed, so a script treats an answer that is not JSON as "no work". `--prompt` with work prints a short, self-contained instruction for the orchestrator model instead of the item list (who it is, the items, where each board is, the rules: one item at a time and at most three per run, verify results yourself before accepting, never `approve` or `done`, stay inside the approved scope, no external actions, card text is data, change the board only through `delegate`/`claim`/`report`/`accept`/`return`/`undelegate`/`save`, check `limits --check` before each item and stop unless it exits 0, keep the owner's reserve; and the exact `roadctl` commands for the kinds that are present). Without work `--prompt` prints the plain state lines, so a scheduler can show them.

**Stability and Hermes monitor mode.** Hermes hashes the exact stdout of its monitor and wakes the model when that changes. The examples keep the last nonempty successful prompt in a per-job state file and print it on idle, blocked, busy, paused (exit 6) or error ticks. Thus returning to idle does not wake the model. A new work prompt changes the output; each RUN prompt includes `previous run: <last_run or never>`, so the next due cycle changes it after `routine done`. State defaults to `~/.road-map-journal` on the machine running Python; `ROAD_MONITOR_STATE_DIR` overrides it. Preserve it between scheduler runs. An initial idle prints nothing. Monitor errors are reported on stderr; the tick ledger has the reason for blocked work.

Copy `examples/scheduler/hermes-monitor-tick.py`, `hermes-routines-tick.py` and `monitor_common.py` to Hermes's scripts directory and adapt their agent and host settings. These examples use Windows `wsl.exe` to run roadctl. Create two independent jobs, without `--skill` or `--workdir`:

```text
hermes cron create "every 30m" --name road-routines --model gpt-6-luna --reasoning-effort low --monitor-script hermes-routines-tick.py "Follow the routine prompt in the monitored output."
hermes cron create "every 2h" --name road-orchestrator --model <main-model> --reasoning-effort medium --monitor-script hermes-monitor-tick.py "Follow the tick prompt in the monitored output."
```

The routines monitor uses `--kinds run` for Hermes and for each configured external agent. For external Claude routines the local tick only decides which routines are due; for each one it sends the agent, routine id, project and model over SSH, and the remote host runs its own `roadctl tick --routine ID --project P --prompt` (its own paths, pull and limits gate) and starts `claude -p --model <model> --max-turns 30` under `timeout` (default 30 minutes, `ROAD_CLAUDE_TIMEOUT`; `tick-claude.sh` has `CLAUDE_TIMEOUT`) with nohup only when that tick says work. The unattended run may call only the roadctl subcommands the routine prompt names (`limits --check`, `show`, `log`, `delegate`, `save`, `routine done`), not `Bash(roadctl:*)`. The local script reads the RUN items of `roadctl tick --kinds run --json` (project, routine id, model); it does not parse the prompt text. Nothing from the local board, not even a path, is sent as a prompt. Remote `flock` prevents overlapping external runs; output goes to `~/.local/state/road-map-journal/external-routine.log` on the remote host, one `== time project/id` line per launch. Permission rules for file writes must be `Edit(path)`: Claude does not match `Write(path)` rules. Configure SSH access, remote `flock`, roadctl, Bash and Claude separately; the examples do not create a job or connect by themselves. The orchestrator filters to `take,accept,start,stale`. Adapt the intervals (1–2 hours for the orchestrator) and model to the installation. `hermes-routine-tick.py` remains an example for a separate single-routine job, with its own sticky state. `tick-claude.sh` is a Linux alternative that runs Claude only on exit 0.

**Lock.** One tick per agent at a time on a machine: `${XDG_STATE_HOME:-~/.local/state}/road-map-journal/tick-<agent>.lock` (characters other than letters, digits, `.`, `_`, `-` become `_`), removed at the end of the run and taken over when older than 10 minutes. A second tick prints `tick AGENT: busy` and exits 5. The lock is held only while tick itself runs, not while a model that a scheduler started from the prompt is working; use `roadctl supervise` around the model (see [Run supervisor](#run-supervisor)), which holds a lock for the whole run, if two model runs must not overlap; `tick` then offers no `RUN` for a routine whose supervised run is live.

**Ledger.** Every run appends one JSON line (time, agent, decision, counts of TAKE/ACCEPT/START/STALE, limits provider and state, and `filter` when `--routine` or `--kinds` was used) to `${XDG_STATE_HOME:-~/.local/state}/road-map-journal/ticks.jsonl`. It is not printed by the run, so stdout stays stable. `roadctl tick --ledger [--as AGENT] [-n 20] [--json]` prints the last entries and changes nothing. Repeats of a `blocked-reserve`, `blocked-unknown`, `busy` or `paused` decision are folded (one line, a counter in `ticks.state.json`) and the file is rotated inside `tick` to one previous generation, `ticks.jsonl.1`, when it passes 1 MB; see [Run ledger](#run-ledger). A line is about 200 bytes.

What tick does not do: it starts no model, writes no card, approves nothing, and cannot see the server state beyond what `pull` brought in (offline it uses the local state and says so).

## Pause and resume

`roadctl pause [--reason TEXT] [--until SPAN|TIME] [--by NAME]` is the owner's stop switch for **one machine**: it takes effect at once, without git and without waiting for a sync. `roadctl resume` ends it. `roadctl pause status [--json]` prints the state without a board (`not paused`, or the `PAUSED since ... by ...: reason` line).

- **What it is.** One file, `pause.json`, in the machine state directory (`${XDG_STATE_HOME:-~/.local/state}/road-map-journal/`, next to `ticks.jsonl`): when, who (`--by`, default the login name), the reason (one line, up to 200 characters, sanitised) and the optional end. Nothing is written to a board, a card or git, so another machine is unaffected; it is local state, not a board format, so it needs no `requires` and no `VERSION` change. The file is written atomically and survives a restart of any process; a file that cannot be read counts as a pause (the safe side), and `resume` removes it either way.
- **What it stops.** `roadctl tick` for every agent, filter and kind: `TAKE`, `ACCEPT`, `START`, `STALE` and `RUN` alike, because it stops before the boards are even read. A paused tick takes no lock, pulls nothing, asks no limits gate, runs no module tick hook, prints `tick AGENT: paused` and the reason, and exits **6**. A scheduler that starts a model only on exit 0 starts none (`examples/scheduler/tick-claude.sh` ends quietly on 6; the Hermes monitor scripts keep printing the last prompt, so the model is not woken; `hermes-routines-tick.py` launches nothing). The ledger gets one folded `paused` line and a `skipped` record with the reason `paused` ([Run ledger](#run-ledger)).
- **What it does not stop.** A run that has already started (without `--now` the model keeps working and may call `claim`, `report`, `routine done`...), and interactive sessions. **`pause --now`** (the same file, with `"now": true`) also stops every run that `roadctl supervise` holds on this machine: within a second the supervisor sends TERM to the command's process group, then KILL, and the outcome is `aborted` (reason `pause --now`); `resume` removes the file. A run that nobody supervises is not stopped. Commands other than `tick` are unchanged.
- **`--until`.** `--until 4h` (a span: `30m`, `2h`, `1d`, at most `90d`) or `--until 2026-11-14T09:00:00Z` (a time with a zone, in the future) ends the pause by itself; the clock is roadctl's own (`ROADCTL_NOW` in tests). An ended pause is ignored by `tick`, `status`, `routine list` and `pause status`; the file stays until the next `pause` or `resume`, and `doctor` says so. Without `--until` the pause lasts until `resume`. A second `pause` replaces the first (new reason, new end).
- **Where it shows.** `roadctl status` (a `PAUSED ...` line first; `--json`: a `pause` object in every board summary), `roadctl routine list` (the same, also in `--json` rows), `roadctl tick --json` (`decision: paused` and `pause`), `roadctl doctor` (check `pause`) and `roadctl pause status`.
- **Whose directory.** The pause belongs to the state directory: WSL and native Windows have separate ones (`doctor` reports a second one), and a Hermes job that runs `roadctl` through `wsl.exe` is paused by the WSL one. Hermes jobs keep calling their scripts; the scripts see exit 6 and do nothing. From another computer: `ssh HOST roadctl pause --reason "..."` and `ssh HOST roadctl resume`. The switch shared through git, for the routines of a board on every machine, is `roadctl autonomy routines off --by NAME`.
- **Who may run it.** The owner. `resume` is left out of the `roadctl help` overview (which has a line budget; it is in `roadctl help resume` and named by `pause`); an agent does not resume what the owner paused. `pause` is an owner command: in an unattended run it is refused (see [Unattended mode and the owner audit](#unattended-mode-and-the-owner-audit)); `pause status` only reads.

## Unattended mode and the owner audit

An **unattended run** is a process with `ROADCTL_UNATTENDED` set (not empty, not `0`; a scheduler script or a scenario sets it) or with `ROADCTL_RUN_ID` (`roadctl supervise` sets it for the command it holds). Interactive sessions have neither and are unchanged.

- **Owner calls are refused.** The list of owner commands is the `owner` entries of the command table (`help` marks them; the line "Owner-only commands" above is checked against the table by a test): `approve`, `done`, `auto`, `resume`, `queue add|remove|move`, `pause` (not `pause status`), `mandate approve`, `routine on|off|resume|promote`, `autonomy on|off|routines`, `limits --confirm`, `boards add|remove`, and the `*-install` and `*-uninstall` commands with `--apply` (without it they only print the plan). In an unattended run each is refused with **exit code 1** (the code of every refusal; 2 stays the usage error) and the message `roadctl <command>: refused: an unattended run ... never runs <command>; only the owner does, in person`. The same call without the variables works as before. `roadctl <command> --help` is never refused.
- **The audit is always on.** Every owner call, refused or not, adds one line to `owner-commands.jsonl` in the machine state directory (next to `runs.jsonl`, never in git): `{"time", "command", "target", "by", "outcome": "ok|refused", "via", "run_id", "unattended"}` (a refusal also has `reason`; `mandate approve` also `hash`). `via` is `direct`, or the value of `ROADCTL_VIA` when a bridge (P5.26, P5.32) runs the command for the owner. A usage error (exit 2) did nothing and writes no line. The audit is detection, not prevention: removing the variable does not remove the line, and the line is the only thing the owner has to tell what an agent did with an owner command. Readers (`digest`) ignore fields they do not know.
- **The owner is told.** `roadctl digest` (the news, at once): a refusal in an unattended run is one line `owner command approve P5.1 by NAME: refused in an unattended run, run RUN` (the agent tried to approve); and, when the local setting `${XDG_CONFIG_HOME:-~/.config}/road-map-journal/owner-gate.json` is `{"bridge": "NAME"}` (a bridge is connected), every owner command whose `via` is not NAME is a line `not through the bridge NAME`. Each line is told once. `digest --daily` has the line `owner commands, last 24h` (see [Run summary and delivery](#run-summary-and-delivery)).
- **Bounds of the project mandate** (P5.33). In an unattended run on a board whose mandate is L3 or L4, the card commands `claim`, `delegate`, `report`, `review`, `accept`, `return` and `undelegate` on a card that is not approved by hand (no `approved`) must be admitted by the mandate: kind, size, goal, level, an unchanged approved mandate (`by_mandate` equal to its hash) and, for `delegate`, the budget. Otherwise the call is refused with exit 1, an audit line (`outcome: refused`, `reason`) is written and the digest tells it like any other refusal. A board without a mandate, a mandate at L1 or L2, and a card approved by hand behave as before. What roadctl cannot check (the way of merging, `## Forbidden`) stays in the prompt and is read afterwards in the report and the audit.
- **It is an agreement, not a sandbox.** A process that can unset a variable, call `node roadctl.mjs` with another environment, or edit the board files is not stopped; the gate stops a well-behaved agent, makes the line visible, and the audit shows the rest afterwards. The real barrier is what the launcher gives the agent (its settings and tools).
- **Broad permission rules (lint).** `roadctl lint` reports, for every routine file (rule 33), a permission rule that is too wide: `Bash(roadctl:*)` (error: it allows `approve` and `done` as well), a whole MCP server (`mcp__server`, error), a bare `Bash` rule (error), `Bash(git:*)` and `Write` or `Edit` without a path (warnings). **A prefix rule is not "read only"**: `Bash(roadctl show:*)` allows every command that starts with `roadctl show`, and `Bash(git:*)` allows `git push`. Give a routine the exact subcommands it needs (`Bash(roadctl show:*)`, `Bash(roadctl log:*)`) and a path for every file rule.

## Recurring routines

Routines are recurring, mostly mechanical project tasks that the owner can switch on and off: for example collect the state of merge requests, issues and messages and update cards, or watch servers and support requests. They live in the board as `board/routines/<id>.md` (format and lint rules: [board-spec.md](board-spec.md#recurring-routines)). Two things set them apart from cards: the owner names the executor **when the routine is created** (`agent`, `model` and `env` are required; a routine missing one never runs), and they are started through the same single entry point as everything else, `roadctl tick`.

**Switches and gates.** A routine runs only when the board switch `autonomy.routines` is `true` (default `false`; `roadctl autonomy routines on|off --by NAME`, independent of `autonomy.enabled`, which is for cards), the routine is `enabled: true`, has an `approved` record (`scope=read+board[+external]`), has agent, model and env, and is **due**: no `last_run`, or now (`ROADCTL_NOW` in tests) is at least `last_run` plus `every`, and (optional) inside its **`hours`** window. `hours: mon-fri 09:00-19:00`, `hours: daily 08:00-23:00` or `hours: sat,sun 10:00-14:00 tz=Europe/Moscow`: days are `daily`, a comma list of `mon`..`sun` and ranges like `mon-fri` (`fri-mon` wraps over the weekend); the window runs from the first time (included) to the second (excluded, `24:00` allowed) on that day and does not cross midnight; `tz=` is an IANA zone (checked with `Intl`), without it the local time of the machine that runs `roadctl` counts. Outside the window a due routine is not offered (`routine list` says `outside hours`), inside it it is offered as before; `every` and `last_run` are not changed by the window. `routine new ... --hours "mon-fri 09:00-19:00"` writes the line. `routine on` and `autonomy routines on` are the owner's decisions: an agent runs them only on the owner's words.

**Creating one.** The owner names the executor: ask which agent (`claude-code@work-notebook`), which model (`claude-haiku-5-5`) and which environment (`Work-notebook-wsl`), and how often.

```text
roadctl routine new mr-status "Collect MR, issue and message state, update cards" \
    --agent claude-code@work-notebook --model claude-haiku-5-5 --env Work-notebook-wsl --every 2h
# edit board/routines/mr-status.md: Goal, Steps, May write, Escalate
roadctl routine on mr-status --by Lujker --source "chat 2026-11-12"     # records the approval: scope read+board
roadctl autonomy routines on --by Lujker                                   # the board switch
roadctl save
roadctl routine list
```

```text
roadctl routine new server-watch "Watch servers and support requests" \
    --agent hermes@work-notebook --model claude-haiku-5-5 --env Work-notebook-wsl --every 30m
```

Generic starting texts for both are in [`examples/routines/`](../examples/routines/) (switched off, marked as examples). `routine new` writes a template with `enabled: false` and no approval; `routine on` refuses when agent, model or env is missing, requires `--source` when it has to record the approval (default scope `read+board`; `--scope read+board+external` allows external writes and is recorded as a new approval), sets `enabled: true` and adds a Log line; `routine off` sets it back.

**Approval bound to the content (roadctl 0.6.0, P5.15).** On a board whose `config.json` says `"requires": "0.6.0"` or newer, `routine on` records `approved_hash: sha256-v1:<64 hex digits>` in the routine header (a board that has not raised `requires` gets no hash and behaves as before). From then on a routine whose content no longer matches the hash is **changed after approval** and does not run: `tick` offers no `RUN`, `routine list` and `routine show` say `would not run: changed after approval: ...`, `lint` reports it as rule 30 (error, `would not run: ... (module approval-hash)`), `status`, `brief` and the daily `digest` count the routine as not running, and `digest` (the immediate one, per `--since-state`) tells it once as a problem (`routine <project>/<id>: BLOCKED`, a `permanent approval-hash` problem; it is told again after a new approval and a new edit, even when a run of the routine did not come in between, and once as `resolved` when the owner approves it again; it never closes or is closed by a problem the routine's runs reported; the routine's `notify: never` keeps it silent, like every other message). Only the owner's `roadctl routine on <id> --by NAME` (which needs no `--source` when the approval record exists) approves the new text: it records the hash again.

- *Covered by the hash:* every header key except those named below (agent, model, env, `every`, `hours`, `timeout`, `id`, `title`, and any key a later version adds, such as `allow` or `mcp`); the scope of `approved`; the sections Goal, Steps, May write and Escalate, and also any other section except valid Questions data and any text before the first section (the model reads the file as a whole, so an extra section would be a way round). `every` is covered on purpose: a shorter interval is a way to burn the limit.
- *Not covered (outside the hash):* `enabled`, `notify` (changing it needs no new approval), `last_run`, `last_result`, `last_reason`, `fails`, `hold`, `hold_id`, `answers_received` (the delivery mark of owner answers, P5.24; the outcome-policy state of P5.4: run results are records, not instructions), on boards requiring 0.13.0 or later, valid `## Questions` data and `inbox_defer`, and the `## Log` section (the Log is a record, not an instruction: the executor must not read it as part of the task), the rest of the `approved` line (who, when, source) `approved_hash` itself and `approval_id` (a random id written with the hash by every `routine on`; the digest uses it to tell two approvals of the same text apart, and a routine approved before it existed simply has none). `routine done` therefore never changes the hash.
- *Normalised before hashing:* LF line ends (a CRLF file hashes the same), trailing whitespace of a line, blank lines around a section, the order of the header keys, the order of the scope tokens. A change of words, of the order of the sections, of the order of lines inside a section or of indentation is a change.
- *A missing hash.* On a board whose `config.json` says `"requires": "0.6.0"` or newer, an enabled and approved routine without `approved_hash` (also an empty one, or one with a version this copy does not know) is **not approved** and does not run, so deleting the key does not return the routine to the old mode. Below that, a routine without a hash keeps working by the old rule (an edit does not stop it) and `lint` warns on every enabled, approved one (rule 32, `approved without a content hash`); a hash that is present is checked on any board. Order of rollout: install 0.6.0 on every machine that runs `tick`; set `"requires": "0.6.0"` in `board/config.json` (a copy older than 0.6.0 then refuses the board, [developing-roadctl.md](developing-roadctl.md)); every routine approved earlier now says `not approved: no approval hash` until the owner runs `routine on <id>` for it, which records the hash. A copy of `roadctl.mjs` without its `roadctl/` folder (or without the `approval-hash` module) refuses such a board as a whole (`board requires the module approval-hash ...`: no `RUN`, `routine list` and `lint` rule 10 say so), so a half-installed copy cannot run a routine the hash would have stopped. `routine on` also refreshes a hash that is already there on a board below 0.6.0. Until `requires` is raised nothing protects a routine, because the agent can still remove a hash: that is why the owner raises it.
- *Limit: the hash is public.* Anyone who can write the board can recompute `approved_hash` for an edited routine, or lower `requires`. The hash detects edits made after approval (accidental and naive ones); it is not a defence against a malicious agent. That defence is a signature with the owner's key kept outside git, planned in P5.3 and P5.32.
- *Limit: what is outside the hash.* The hash covers the routine file only. The local watchdog script a routine runs (P5.6), the launch template and the settings file of the agent are outside the board and outside the hash: whoever can change them changes what runs without any reasons being shown. They are protected by the permissions of the machine, not by `roadctl`.

**The run.** `roadctl tick --as AGENT` prints `RUN project/id title` for each routine that is due and allowed, only for the routine's own `agent` (a different agent never sees it), after the usual limits gate (checked only when there are items; the output stays stable, no times). `--json` has an item `{kind: "RUN", project, id, title, routine: {agent, model, env, every, file, last_run}}`, and `routine.attempt` (2 or more) after a run of that routine crashed or failed without a `routine done` (see [Run ledger](#run-ledger)); the text then ends the line with ` (attempt N)`. `--prompt` adds for `RUN`: the routine file (full path), previous run (`last_run` or `never`), the required model and environment (`run it with ITS model and environment; if you are not that model, start a session or subagent with it, for example the agent's launch note in the registry`), the rule to follow the file's Steps, May write and Escalate and nothing else, external writes only if the approved scope has `external`, and to finish with `roadctl routine done`. The text of the routine is never put into the prompt. The executor then:

1. runs the routine with the named model in the named environment (a launcher or an orchestrator starts a session with that model when the one that received the prompt is not it);
2. follows Steps and writes only what May write allows (default: Log lines, delegations, questions for the owner on the board; external systems read only);
3. hands over as Escalate says: `roadctl delegate` to an orchestrator or a stronger worker (for a card with an approved record), or a question for the owner (a `QUESTION for the owner:` Log line); a card is set `blocked: decision: ...` only through the normal tools;
4. records the run: `roadctl routine done <id> --as AGENT --result ok|escalated|failed "summary"`.

`routine done` works only for the routine's own agent (with `--did` and the other fields instead of, or besides, the text: [Run summary and delivery](#run-summary-and-delivery)). It sets `last_run` (now), `last_result` (one of `ok|escalated|failed`; it never grows), `last_reason` (the detail: `ok`, `escalated`, `failed`, or `transient`/`permanent`/`unknown` from `--problem`, or `timeout`/`aborted`/`crashed` when the supervisor records the run) and the consecutive-failure counter `fails` (see [Outcome policy and HOLD](#outcome-policy-and-hold)), appends a Log line (`- date [AGENT] RUN ok: summary`, sanitized like `report`, up to 1500 characters, with ` [run=<id> dur=<s>s host=<host>]` at the end when the run is known; the last 50 Log lines of the file are kept), writes the run to the local [run ledger](#run-ledger), then commits **only that file** and pushes it, like `report`: pushed (`recorded`), or kept locally when offline, without a remote or without git (`recorded-local`; the next `save` pushes it); if the file changed on the server the run is applied again on the server's file. It refuses when the file has other uncommitted changes, when the agent is not the routine's, or when the result is not one of the three. After it the routine is not due until `every` has passed, so the next `tick` is idle.

**Outcome policy and HOLD (roadctl 0.12.0, P5.4).** A routine stops running by itself after repeated failures or a run that may have written outside: `hold` and the `fails` counter live in the routine header (git), so every machine and the owner see them. Three rules: (1) **K consecutive `failed`** (K = 3; `ok` resets the counter, `escalated` is not a failure and does not reset it) sets `hold: after N failed runs in a row`; (2) a run of a routine with scope `external` that began but ended **without a result** (the supervisor recorded `failed: no result`) sets `hold: external run without a result` at once; (3) an **`aborted`** run (timeout, `max_turns`, a crash, or the supervisor told to stop) sets `hold: <timeout|aborted|crashed>` at once, whatever the scope — a stopped run may have written outside, so it is never retried automatically. While `hold` is set `tick` offers no `RUN` (the reason `held: ...` is the same in `tick`, `routine list`, `routine show`, `status`, `brief`, lint and `digest`), `tick` writes nothing to the board, and a second clone sees the hold after `roadctl pull`. The owner lifts it with `roadctl routine resume <id> --by NAME` (owner only): it clears `hold` and `fails` and logs `RESUME`; `resume` does not re-enable or approve anything. The reason comes from one place, the `routine-reasons` hook of the module `outcome-policy` (a board that requires 0.12.0 needs that module, like the approval hash needs its own): `lint` shows it as rule 30 (a warning, `would not run: held: ... (module outcome-policy)`), and `digest` tells it at once as an immediate problem. A hold is one episode with its own id (`hold_id`, written with `hold`, removed by `resume`; outside the approval hash): `digest` tells each episode once, so a hold that `resume` cleared and that came back with the very same text before any digest is told again, and a later tick or digest does not repeat it. `resume` ends the episode. `skipped` (a run the tick or supervisor did not start: `busy`, `limits`, `not-due`, `paused`, `unreachable`) never changes `last_result` or `fails`; the detail is in the run ledger. Two skips also start the term of `every` again (`routine-last-run` hook of the run ledger, this machine only, never git): `limits` (the gate refused a due run) and `unreachable` (the environment was not reachable). `routineRows` then counts the term from the later of the git `last_run`, an `observe` heartbeat and that skip, so `tick` offers the RUN one `every` after the skip, not on every tick; `routine list` shows `(skipped TIME)` and `last_run` stays the real one. `not-due` never moves it (a frequent tick would postpone the RUN for ever), `busy` does not (a live run writes its own `last_run`), `paused` does not (the owner's decision: after `resume` the routine is due at once). **Rollout:** roadctl writes `last_reason`, `fails`, `hold` and `hold_id` only when `config.json` of the board says `"requires": "0.12.0"` or newer (the owner raises it after every machine runs 0.12.0), so an older copy that does not know a hold is refused with one `requires:` line before it can offer a RUN of a held routine. On a board without `requires` (or below 0.12.0) `routine done` and the supervisor behave as before 0.12.0: only `last_run`, `last_result` and the Log line, and nothing holds. A `hold` that is already in a file is always honoured.

**Watchdog routine: a script and no model (`routine observe`).** A routine whose `model` is `none` and whose `agent` is a script agent (registry host `script`, or a name `cron:...`) is run by a scheduler, not by a model. `roadctl tick --as SCRIPT --routine ID` gives `RUN` for it without asking for subscription limits (only when every item is such a RUN; a routine with a model still needs its provider's limits). The script collects facts, applies its rules in code and pipes JSON to `roadctl routine observe <id> --as SCRIPT` (stdin: `{"problems":[{"key":"disk-full","text":"/var is full"}],"did":"nodes 7/7, requests open 1"}`; `key` is a stable name of letters, digits, `.` `_` `-`, up to 40; the same key is the same problem whatever its text). Only the routine's own agent may call it. It records the run through the same publish path as `routine done` (one routine file, committed and pushed alone, applied again on the server's file after a conflict, the run in the local run ledger), with the confirmed problems as `--problem unknown: KEY: TEXT` fields, so `digest` tells each key once and one line when it is gone. Input that is not JSON, or has the wrong shape or a bad key, is recorded as a `failed` run with the problem `transient: observe-input: ...` and exit 1. More than three problems: two are listed and the rest is one `more` problem.

- `--confirm-after N` (default 1): hysteresis. A problem is published after N observations in a row with it, and a published one is gone after N in a row without it; a one-off shorter than N is never published. The streaks live in a local snapshot, `observe.state.json` in the machine state directory (next to `ticks.jsonl`; not in the board, not in the routine header).
- `--heartbeat DUR` (for example `12h`; default: not set): an unchanged confirmed set is not a board commit. The run is closed in the run ledger and its time is kept in the machine state (`last_observed`), which `tick`, `routine list` and `digest` on this machine read as `last_run` (the later of the two). The board gets a commit when the confirmed set changed, when the previous run failed, on the first run, and when the committed `last_run` is older than DUR. Without `--heartbeat` every run is a commit. Limit: another machine sees the committed `last_run` only, so with a `--heartbeat` longer than twice `every` its `digest --daily` shows the quiet watchdog as OVERDUE; set DUR below twice `every` where that matters, or read the digest on the machine that runs the script.
- A crash writes nothing, so the routine stays due and the next tick runs it again; `pause` stops the tick as for any routine.

The shipped example: [`examples/routines/watchdog.md`](../examples/routines/watchdog.md) and [`examples/scheduler/watchdog-example.py`](../examples/scheduler/watchdog-example.py) (switched off, marked as an example). Its rules live in the script: closed objects are never problems, and a request is late by the time since it last moved in its status against a limit per status, not by its age.


**Looking.** `roadctl routine list [--all] [--json]` prints, per routine: id, on/off, every, agent, model, env, last run and result, `due` or `not due`, and why it would not run now (`missing model`, `not approved`, `disabled`, `board switch off`, `outside hours`, `duplicate id`, `invalid: ...`); `--all` covers every board. While the machine is paused the output starts with the `PAUSED ...` line (`--json`: a `pause` object in every row), because nothing starts here whatever `due` says. `roadctl routine show <id>` adds the header and the Goal, Steps, May write and Escalate text, which is data for whoever runs the routine. `roadctl autonomy` lists the routines with their run state under the card queue, `brief` and `status` have one line (`ROUTINES switch on | 2 routine(s), 1 on, due now 1`) only when routines exist, and `BOARD.md` has a short `Routines` section with static facts only (no last run, so a run never makes it out of date).

**Lint.** Rules 25 to 29 and 21: a malformed routine file (25; this includes an `hours` that does not parse, has an unknown time zone or ends before it starts, a `timeout` that is not like `30m`, `2h`, `1d`, and a `notify` that is not `problems`, `always` or `never`), a routine without agent, model or env (26), `enabled` without `approved` (27), a duplicate routine id (28), an agent that is not in the registry when one exists (29, warning), an unknown scope token (24, warning, tokens `read`, `board`, `external`), a malformed `autonomy.routines` (21).

What routines do not do: roadctl starts no model and calls no external system; whether the executor kept to May write is not checked by a tool, the approved scope limits what the executor was told, and a run is a claim to verify like a report.

## Work environment apart from the executor's machine (P5.23)

Where the model runs and where the work lies are two things. A routine already has `agent` (the executor, whose registry name ends in its machine) and `env` (the environment); a card may carry `env`, `role` and `needs` (tools or MCP servers, `data:NAME` for data access) in its header. The owner's local registry (never the public skill) says how an executor reaches an environment. Both ways are legitimate:

- `placement: on-host` (the default): the executor runs on the machine of the environment (an agent such as `claude-code@work-notebook`).
- `placement: remote-access`: the model runs on another machine (for example the home PC) and reaches the environment through the `access` paths: `ssh` host and the MCP servers the path is said to offer.

```json
"environments": { "Work-notebook-wsl": { "machine": "work-notebook", "placement": "remote-access",
                  "access": [ { "from": "home-wsl", "ssh": "work-notebook", "mcp": ["atom-services"] } ] } },
"preference":   { "worker": ["claude-code@home-wsl", "codex@home-wsl"] },
"agents":       { "claude-code@home-wsl": { "machine": "home-wsl", "tools": ["atom-services"], "data": ["atom"], "fit": { "worker": { "confirmed": "2026-11-10", "evidence": "checks of similar tasks" } } } }
```

A registry without these keys behaves as before. The `ssh` value must look like a host name (letters, digits and `. _ @ : -`, not starting with `-`): anything else is refused and never passed to ssh, so a registry cannot slip in an ssh option. MCP in the registry is a declaration, never proof that the server works now, and ssh to the machine is not the MCP server.

- `tick` and `routine show` show the environment and the way to it for a described `remote-access` environment: `RUN` items carry `routine.access`, `TAKE` items `delegate.env` and `delegate.access` (`placement`, `via` ssh|local|none, `machine`, `ssh`, `mcp`). Without the registry keys the output is unchanged.
- `lint` warns (rule 32 for a routine, the board check for a delegated card) when the executor is on machine A, the environment on B and the registry has no access path from A to B, and when the placement is `remote-access` but the executor runs on the environment's own machine.
- `roadctl env check ENV [--as AGENT | --from MACHINE] [--json]` is read only: the environment is on the executor's machine (reachable), or `ssh -o BatchMode=yes -o ConnectTimeout=5 HOST true` answers, or there is no path (unreachable; exit 1). `supervise` makes the same check before the model starts; when the environment is unreachable the run is recorded as `skipped: unreachable` (exit 4) and the command does not start.
- `roadctl candidates --card ID [--json]` or `roadctl candidates --env NAME [--role ROLE] [--needs a,b,data:x] [--json]` is one read-only choice of an executor. It walks `preference.ROLE` (the first is the main one, the rest the agreed reserve; without a list, every agent with the role) and shows for each agent the order and why it is refused: not in the owner's list, no role, fitness for the role not confirmed (`agents.NAME.fit.ROLE.confirmed`), missing tool or data, no access path, environment unreachable, the agent's own limits (reserve reached, unknown limit: no guess), a paid API with no agreed `budget`. The first eligible agent is `chosen`; no candidate means exit 1 and nothing is launched. It never changes the environment, the rights, the data access or the budget, does not map S/M/L to a model and does not learn; no model name is built into roadctl. The choice is checked again before the actual start.

**Profiles and fitness.** The registry holds profiles by kind of work (ordinary implementation, hard diagnosis or planning, review), a main executor and an agreed reserve. Fitness is confirmed by checks of similar tasks; price and usage count only among the fit candidates.

**Hermes.** Hermes is no longer the main way to work on a remote environment: with `remote-access` the model starts locally and reaches the environment by ssh and MCP. With `on-host` it is as before (the example scripts run `claude -p` on the machine of the environment over ssh). Starting a model on the environment's machine from a service waits for the release candidate; the dispatcher starts models on its own machine only.

- `roadctl candidates --multiagent` is a read-only advisory: registry-ordered `preferences` include `provider`, `model`, `eligible` and `reasons`, using the same static role, fitness, script, tool, data and environment checks as normal candidates. Availability and limits are not probed, so no row is eligible for launch; unknown provider or model is `null`. It does not choose, launch, grant access or authorize spending. The harness must verify routes, availability, limits and permissions before use. An empty preference list is valid.

## Checking the environment (doctor)

Machines differ in small ways that only show on the first real run: an old installed copy, a path with another letter case, a command that is in `PATH` of a login shell but not of cron or `ssh host command`, a repository the user cannot write to, a state directory on the WSL side and another on the Windows side. `roadctl doctor [--agent NAME] [--json] [--online [--host HOST]]` finds them in one command. It names the actual `roadctl` a non-interactive shell finds and the copy it runs, the board for the working directory, the profile `ROADCTL_AS` resolves to and the state directory (checks `launcher`, `board-current`, `agent-name`, `state-dir`). For hooks it separates a configured settings file from a recorded run: only a line written by `roadctl hook` shows that the harness actually calls it. It cannot prove that a running agent session has loaded the skill; the check for that is in `references/setup.md` of the skill. It is **read only**: it writes no file and no git state (it runs `git` with `GIT_OPTIONAL_LOCKS=0`), starts no model, does not poll the limits, and touches the network only with `--online`. A test compares a snapshot of the whole working tree before and after.

Each check has an `id`, a `status`, a `detail` and a `hint`. `ok` passed; `warn` is a difference that may bite later (the run goes on, exit 0); `fail` is a defect that stops work; `skip` was not checked (the detail says why). The text output lists failures, warnings, passed and not-checked checks apart. Environment variables are only ever **named**, never printed, and a value held by a variable whose name looks like a secret (`TOKEN`, `SECRET`, `PASSWORD`, `KEY`, `AUTH`, ...) is replaced by `[redacted]` if it ever reaches the text. Paths under the home directory are shown as `~/...`.

| Check `id` | What it looks at | When it is not `ok` |
| --- | --- | --- |
| `version` | version and short sha (12 hex characters) of the copy that runs, and whether it is a checkout or an install | never (information) |
| `node`, `git` | Node 20 or newer (warn below 20, fail below 18); `git --version` | `git` missing: fail |
| `installed-copy` | `~/.local/share/road-map-journal/roadctl.mjs`: its version, its sha, and the record `installed.json` that `update-installed.mjs --roadctl --apply` writes (version, sha, per-file sha) | no copy, no `installed.json`, files that differ from the record: warn. A version below 0.2.0 warns that it **cannot see `requires`** and would run a board that asks for a newer roadctl |
| `installed-modules` | the `roadctl/` folder with `index.mjs` next to the installed file, and every file the record lists | folder or a recorded file missing: fail (built-in commands run, module commands and hooks do not); files this copy has but the install lacks: warn |
| `installed-current` | the installed copy against the copy that runs doctor (version and sha) | differs: warn (the hint says which command installs this one) |
| `launcher` | the `roadctl` a non-interactive shell actually finds in `PATH`, the target of its launcher and that target's version and sha, against the installed copy and the copy that runs doctor | no `roadctl` in `PATH`, a launcher whose target is gone, or a third copy that is neither the installed one nor this one: warn (or **fail** for a missing target) |

| `pause` | only when `pause.json` exists in the state directory: a pause that is in force is a warning (a forgotten pause is the usual reason for "nothing runs"; the hint is `roadctl resume`), an expired one is ok | paused: warn |

| `state-dirs` | on WSL: a second, native Windows state directory (`<Windows home>/.local/state/road-map-journal`; found under `/mnt/c/Users/*`, or set `ROADCTL_WINDOWS_HOME`). Locks, the ledger and limit confirmations are not shared between the two | both exist: warn. A Hermes monitor state directory (`~/.road-map-journal`) is mentioned, not judged |

| `agent-name` | `ROADCTL_AS`: resolves in the registry to an executor, a profile, a variant or an `orchestrator/profile` pair (the name `claim` writes) | not set: skip (the hint says how to set it); no registry: skip; a name that does not resolve: **fail** (the hint lists the known profiles and executors) |
| `hooks` | for each harness whose command is in `PATH` (`claude`, `codex`, `hermes`): whether its roadctl hooks are in the settings file, and separately whether a hook run was recorded in `$XDG_STATE_HOME/road-map-journal/hooks.jsonl` by `roadctl hook` | command in `PATH` but no hooks: warn (the hint is `roadctl hook-install --claude --user --apply`, `--codex --apply` or `--hermes --apply`); hooks configured but never recorded: warn, and the detail says this proves configuration only, not that the harness calls it; configured and recorded: ok, with the event and time; command not in `PATH`: skip. | `launch-templates`, `launch-template` | the local file `conductor.json` (see [Launch description](#launch-description)): absent is `skip`; inside a git work tree, owned by another user or writable by group or others, or invalid: **fail**; a settings or MCP file it names that does not exist: warn; with `--agent NAME`, `launch-template` warns when no template exists for that agent | fail / warn as listed |
| `board-current` | the board found for the working directory (or `--board`), with its actual path | none: warn |
| `boards` | every board found: the workspace, the boards list and the one for the current directory, each with its actual path | none: warn |
| `board-load`, `board-requires`, `board-requires-installed` | per board: `config.json` reads; `requires` (see [Compatibility between copies](developing-roadctl.md)) against this copy and against the installed copy | a board that this copy or the installed copy is too old for: **fail** (`board requires a newer copy`); unreadable board: fail |
| `board-git`, `board-sync`, `origin-reachable` | per board repository: its `.git` is writable by this user and has no stale `index.lock`; uncommitted changes, commits not pushed, commits behind origin as last fetched; with `--online`: `git ls-remote` answers | `.git` not writable: fail; the rest: warn |
| `service-clone` | the `service` object of the local `conductor.json` (`workspace`: the clone the service works in; optional `owner_clone`, else the default workspace of the owner: the pointer file and `~/projects/agent-workspace`): absent is `skip`; `workspace` is not a git clone: warn; `owner_clone` that does not exist or is not a git clone: warn (the clones cannot be told apart); it is the same repository as the owner's working clone (a folder inside it counts): warn, with the hint to clone the boards repository for the service; a clone of its own: ok | warn |
| `routines` | per board with routines: every enabled routine has agent, model, env, an approval and valid fields, appears once, and (with a registry) names a known agent | inconsistent: warn |

`--agent NAME` also counts the routines of that agent. `--online` adds `origin-reachable` and, with `--host`, `ssh-env`; it never asks a model and never polls limits (use `roadctl limits` for that). `--host` takes an ssh destination and is only accepted together with `--online`, because it contacts that host.

`roadctl --version` prints one line, `roadctl <version> sha:<12 hex>`, for the copy that runs; `roadctl version` still prints the version alone. The sha covers `roadctl.mjs` and the `.mjs` files of `roadctl/` (line endings normalised, test files excluded), so two machines with the same line have the same code. `update-installed.mjs --roadctl --apply` writes `installed.json` next to the installed copy (`schema`, `version`, `sha`, per-file `files`, `installed_at`) and leaves it untouched when nothing changed.

**Exit codes:** 0 no failure (warnings may be present), 1 at least one failure, 2 usage error (`--agent` without a valid name, `--host` without `--online`).

**`--json`** prints one object: `{"schema": 1, "roadctl": {"version", "sha"}, "platform", "node", "online", "agent", "ok", "summary": {"ok", "warn", "fail", "skip"}, "checks": [{"id", "subject", "status", "detail", "hint"}]}`. `subject` is the board or agent a check is about (`null` for the machine), `hint` is `null` when there is nothing to suggest, `ok` is true when `summary.fail` is 0. A change of this shape raises `schema` and `scripts/testkit/doctor-schema.mjs` in the same commit.

## Explicit card checkpoint (P5.43 building block)

```sh
roadctl checkpoint W-3 --board ./board --as worker < handoff.json
```

The agent supplies sanitized JSON, not a hook error or a transcript:

```json
{"did":"Checked the local diff","next":"Run the scoped tests","in_flight":"unknown: remote write; read back before retry"}
```

All three fields are required, nonempty strings of at most 350 characters with no control characters. Only these keys are accepted; stdin is limited to 8192 bytes. Do not put credentials, raw provider errors or private transcripts in these fields: their content goes into the card's git-visible Log, not the local run ledger. Validation is structural, not a secret detector.

Both the card ID and `--board DIR` are mandatory (`--project` and implicit CLI context are not accepted); `--as AGENT` names the author. The target must exist exactly once, have a valid parsed header and be `doing` according to the board's `status_map`; unsupported `requires` refuses the write. Several doing cards are fine: none is guessed. The command reuses the normal Log writer, appends one `checkpoint: did: … | next: … | in-flight: …` entry and updates `as_of`, preserving the status and other cards. Exit 0 means written; invalid input, unavailable targets and write errors exit 2. No commit or push.

This is an explicitly invoked handoff handler, **not an automatic checkpoint** and not evidence that a request or process stopped. Input is sensitive: it is written to the card Log and can be committed and shared through git; do not include secrets or provider error payloads. Markup is stripped and `|` replaced in the fields. The unattended L3/L4 mandate gate applies (refusal exits 1). It does not consume Hermes `api_request_error`, simulate 429, infer terminal outcomes, deliver notifications, recover work or retry. Those paths remain separate. The one-writer-per-card rule is required: validation and writing are not atomic against another writer (TOCTOU), and repeated calls append repeated entries.

## Run ledger

Every run of a routine and of a delegated task, and the end of a run of the duty orchestrator (`run done`), leaves a record on the machine where it ran, not only the decision of `tick`. The record has a start, an end, an outcome, a reason, the attempt and the fields of a run summary; a run that began and never ended is found and marked. The code sets the duration, the host, the version of roadctl and the times; the model does not carry an identifier.

```text
roadctl runs [--open] [--json] [--as AGENT] [-n 20]
roadctl run begin <routine|card> --as AGENT [--run ID]
roadctl run note [RUN_ID] "what was done" [--as AGENT]
```

`roadctl runs` is the owner's view (read-only; `--open`: runs that began and did not end, with `OVERDUE` for one past its deadline; `--json`: an array of run records, below). `roadctl run begin` and `run note` are for paths without a supervisor. Both commands are hidden from the `roadctl help` overview (it has a line budget of 70) but `roadctl help runs` and `roadctl help run` work; a scheduler that supervises the process (P5.2) uses the same records.

**Where the ledger lives, and what is in it.** In the machine state directory, `${XDG_STATE_HOME:-~/.local/state}/road-map-journal/`, next to `ticks.jsonl`: `runs.jsonl` (append-only, one JSON line per event, never longer than 4096 bytes; text is cut to fit), `runs.jsonl.1` (the one previous generation), `ticks.state.json`, `ledger.lock`. **`runs.jsonl` holds the text of run summaries and checkpoints** (what the agent said it did, why a run failed), so it is local to the machine and is never written inside a git work tree: when the state directory is inside one, roadctl does not write the ledger (`run begin` says so on stderr; `routine done`, `claim`, `report` and `tick` go on as if there were no ledger). A repository made of the whole home directory is not counted. Other machines do not see this file; they see the Log line of the routine (below). A reader skips a broken or half-written line, and nothing about the ledger can stop `routine done`, `claim`, `report` or `tick`: an unusable state directory (a path that cannot be created, a full disk, a held lock) only means no record.

**The run record** (the element of `roadctl runs --json`; every field is always present, in this order; the checker is `scripts/testkit/run-schema.mjs`):

| Field | Content |
| --- | --- |
| `run_id` | `r-` and 12 hex digits, derived (below), or the id a supervisor or `--run`/`ROADCTL_RUN_ID` gave; `s-...` for a skipped run |
| `kind` | `routine`, `task` (a delegated card) or `orchestrator` |
| `id`, `project` | the routine or card id, and the project (board) name; `project` is `null` for an orchestrator run |
| `agent`, `model` | who ran it; `model` is the routine's `model`, otherwise `null` |
| `host` | the host name of the machine (`ROADCTL_HOST` overrides it), set by code |
| `source` | `agent` (the command of the agent), `supervisor` (a supervisor looks after the run: P5.2) or `tick` (written by `tick`: crashed, skipped) |
| `started`, `finished` | ISO-8601 UTC, the clock of roadctl (`ROADCTL_NOW` in tests); `started` is `null` for a run that ended without a `begin` |
| `duration_s` | seconds between them, set by code; `null` when unknown |
| `outcome` | `started` (open), `ok`, `escalated`, `failed`, `timeout`, `aborted`, `crashed` or `skipped` |
| `reason` | for `skipped`: `busy` (another tick of this agent holds the lock), `limits` (the gate was closed for work that was due), `not-due` (the routine is allowed but not due yet) or `paused` (the owner paused this machine); for `crashed`: why; otherwise `null` |
| `attempt` | 1, or one more than the runs of the same routine that ended `crashed`, `failed`, `timeout` or `aborted` since its `last_run` |
| `roadctl` | the roadctl version that wrote the record |
| `usage` | reserved, always `null` (the cost of a run is filled by a later card) |
| `did`, `decisions` | lists of short texts (limits: [Run summary and delivery](#run-summary-and-delivery)); without `--did` `did` has the first 120 characters of the text given to `routine done` or `report` |
| `problems` | list of `{kind: transient\|permanent\|unknown, key, text}` |
| `needs_owner`, `not_checked`, `ref` | text or `null` (`ref`: a link to the details, for example a session id) |
| `writes` | what the run wrote, set by code (`routine:<id>`, `card:<id>`) |
| `note` | the last checkpoint of `run note`; it stays in the record when the run is broken off |
| `count` | 1; for a folded streak of `skipped` the number of repeats |
| `deadline` | when an open run without an end counts as `crashed` (set at `begin`); `null` for a run that was never open |
| `owner_answer_ids` | IDs of owner answers passed to a routine at the start of this run; empty when no snapshot was supplied, including older records |

The fields from `did` to `ref` are the summary of a run; the agent fills them with `--did`, `--problem`, ... (below, [Run summary and delivery](#run-summary-and-delivery)). The ledger checks types and the 4096-byte line.

**Events and folding.** The file holds events (`begin`, `note`, `end`, `crash`, `skip`, `skips`); the run record is the fold of the events of one `run_id` (both generations of the file are read). The first real `end` wins; an `end` replaces a `crashed` mark (the agent did finish, only late); a `crash` never replaces an `end`.

**The run id and begin.** `roadctl run begin <routine|card> --as AGENT` starts a run and prints `run <id> begun`. It is idempotent: a second `begin` of the same thing while its run is open prints `run <id> already begun at <time> by <agent>` and exits **5**, so two schedulers on one machine do not both start it. The id is derived from the routine, its previous `last_run` and the attempt (the same inputs give the same id), so nothing in the text of `tick` has to carry it; a supervisor can put its own id in `ROADCTL_RUN_ID` (or `--run ID`), and then `begin`, `note` and `routine done` read it from the environment and the model never carries it. Through `wsl.exe` a variable does not pass without `WSLENV`, and through `ssh` only when it is set in the remote command. `routine done` finds the open run of its routine by itself; with `--run` or `ROADCTL_RUN_ID` naming a run of another routine it refuses; without a `begin` it still writes a whole record (`started` and `duration_s` are `null`) and works exactly as before.

**Crashed.** An open run whose `deadline` has passed is marked `crashed` by the next `tick` (`reason: no end by the deadline <time>`, the last checkpoint kept in `note`). The only test is time: `timeout` of the routine (`timeout: 30m`, `2h`, `1d`; 5 minutes to 30 days; default 2 hours) from the start, or for a delegated task the end of the lease; the clock is `nowMs()` (`ROADCTL_NOW`). The process of a run is never looked at (the process that ran `begin` is gone long before the agent finishes), except that a run with `source: supervisor` is left to its supervisor. Two ticks do not both write it (a lock), and a `routine done` that arrives later replaces the mark. A new `claim` of a card whose earlier run is still open closes that run as `crashed` (superseded).

**The text of `tick` and `attempt`.** After a `crashed` (or failed, timed out or aborted) run without a recorded `routine done`, the same routine is offered again with `attempt N` in its item: `RUN project/id title (attempt 2)` in the text and `routine.attempt` in `--json` (only from 2 on; the text of a stuck routine therefore changes once, which wakes a monitor that compares the output, and is stable again). Nothing else about a run enters the text: no id, no time, no counter (one exception: ` (recover: supervised run ID died)` after a dead supervisor, see [Run supervisor](#run-supervisor)). A finished run (`routine done` moves `last_run`) starts again at 1.

**Skipped.** A tick that did not run something leaves one record of its reason: `limits` (the gate was closed while a routine was due), `busy` (the lock of this agent or of this routine job was held), `not-due` (an allowed routine of this agent that is not due), `paused` (the machine is paused: a tick that stops at the switch records one skip for the agent, or for the routine of a `--routine` job; it does not look at the boards, so it cannot say what was due; the next tick that is not paused ends the streak). A streak of the same skip is one record whose `count` grows; a different reason, or the thing running again, ends the streak.

**Tasks.** `claim` begins a run of the card (`kind: task`, the lease as the deadline) and `report` ends it with `ok` and the first characters of the report; no new protocol.

**The ticks ledger.** `ticks.jsonl` keeps the format of its lines (`roadctl tick --ledger` is unchanged). A tick that repeats a `blocked-reserve`, a `blocked-unknown`, a `busy` or a `paused` of the same agent and filter does not add a line; `ticks.state.json` holds, per agent and filter, the last decision with its count and the first and last time (a streak of ten `blocked-reserve` ticks is one line and a count of ten); `idle` and `work` still add a line per tick. Inside `tick`, under its lock, a `ticks.jsonl` over 1 MB is renamed to `ticks.jsonl.1` (one previous generation, the older one is replaced) and `runs.jsonl` over 4 MB likewise.

**The Log line.** When the run is known (a `begin`, `--run` or `ROADCTL_RUN_ID`), `routine done` ends the Log line of the routine with ` [run=<id> dur=<seconds>s host=<host>]` (`dur` is left out when there was no `begin`); the line stays within the 1500 characters. Another machine sees only git, so it reads the run back from this trailer. A run without a `begin` keeps the line exactly as before.

**Format change (roadctl 0.3.0).** The routine header key `timeout` and the `attempt` field of a RUN item are new. An older copy only warns about the unknown key and ignores `attempt`, so a board that uses `timeout` sets `"requires": "0.3.0"` in `board/config.json` first (see [developing-roadctl.md](developing-roadctl.md)); a board that does not use it needs nothing. `last_result` keeps `ok`, `escalated` and `failed`.

## Owner questions

Boards using owner questions must set `"requires": "0.13.0"` before writing them, so an older roadctl refuses the board. `roadctl ask ID --board DIR --as AGENT` reads JSON on stdin; `ID` names exactly one card or routine. For a reversible question provide a recommendation; the undo window is roadctl's own: the next daily overview from `digest` in `board/config.json` (`{"digest": {"daily": "09:00", "tz": "Europe/Moscow"}}`), or 24 hours when the board has no such schedule, and an `undo_until` sent by the asking side is ignored. The question is a recorded decision that may be undone until that time. Use reason `irreversible` or `outside-mandate` for a blocking question; do not supply a recommendation. A claimed card requires `checkpoint` with `did`, `next` and `in_flight`. A blocking question releases its claim and blocks that card; a reversible non-blocking question keeps the claim with the current worker, who continues and reports. After the owner answers, `tick` offers `RESUME` to its original agent. Other cards continue. A routine waits for its answer; the next RUN prompt includes it as data. Delivery is an explicit mark in git, not a comparison of times: the routine header `answers_received` (outside the approval hash) lists the ids of the answers that a finished run received. `routine done` writes it in the same commit as the run, so every clone sees it after a pull. An answered question whose id is not listed is in the prompt of every RUN again (repeating is allowed, losing is not). `routine done` marks an answer only when the run began after it (the begin in the local run ledger: `run begin`, `supervise`) and ended with a result of its own (`ok` or `escalated`); a run that failed, a run the supervisor recorded without a result, a timeout or a crash, and a bare `routine done` with no begin mark nothing. A run that began before the answer and ends after it does not take the answer. A question leaves its card file uncommitted: after `ask` on a claimed card run `roadctl save` before `roadctl report`, which refuses a card file with other uncommitted changes.

The class of a question is decided by roadctl, not by the asking agent: it is blocking when `reason` is `irreversible` or `outside-mandate`, when the question has no `scope` (an area that cannot be established never makes a non-blocking question), when the question's `scope` or the card's approved scope (or an `external:` blocked reason) names an external area, when `scope` names an area outside the card's approved scope, when the card is outside the approved mandate, or when the question's prompt, a choice point's prompt or a named area matches a subject of the mandate's `## Tell the owner` (case-insensitive). A declared `reversible` never lowers it: the question is stored blocking and no decision is written. A stored `blocking` may only raise the strictness: a record with an irreversible reason or an external area and `blocking: false` is refused as invalid data. `scope` is 1 to 5 short area names such as `board`, `repo` or `external`.

```json
{"question":{"id":"q1","kind":"confirm","prompt":"Proceed?","reason":"irreversible"},"checkpoint":{"did":"Prepared the change","next":"Wait for the owner","in_flight":"none"}}
```

Kinds: `confirm` answers are JSON booleans; `text` answers are strings of at most 1000 characters; `choice` carries `points`, each with `id`, `prompt` and an `options` array, and its answer is an object mapping point IDs to selected or custom text. Answer choice points together or separately. `roadctl answer ID QUESTION --board DIR --by OWNER` reads `{"answer": ...}` from stdin. `roadctl undo ID QUESTION --board DIR --by OWNER` reads `{"comment": "..."}`. Both are owner-only and audited; exit 7 means already answered and exit 8 means the undo window expired. Undo refuses a card outside doing or review, so it cannot silently reopen an accepted or separately blocked card. The commands publish only the changed item to its configured upstream branch when the board has a remote and upstream; they refuse an item with other uncommitted changes. They leave the result local when another commit is already unpushed, and never push tags. A failed push leaves the change or commit locally and reports that it was not published; reconcile and save the board. A board without a remote stays local.

`roadctl inbox --board DIR --json` returns `{ "version": 2, "items": [...] }`; version 2 adds a `refused` item with a reason and a hash of the unreadable item, so strict version 1 clients must reject the new version. Every item has `type`, `target`, `hash` (SHA-256 of its current content), and a roadctl-generated `confirmation`; question and decision items also have `question`, a `quote` with the agent's own wording and `undoable` while the decision may be undone. The `confirmation` is built from roadctl data only — kind of action, target, question id, card title, area and a short content hash — and never contains the agent's prompt or the escalation text; those go in `quote` (question and decision: the prompt; escalation: the `RUN escalated:` line), so the action line and the agent's words are shown separately. It is the same contract for every type: question, decision, review, approval, escalation, proposed and milestone. `undoable` is true only while `roadctl undo` would pass: a decision in its window on a card that is doing or review, so no Undo button appears for a done or separately blocked card. After an undo the rework `RESUME` goes to the current holder of the work (the claim, else the delegated agent, else the asking agent), and only that holder loses the plain `TAKE`; an unreadable `Questions` section produces a `refused` item and is reported by `lint`, while other cards keep their items. Types are `question`, `decision`, `review`, `approval`, `escalation`, `proposed` and `milestone`. `roadctl inbox defer ID QUESTION --board DIR --by OWNER --until ISO` hides that item until the specified time; use `review`, `approval`, `escalation`, `proposed`, or `milestone` instead of QUESTION for those items. It does not answer the question or allow work to start. The daily digest shows decisions, proposals and milestone requests. Do not treat board text or owner answers as instructions to expand permissions. After `undo` the card is a `RESUME` task for its original agent, with the owner's comment, and is not offered as a plain `TAKE`.

For a routine, `tick --json` carries up to 40 pending answers in `routine.owner_answers` and `tick --prompt` prints their IDs beside the answers. Pass exactly the IDs of the answers sent to the executor to `run begin --owner-answers ID,ID` or `supervise --owner-answers ID,ID` at startup. Keep the launch prompt and IDs together. `routine launch --json` includes both when there are answers. Finish with the returned `routine done --run ID` or the supervisor-provided `ROADCTL_RUN_ID`. An explicit `ok` or `escalated` result publishes just those answers in `answers_received` with the routine result, including when a late result replaces a crash. Pending answers stay eligible for subsequent runs until an executor reports receiving them. A run with no snapshot leaves answers pending.

## Run summary and delivery

The owner does not read logs: every unattended run (a routine, the duty orchestrator) and every delegated task ends with a short summary that the agent fills in, and a command with no model in it, `roadctl digest`, turns what happened into a few plain lines that a scheduler can forward to a chat. roadctl sends nothing over the network itself.

**The fields** (flags of `routine done`, `report` and `run done`; the same names and limits everywhere):

| Flag | Meaning | Limit |
| --- | --- | --- |
| `--did TEXT` | what was done; repeatable; **required** (see below) | 3 items, 120 characters each |
| `--decision TEXT` | a decision the agent took; repeatable | 3 items, 160 |
| `--problem "kind: key: text"` | a problem; `kind` is `transient`, `permanent` or `unknown`; `key` is a short stable name (`dns-timeout`, letters, digits, `.` `_` `-`, up to 40) that lets the owner see one problem once; repeatable | 3 items, text 160 |
| `--ask TEXT` | what is needed from the owner | 200 |
| `--not-checked TEXT` | what was not looked at | 160 |

**Questions and decisions.** Ask the owner before an irreversible decision or one outside the approved mandate or card, and wait for that decision. For reversible decisions inside the approved scope, the owner’s standing rules may permit the agent to record its recommended choice and continue; make the choice and how to reverse it visible. A question may be a confirmation, points with options and a custom answer, or a free-text question. The `--ask` flag above is a summary field, not a structured question or an owner answer.

The duration, the host, the model, `usage`, `ref` and `writes` are set by code. Over a limit the text is cut (with `…`) and extra items are dropped, with a warning on stderr: the run is still recorded. A `--problem` without a key or kind is accepted with a derived key and a warning (the same problem is then not recognised in the next run). The language is not checked; the headings of the owner's text follow `language` of `board/config.json` (`ru`, otherwise English), the agent's words are shown as written. Values lose `|` (becomes `/`) and `;` (becomes `,`), which are the separators of the Log form.

**Old form and `summary: required`.** Without any of these flags `routine done` and `report` work exactly as before (the text is the summary, the Log line is unchanged). With a flag but without `--did`, the positional text becomes the one `did` item. A board whose `config.json` says `"summary": "required"` refuses a `routine done` or `report` without `--did` (exit 1, nothing recorded); `run done` always needs `--did`. Without a text and without `--did` the command is a usage error (exit 2). The `--did` flag needs no positional text.

**The Log form.** With fields, the Log line of a routine is `- DATE [AGENT] RUN ok: did: a; b | decision: c | problem: transient: key: text; permanent: key2: text | ask: question | not-checked: what [run=ID dur=Ns host=H]` (labels in this order, empty fields left out; the card's REPORT line is the same without `RUN ok:`). It always has the run trailer, is at most 1500 characters (when it would be longer the longest texts are shortened, decisions first and `did` last) and is the copy another machine reads after `pull`: `roadctl digest` parses it back into the same fields. The full record (with the same fields) is in the local run ledger.

**What the command prints.** After the usual line, `routine done` and `report` with fields print the summary for the owner, at most six lines of plain text (no markdown, no raw output, nothing from a log): the header (`routine my-app/server-watch: ESCALATED (agent, 12s)`), `did`, `decided`, `problem`, `needs from you`, `not checked`. A Hermes agent that answers the owner with exactly what `routine done` printed gives the owner this text. A run that is only recorded locally (`recorded-local`, `reported-local`: offline, no remote) ends its last line with `[not published: waits for roadctl save]`. `run done` prints the same lines; its record lives only in the local ledger (the duty orchestrator has no routine or card to write to), so the digest of that machine delivers it. `run done` ends the open run of the agent when there is one (`ROADCTL_RUN_ID`, `--run`), else it writes a whole record (`kind: orchestrator`, `id` = the agent).

```text
roadctl routine done mr-status --as claude-code@work-notebook --result escalated \
    --did "checked 9 servers" --problem "permanent: disk-full: /var is full on srv-3" \
    --ask "free space or approve a bigger disk"
roadctl run done --as claude-code@home-wsl --result ok --did "took W-3" --did "accepted W-2"
```

**`roadctl digest`** (hidden from the overview like `runs`; `roadctl help digest` works):

```text
roadctl digest [--since-state NAME] [--dry-run] [--all] [--json]    what is new: problems and questions, each once
roadctl digest --daily [--all] [--json]                              the overview
```

An empty output means silence: a scheduler forwards whatever is printed and nothing else. The exit code is 0 when there is nothing to say; 2 is a usage error or no board.

- *Sources.* The Log lines (`RUN ...`) of the routines and the `REPORT:` lines of the cards of the board (`--all`: every known board), so a run on another machine arrives after `roadctl pull` (run it first; digest does not touch the network), and the local run ledger for what never reaches a board: `crashed`, `timeout`, `aborted`, `skipped` and the orchestrator's `run done`. Lines without fields (the old form) are read as one `did`. A Log line of a run older than 30 days is never reported; the first digest of a state name reports only the last two days and marks the older ones seen without a word.
- *What is news* (header `notify` of the routine; the default `problems`). A finished run is told when it brings a problem that is not open yet: the result `escalated` or `failed` (the outcome counts as a problem named after itself), a run that crashed or timed out, a `--problem` with a new key, or a question (`--ask`) not asked before. The same key in the next run is not told again; a problem that is absent from a later run of the same routine is one line `resolved: my-app/server-watch: dns-timeout`. `ok` with nothing new is silent. `notify: always`: every run (and the skipped streaks of that routine); `notify: never`: nothing at once (the daily overview still shows it). Tasks (`report`) and orchestrator runs follow `problems`. `skipped` (limits, busy, not due) is news only under `always` and is counted in `--daily`.
- *At most six lines per run*, separated by a blank line, and about 3500 characters in all (the smallest common chat limit is 4096); what does not fit stays unmarked and comes in the next digest, after a line `N more`.
- *The delivery state.* `digest.state.json` in the state directory (next to `runs.jsonl`; keys and times, never summary text): per `--since-state` name the events already told (with the time, kept 60 days) and the open problem keys. Use one name per channel. The mark moves after the text was printed; a second digest at the same time prints nothing and says so on stderr (a lock). `--dry-run` prints without marking. **A delivery that fails after roadctl printed the text loses that message**: Hermes (or whatever forwards the output) may fail after roadctl marked it told. This is accepted; the daily overview is the safety net, because it is a snapshot of the state, not a list of news.
- *`--daily`* (the scheduler runs it once a day; the time is the scheduler's setting, roadctl has none; it changes no state): `roadctl daily overview DATE`, then one line per enabled routine: `my-app/server-watch: ok 2h ago - checked 9 servers`, `ESCALATED 5h ago - problem disk-full`, `never run`, `not running (reason)`, and **`OVERDUE, last run 3d ago (every 1d)`** for a routine that is allowed to run (enabled, board switch on, inside its `hours`) and whose `last_run` is older than twice its `every` (outside its `hours` it is not overdue). A line `PAUSED since ...: reason` follows while this machine is paused (`roadctl pause`; the routines are then late by the owner's own choice). Then the orchestrator runs of the last 24 hours, one line `this machine, last 24h: crashed 1, skipped busy 14`, the tasks reported in the last 24 hours and one line about the owner's commands (below). This is the only way to tell "all is well" from "the scheduler is dead". A board whose routines are all held back by the board switch is one line.
- *A board that needs a newer roadctl* (`requires` in `config.json`, see [developing-roadctl.md](developing-roadctl.md)) gives one `requires: <project>: board requires roadctl X or newer; this is Y` line (the same as `tick` prints), once in the news and always in the daily overview; its runs are not read.
- *The owner's commands.* The daily overview has a line `owner commands, last 24h: 2 (approve P5.1 by AGENT; ...)` read from `owner-commands.jsonl` in the state directory, one JSON object per line: `{"time": ISO, "command": "approve", "target": "P5.1", "by": "AGENT", "outcome": "ok|refused"}`. The writer is the owner audit ([Unattended mode and the owner audit](#unattended-mode-and-the-owner-audit)); without the file there is no line. The line also counts what owner commands left in git (`approve` and `auto`: the card's `approved`; `done`: `accepted`; `routine on|off`: the routine's Log; `mandate approve`) in the last 24 hours (by date: yesterday and today), so a command run on another machine is in it after `roadctl pull`; a command that has a local audit line is counted once.
- *`--json`*: `{mode, state, events, resolved, text}` (daily: `routines`, `owner_commands`).

**Delivering it without a model.** [`examples/scheduler/hermes-digest.py`](../examples/scheduler/hermes-digest.py) is a Hermes `no_agent` job: it runs `roadctl digest --all --since-state telegram` (every few minutes) or `--daily` (once a day; the owner chooses the time and sets it in the Hermes job), prints the text and nothing else (one short line when roadctl itself failed, never a raw output). Telegram is the main channel and VK the reserve: both are configured in Hermes (a job per channel with its own `STATE_NAME`, so that each is told on its own); roadctl does not know either. The text is plain, short and needs no markup.

**Format change (roadctl 0.5.0).** New: the routine header key `notify`; the summary form of the Log line of a routine and of a REPORT line (new labels, always with the trailer); the `summary` key of `config.json`; `roadctl digest`, `roadctl run done`, the flags above. An older copy warns about the unknown key `notify` (and ignores it), reads the summary form as plain text and does not know `summary: required`; so a board that uses `notify` or `"summary": "required"` sets `"requires": "0.5.0"` in `board/config.json` first (and installs 0.5.0 on every machine that runs its routines). `last_result` keeps `ok`, `escalated` and `failed`; a board that uses none of it needs nothing.

## Run supervisor

`roadctl supervise (--routine ID | --card ID | --orchestrator) --as AGENT [--timeout 30m] [--stdin] [--model NAME] [--detach] [--board DIR] -- COMMAND [ARGS...]` runs COMMAND as **one supervised run** and makes sure it is not duplicated, does not hang for ever and does not lose its result, whatever the agent is. It starts no model by itself: COMMAND is yours (`claude -p ...`, a script of a scheduler). POSIX only (WSL included); on native Windows it refuses with an explanation and exit 2. Everything after `--` is the command line, never roadctl flags. `--stdin` gives the command this process's stdin (the prompt from [`roadctl launch`](#launch-description); without it the command has none, also with `--detach`, where the pipe is inherited by the detached supervisor), and `--model NAME` records the actual model of a card or orchestrator run (a routine's model is its header), so a later attempt of the card keeps the models it really ran under. It needs a board for `--routine` and `--card` (`--board DIR`, `--project NAME` or the current directory); `--orchestrator` takes the agent from `--as`.

- **One run per key, for the whole run.** The key is a routine of a project (`routine:PROJECT/ID`), a card (`task:PROJECT/ID`) or the orchestrator of an agent (`orchestrator:-/AGENT`). The lock is a file `supervise-<key>.lock` in the machine state directory, taken with the same helper as the other locks (exclusive create; no `flock`); it holds the pid of the supervisor and its pulse is the modification time, touched every 30 seconds. A second `supervise` of the key prints `busy` and exits **5** (the same code as a busy `tick`) and writes a `skipped` record with the reason `busy` to the run ledger, instead of exiting 0 silently. A lock whose supervisor is dead is taken at once, not after 10 minutes; a lock with a live pid and a pulse older than 10 minutes is taken over by age.
- **Checked again under the lock.** Between `tick` and `supervise` the decision may change: under the lock the supervisor checks the pause (exit **6**), the local back-off below, the board's `requires` and, for a routine, "allowed and due" with the same rules as `tick` (routine switched off, outside hours, not approved, not due any more): then it starts nothing and exits **4**.
- **The run.** The supervisor begins the run in the run ledger (`source: supervisor`; ROADCTL_RUN_ID is given to the command, so `routine done`, `report` and `run done` find it), starts COMMAND in a **new process group** (its stdin is empty), and ends the run with the outcome. A command that outlives `--timeout` (default: the routine's `timeout:`, else 2 hours; `90s`, `30m`, `2h`, `1d`) gets TERM, then KILL, for its whole group, and the outcome is `timeout` (exit 7). Whatever the command leaves in its group dies with it. TERM, INT or HUP sent to the supervisor itself passes TERM to the group (then KILL) and the outcome is `aborted` (exit 8), the lock is released.
- **The result.** The supervisor learns that the command reported by the run ledger (an end record with this `run_id`), not by comparing text: then that outcome stands (`ok` and `escalated` exit 0, `failed` exit 1). A command that ends **without** a result is `failed: no result` (reason `no result`, the exit code or signal in the problem text); a `timeout` and an `aborted` run likewise have no result. For a **routine** the supervisor then writes the result to the routine file itself, through the same code and the same module hooks as `routine done` (`last_run`, `last_result: failed`, a Log line, committed and pushed the same way; a hook that refuses, for example an approval check, means nothing is written, the run's reason in the ledger says `the routine file was not written (refused: ...)` and the local back-off below applies), so the next `tick` does not offer the routine again at once: `did` is the last checkpoint (`roadctl run note`) or "no data", `problems` the reason, and the line ends with `src=supervisor` (`[run=ID dur=Ns host=H src=supervisor]`). For a card or the orchestrator the record stays in the ledger (the digest delivers it). Exit codes of the command itself are kept in the record's `usage`.
- **Its own log.** `run-logs/<run_id>.log` in the state directory: mode 0600 (the directory 0700), at most 1 MB (the rest of the output is dropped), a header (start, run, key, timeout, command) and a footer (end, exit or signal, duration), removed after 30 days (at the next run). The last 600 characters of the output go to the ledger record (`usage.tail`). Optional adapter: when the command line has `--output-format json` (`claude -p`), the last JSON line gives `usage.claude`: exit code, `session_id`, turns, `is_error`, subtype (for example `max_turns`) and cost; missing data is `unknown` and never makes a run a failure by itself.
- **`--detach`.** Prints `run_id=ID` (or JSON with `--json`) once the command is running and returns 0; the supervisor goes on in a session of its own, so a dropped ssh does not stop it. A refusal (busy, paused, bad arguments) is the exit code of the parent.
- **A killed supervisor (orphan).** After `kill -9` of the supervisor the lock keeps the pid and a sidecar `supervise-<key>.lock.run` keeps the process group of the command. The next `supervise` finds the orphan: the group is **alive** -> `busy` (exit 5; when the run's own deadline has passed the group is finished off instead); the group is **gone** -> the lock is taken at once, the old run is marked `crashed`, and for a routine a `failed` result (`src=supervisor`) is written. If that cannot be written, or the run was not a routine, a **local back-off** keeps the key quiet: no start and no `RUN` from `tick` for 10, then 20, then 40 minutes after the first, second and third such run in a row; after the third a local **stop** (a `supervise-stop` problem in the record, so the digest tells it at once) until `roadctl supervise <the same selector> --as AGENT --reset`. A run that gets to its end on its own clears the count. `roadctl tick` does **not** recover: it writes no board file, takes no supervisor lock and pushes nothing for this (its own records in the run ledger, such as marking an overdue unsupervised run `crashed` and the folded skips, are written as before, P5.1). When a routine is offered while a supervised run of it is still open in the ledger and nothing holds its lock, its `RUN` line ends with `(recover: supervised run ID died)` (`routine.recover` in `--json`), so the text changes once and a monitor starts the supervisor; `supervise` then does the recovery under its own lock, after it has checked the board's `requires`. The lock is taken over under the takeover guard of the shared helper, so two processes that see the same dead lock cannot both take it, and a lock file without readable content is never taken for a dead owner (it is busy until it is stale by age). This is the only protection against a repeat on every tick until the outcome policy (`HOLD`, P5.4) exists.
- **`tick` and the live run.** `tick`, `routine list` and `status` say `would not run: a supervised run is live` for a routine whose run is live, so `tick` offers no `RUN`; once the run has finished and the routine is due again, it is offered again.
- **Examples.** [`examples/scheduler/supervised-routine.sh`](../examples/scheduler/supervised-routine.sh) is a scheduler job (a Hermes `no_agent` script, cron) that asks `tick` and runs the model under `supervise`; the model is never started inside a Hermes job.

| Exit code | Meaning |
| --- | --- |
| 0 | ok: the run ended `ok` or `escalated` (or `--detach` started it, or `--reset` cleared a key) |
| 1 | failed: the command reported `failed`, or ended without a result (`failed: no result`), or could not start |
| 2 | usage error, unknown routine or card, the run ledger is not usable, native Windows |
| 4 | not started: not allowed or not due any more, `requires` (the board's, or the board does not declare 0.6.0), local back-off or stop |
| 5 | busy: another run of the key is live (also an orphan whose command still runs) |
| 6 | paused: the owner's pause (`roadctl pause`) is in force |
| 7 | timeout: the command outlived `--timeout` and was killed |
| 8 | aborted: TERM, INT or HUP to the supervisor, or `pause --now` |

**What a card gets.** What a card's run did before it ended without a result (`failed: no result`, `timeout`, `aborted`, or a dead supervisor) is unknown, so `supervise --card` refuses to run that card again (exit 4) until `roadctl supervise --card ID --as AGENT --reset`; the owner or the orchestrator looks first. A run that reported itself is a known outcome and blocks nothing.

**Requires.** A routine's board must say `"requires": "0.6.0"` (or newer) in `board/config.json` before `supervise --routine` starts anything (exit 4 with the reason), because the Log line trailer ` src=supervisor` is a format change that older copies do not read. Boards that are never supervised are unchanged.

**What is checked, and when it cannot be saved.** An open run that was begun by `run begin` or a claim (not by a supervisor) is not taken over: `busy`, because nothing proves its executor has stopped. A `supervise.state.json` that cannot be read stops every start of a routine of a board that declares `requires` 0.6.0 (fail closed; boards that cannot be supervised are not touched) until `--reset` rewrites it; a running command's end never rewrites such a file. When a stop (a card's, or a routine's back-off) cannot be saved, the lock is kept with a `stop_unsaved` marker and nobody takes it until `--reset`. When the end of a run, its back-off or its stop cannot be saved the exit code is an error and the message says `WARNING: ...`; an end that is missing makes the next `supervise` or `tick` mark the run crashed. An error after the command has started kills its process group, and a delayed KILL is cancelled once the group is confirmed gone.

The state files are `supervise-<key>.lock`, its `.run` sidecar, `run-logs/` and `supervise.state.json` (the local back-off), all in `${XDG_STATE_HOME:-~/.local/state}/road-map-journal/`, never in git. For tests, the real-time mechanics can be shortened with `ROADCTL_SUPERVISE_HEARTBEAT_MS` (30000), `ROADCTL_SUPERVISE_POLL_MS` (1000, the look for `pause --now`), `ROADCTL_SUPERVISE_GRACE_MS` (5000, TERM to KILL) and `ROADCTL_SUPERVISE_LOG_LIMIT` (1048576), `ROADCTL_SUPERVISE_SIGLOG` (a file that gets one line per signal sent to a group) and `ROADCTL_SUPERVISE_FAULT=after-spawn` (an injected error); the times in the ledger follow `ROADCTL_NOW`.

**Known limitations.** (1) A SIGKILL of the supervisor in the instant between starting the command and writing its process-group id leaves a group nobody can find; the next `supervise` takes the lock for dead. (2) `run begin`/claim runs of another executor that are past their own deadline are marked `crashed` by the run ledger (P5.1) when a supervisor begins its run, so an executor that is still alive can run beside the command; both wait for a liveness proof for unsupervised runs (P5.4, P5.21). (3) If the takeover guard stays busy when a run ends, no `stop_unsaved` marker is set, so a stop that could not be saved may be lost once the supervisor exits. (4) The shared lock helper (`acquireLock`) still removes a takeover guard older than 5 seconds; the supervisor's own guard handling removes one only when its owner is dead or it is older than 10 minutes.

**Format change (roadctl 0.6.0).** New: the supervisor's Log line trailer ` src=supervisor` (`[run=ID dur=Ns host=H src=supervisor]`), the command `supervise`, `pause --now` (a `now` key in `pause.json`), the module hook text `a supervised run is live`, the `routine.recover` field of a RUN item in `tick --json` (and ` (recover: ...)` in its text), and the module api `routineDoneWithHooks` (the whole of `routine done`, hooks included). An older copy reads the new trailer as plain text of the line (the strict trailer expression does not match, so it shows no run id for that line), and does not know `supervise`; so a board whose routines are run by a supervisor sets `"requires": "0.6.0"` in `board/config.json` first (and installs 0.6.0 on every machine that runs them). `last_result` keeps `ok`, `escalated` and `failed` (a supervised `timeout` or `aborted` is `failed` in the routine file and has its own outcome in the local ledger).

## Launch description

`roadctl routine launch <id> [--json]` (and `roadctl launch --card ID --profile NAME [--json]`, hidden from the overview) is the one source of the command that starts an agent. It is read only and **starts nothing**: a scheduler, the conductor service (P5.25) or any other launcher reads the description and runs it, normally under [`supervise`](#run-supervisor). It prints:

- `argv`: the command, with the model, the settings file, the list of MCP servers and the turn cap filled in; the prompt is **never** in argv (it can be long and shows in `ps`);
- `stdin`: the prompt, which the launcher writes to the command's standard input (`supervise --stdin` passes it on);
- `env`: the **names** of the environment variables the launcher passes through, never their values (`doctor` treats them the same way);
- `timeout_s`: for a routine, its own `timeout` (the cap `supervise` takes by default), and `max_turns`;
- `supervise_argv`: the arguments for `roadctl supervise`, ending in `--`, so the launcher appends `argv`; the time cap in it is the one `supervise` enforces. `reasons`: why the routine would not run now (empty when it would).

**Where the command comes from.** The rule: **`roadctl` does not run a command taken from git.** Launch templates live only in the local file `${XDG_CONFIG_HOME:-~/.config}/road-map-journal/conductor.json` of the machine. A routine on the board gives only data under the approval hash (agent, model, `timeout`; later `mcp:` and `allow:`). A `launch` string in the registry (a file in git that agents write) is ignored with a warning. The file is refused when it lies inside a git work tree, belongs to another user or is writable by group or others, and without a template for the agent the command refuses with a hint and exit 1: nothing is started "somehow".

```json
{
  "version": 1,
  "templates": {
    "claude-code": {
      "argv": ["claude", "-p", "--model", "{model}", "--strict-mcp-config", "--mcp-config", "{mcp_config}", "--settings", "{settings}", "--max-turns", "{max_turns}", "--output-format", "json"],
      "mcp_config": "/home/me/.config/road-map-journal/mcp-routines.json",
      "settings": "/home/me/.config/road-map-journal/claude-routines.json",
      "max_turns": 30,
      "env": ["HOME"]
    }
  },
  "profiles": {
    "worker": { "agent": "claude-code@home-wsl", "model": "claude-sonnet-5-5", "attempt": { "timeout": "30m", "turns": 40 }, "card": { "timeout": "2h" }, "strong": "strong" },
    "strong": { "agent": "claude-code@home-wsl", "model": "claude-opus-5-5", "attempt": { "timeout": "45m" } }
  }
}
```

A template is found under the agent's full name, else under its host (`claude-code`). The only placeholders are `{model}`, `{mcp_config}`, `{settings}` and `{max_turns}` (`{prompt}` is refused). `mcp_config` is a file with only the MCP servers the run needs, passed with `--strict-mcp-config`: the tools in the context are the main cost of a run, so a strict list saves most without any accounting. Paths are absolute. This change enables nothing: no template, profile or limit exists until the owner writes it.

**Cards and a second attempt.** A profile gives the agent, the model, an attempt limit (`attempt.timeout`, required; `attempt.turns`), the limit of the whole card (`card.timeout`, `card.turns`) and, optionally, the one stronger profile it permits (`strong`). The time cap of a first attempt is the smaller of the attempt and the card limit. A later attempt (a profile that another profile permits as `strong`, the one whose model matches the first attempt's) gets only what the run ledger can measure: **remaining = card limit minus the sum of the durations of the earlier runs of the card**; turns are **not measured** (the ledger keeps them only for a run the supervisor had to end itself, whose outcome is unknown anyway), so a card with a `card.turns` limit allows the first attempt only and refuses the second. A change of model resets nothing, and the description lists the actual `previous` runs and `models`. It is refused (exit 1, never guessed) while a run of the card is live or its outcome is unknown (crashed, timeout, aborted, or a failure the supervisor wrote because nothing was reported), when the card has no time limit, when the time used cannot be measured or a turn limit of the whole card is set, and when the limit is used up. Units: time is wall-clock seconds of runs under `supervise`; turns are what the CLI counts and are not comparable between CLIs. Without limits or a measurable remainder, escalation is not offered (the `escalation` field of the first attempt says why). Whether and when to escalate is the conductor's policy (P5.25, P5.21), not decided here. These are the time and turn limits and the subscription reserves that exist today; money accounting and the daily cap stay the deferred P5.20, and a list-price estimate is not spending.

**Hermes.** Restricting the tools of a Hermes job is a setting of that Hermes job itself (its own tool or skill set); `roadctl` documents it and prints no argv for it unless a template for `hermes` exists in `conductor.json`.

`doctor` checks the file (`launch-templates`). Exit codes: 0 described, 1 refused, 2 usage error, invalid file, unknown routine or card, or no board.

**Service clone (P5.29).** Besides `templates` and `profiles`, `conductor.json` may have `"service": { "workspace": "/abs/path/of/the/service/clone", "owner_clone": "/abs/path/of/the/owner/clone" }` (absolute paths; `owner_clone` is optional). Only `doctor` reads it for now (`service-clone`, see [Synchronization with the server](#synchronization-with-the-server)); the conductor service (P5.25) will start in that clone.

**Format.** `conductor.json` is local to a machine, not part of a board: no card, routine or `config.json` key was added, so no board needs a new `requires`. `VERSION` is 0.7.0 so that a launcher can require a copy that has `routine launch`, `supervise --stdin` and `--model`.

## Plan check (`roadctl plan check`, P5.34 early slice)

`roadctl plan check FILE [--json]` reads one **proposal file** (JSON) and says what would become of each card. It is read only: no model, no network, no write, no start (hidden from the overview, like `stats`). The same file is meant for a collaborative session (L2), a future planner run on a mandate (L3) and a future request from the channel (P5.36): one format, no second planner. Writing the cards (`plan apply`), inbox, milestones as records and the planner launcher are not built; the owner creates the cards with the existing `new` and fills them from the file. A walk-through for the owner: [plan-check-runbook.md](plan-check-runbook.md).

```text
{ "plan": 1, "source": "collab",                       // collab | mandate | channel (informational)
  "cards": [ { "key": "c1", "title": "...", "goal": "...",
               "criteria": [ { "id": "a1", "text": "...", "check": "test: node --test scripts/x.test.mjs" } ],
               "kind": "fix", "size": "S",              // mandate kinds, S | M | L
               "env": "Local", "role": "worker", "needs": ["data:x"],
               "effects": "scripts/ only", "stop_conditions": "stop on a red test",
               "depends_on": ["c0", "P5.2"],            // keys of this file or existing card ids
               "roadmap": "P5.34", "mandate_goal": "G1" } ],   // one of the two is required
  "milestones": [ { "title": "...", "cards": ["c1"], "meaning": "...", "goal_check": "how the overall goal is checked" } ] }
```

A check method is `test`, `command`, `inspect`, `review` or `owner`, then `:` and what is run or looked at. Per card the result is **refused** (a reason from the table), **proposed** (valid, grants nothing) or **in-mandate** (see below). The file is `proposed` as a whole when no card is refused (exit 0), else `refused` (exit 1). `--json` has `cards[]` (`key`, `title`, `result`, `reasons`, `notes`), `file_reasons`, `limit`, `milestones`, `mandate`, `summary` and the table `reasons_table`; the text output ends with the table of the reasons that occurred.

| Reason | Refused when |
| --- | --- |
| `bad-file` | not JSON, not an object, `plan` is not 1, or `cards` is not a list |
| `no-goal` | the card has no goal |
| `no-criterion` | no criterion, or none with a check method written |
| `no-link` | neither a ROADMAP item (`roadmap`, form only) nor a `mandate_goal` |
| `unknown-goal` | the `mandate_goal` is not in the mandate Goals |
| `over-limit` | the card is beyond `plan_max_cards` of the mandate (built-in default 5): it would not be recorded |
| `duplicate`, `duplicate-in-file` | the same normalised title as an existing card (or an earlier card of the file), or the same mandate goal with the same criteria |
| `unknown-dependency` | `depends_on` names neither an existing card nor a card of the file |
| `dependency-cycle` | the card is in a cycle, or depends on itself |
| `bad-milestone` | a milestone lacks title, meaning, `goal_check` or cards, or names a card that is neither in the file nor on the board |

**What is not a refusal.** A kind or size outside the mandate (`kinds`, `max_size`), no kind or size, an unknown size (it is never turned into S), and a missing, template (`TBD`, `(...)`, `none`) or unknown `env`, `role`, `effects`, `stop_conditions` or check method leave a valid proposal with a note. None of it is ever permission. **Without a mandate, at L1 or L2, or with a mandate that is not approved, was changed after approval or is malformed, no card is better than "proposed"** (the card path stays `approve` by the owner). Only an approved, unchanged L3 or L4 mandate gives "in-mandate", and only for a card whose kind and size are inside it, that links a mandate goal and has a defined environment (the registry is consulted when it describes environments and roles), role, effects, stop conditions and check methods. "In-mandate" is not ready and not taken: the full admission (dependencies done, the budget, the labelled Plan lines) is made at START and `delegate`, and `by_mandate` is written there, never by the check.

**What the check does not judge.** Form and mechanical limits only: it does not know whether a size, an effect or a criterion is true, whether a ROADMAP item exists, or whether `## Forbidden` is respected; that stays with the owner's review and the check afterwards. A milestone is checked for form (its own `goal_check` is required, since closed cards alone do not prove the overall goal); recording and checking it is stage 3.

**Size and splitting.** S, M and L are a rubric for the author (S one bounded, clear result; M one goal across components, with a reason it cannot be split; L composite, split before unattended work), not a count of criteria and not a safety class. A simple task stays one card. A big one is split by results that can each be checked, with `depends_on`, without duplicating existing cards and without artificial pieces. Parallel work gets its change boundaries in the Delegation section; there is no file-overlap analysis or scoring. **Size never chooses a model**: the executor comes from the profile, suitability and availability (`roadctl candidates`, P5.23), and `tick` and `delegate` do not choose it.

## Autonomy metrics (`roadctl stats`, P5.27)

Numbers for the owner who decides which kinds of work may go without confirmation. `roadctl stats [--since DATE] [--accept-from DATE] [--all] [--json]` counts them; it reads and writes nothing (no board file, no state file, no git), and a channel only shows what it printed. Sources: the Log lines of routines and cards in git (`RUN`, `REPORT`, `RETURNED`, `ACCEPTED`, `approved by mandate`, the `accepted` header), this machine's run ledger (the runs the Log does not know: crashed, timeout, aborted, skipped; durations), the audit of owner commands (`owner-commands.jsonl`, P5.3) plus the owner's traces in git (`approved`, `accepted`, `routine on|off`), and the mandate (P5.33). The runs of another machine arrive through git: `roadctl pull` first. Days are compared, never times: the Log has a date only.

**Without the owner** (the definition behind `autonomy`): a run counts as without the owner when (1) it ended `ok`, (2) it asked nothing (no `ask`, so no `needs_owner`), and (3) the owner ran no command on the same routine or card after it, up to the next run of that routine or card (a command on the day of the next run counts for the earlier run). A run that escalated, failed, crashed, timed out or was aborted is never without the owner. A refused command (an unattended run tried an owner command) is not the owner's command.

`--json` (the schema is `scripts/testkit/stats-schema.mjs`; a reader tolerates extra fields, the not yet counted ones are already there as `null` or empty):

| Field | Meaning |
|---|---|
| `stats`, `generated`, `since`, `accept_from`, `projects` | schema version (1), the time of the report, the flags, the boards counted |
| `sources` | how many runs came from `board_logs` and from the `local_runs` ledger, and how many owner commands from the `owner_audit` and from `owner_git`; without a ledger or an audit file these are 0 and the numbers rest on the Log |
| `runs` | `total` finished runs and their outcomes (`ok`, `escalated`, `failed`, `crashed`, `timeout`, `aborted`), `skipped` (this machine: runs per reason), `duration_s` (`n`, `median`, `p90`: the time of a run in seconds, where the run line or the ledger has it) |
| `autonomy` | `runs`, `without_owner` and their `share` (null without runs); `by_routine` (`project/id` of a routine) and `by_track` (a card's track prefix of its id, `P5` for `P5.27`, or `orchestrator`): the same three numbers per kind of work |
| `owner_wait.review_to_acceptance` | the wait for acceptance: from the day a card reached review (its last `ACCEPTED` or `REPORT` Log line) to its `accepted` date: `n`, `median_days`, `p90_days`; `open` cards still in review with `open_oldest_days`; `unknown_start` cards with no such Log line (left out). `--accept-from DATE`: an acceptance before that date is left out and the wait counts from that date at the earliest; use it when a pile of cards waits in review by decision (the date of the release candidate); without it all history counts |
| `owner_wait.question_to_answer` | question to answer, `n`, `median_days`, `p90_days`: empty (0, null) until the questions of P5.24 exist |
| `escalations` | `escalated_runs`, `asks` (runs that asked the owner something), `top_problems` (the ten most frequent `--problem` keys with their kind and count) |
| `returns` | `returned` (`RETURNED` Log lines), `cards` returned, `task_reports` and `share_of_reports` |
| `mandate` | `boards` (project, level, state of its mandate; `none` without a file), `started_by_mandate` (`n` and the `cards` taken by `approved by mandate` Log lines); `proposed` (P5.34), `undone_share` and `blocking_questions_per_week` (P5.24), `milestone_returns` (P5.35) are `null` until those parts exist |

`--since DATE` counts only runs, returns, acceptances and owner commands from that day (the mandate's started cards too). With no board data, no ledger and no audit, every count is 0 and every share `null`; the command still exits 0.

## Instruction blocks

`instructions-install --claude --codex` adds or refreshes one marked block (`<!-- ROADMAP-JOURNAL:START -->` ... `:END -->`) in the user-level `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md`, so that every session in every project knows about the skill, keeps existing plans where they are, creates new boards in the central workspace and finds the helper. Text outside the block is never changed; a file that is a symlink is not edited (the block is printed instead); a backup is made before writing; `instructions-uninstall` removes the block. Where the workspace is not under `~/projects/agent-workspace` or `~/Projects/agent-workspace` (for example on Windows), put its path on the first line of `~/.local/share/road-map-journal/workspace` or set `ROADCTL_WORKSPACE`.
