# roadctl

Optional helper for a board-format project (see [board-spec.md](board-spec.md)). The core is one file, [`scripts/roadctl.mjs`](../scripts/roadctl.mjs); newer parts are small modules in [`scripts/roadctl/`](../scripts/roadctl/) next to it (see [developing-roadctl.md](developing-roadctl.md)). Node standard library only (tests pass on Node 20, 24 and 26). It is **not installed with the skill**: copy the file into your project (for example `tools/roadctl.mjs`) and keep its version line; copy the `scripts/roadctl/` folder next to it (without `*.test.mjs`) to get the module commands, a lone file runs the built-in commands only. For hooks at user level (Codex, Hermes) it needs one stable path: `node scripts/update-installed.mjs --roadctl --apply` installs or refreshes `~/.local/share/road-map-journal/roadctl.mjs`. Files stay the source of truth; the skill and a person can edit cards by hand without it. It never sets `approved` on its own initiative and only checks that references exist, not that evidence is true.

Not sure where to start? `roadctl help` prints an overview grouped by task (what each command is for, and whether it only reads, writes board files or uses git), a quick start for all projects, one project and one card, and the boundaries for agents. `roadctl help <command>` (or `roadctl <command> --help`) gives purpose, usage, flags, examples, what the command changes and its exit codes; `--help` never runs the command and writes nothing.

Global flags: `--board <dir>` (default: search upwards for `board/config.json`, then the known boards, see [Finding the board](#finding-the-board)), `--project NAME` (a known board by project or `match` name), `--workspace DIR` (or `ROADCTL_WORKSPACE`), `--date YYYY-MM-DD`. Exit codes: 0 ok, 1 findings or refusal, 2 usage error, 3 limits unknown (only `limits --check`).

## Finding the board

Which board a command works on is decided in this order (the first hit wins):

1. `--board DIR`, or `--project NAME`: a known board by project name or `match` name (an unknown name exits 2 and lists the known projects).
2. The project board: `board/config.json` in the current directory or above it.
3. A known board whose **project folder name** (the folder above its `board/`) or one of its `match` names equals the name of the current directory or of an ancestor (case-insensitive, `_` and `-` equal). The central workspace is looked at first, then the user list.
4. None: commands exit 2 ("no board found ..."); `where` exits 1.

**Known boards** are the boards of the central workspace (`<workspace>/projects/<name>/board`, the first workspace root: `ROADCTL_WORKSPACE`, the pointer file, `~/projects/agent-workspace`) plus the **user list** for people without a central workspace: `${XDG_CONFIG_HOME:-~/.config}/road-map-journal/boards`, one absolute board directory per line, `#` comments. The name of a listed board is its project folder name. Everything that iterates over all boards (`--all` of `lint`, `status`, `list`, `next`, `tasks`, `tick`, `autonomy`; `--project`; the listing of `where`; discovery by folder name) uses the workspace boards and the listed ones together, deduplicated by real path (a symlink to a board is the same board). A project board in the project folder still wins over both.

`roadctl boards [list] [--json]` shows them (name, `workspace` or `list`, directory, `match` names; a listed directory that is gone is marked `MISSING` and not used). `roadctl boards add [dir]` records a board (default: the one found from the current directory; already known paths are not added twice) and `roadctl boards remove <dir|name>` forgets one (comments and other lines of the file stay; an ambiguous name is refused). Both only edit that one file; no board file changes.

**`roadctl where [path]`** prints the board for `path` (default: the current directory), so a session that started in a parent folder of several repositories can ask for the repository it actually works on. When nothing is found it exits 1, prints nothing on stdout and writes to stderr `no board for <dir>`, the known boards (name, directory, `match` names) and the ways out: `--project NAME`, `--board DIR`, adding the folder name to `match` in the board's `config.json`, or `roadctl boards add`.

**Registry lookup** (executors, limits, roles): `ROADCTL_REGISTRY` (a file that does not exist then means no registry) -> `<workspace>/agents/registry.json` -> `${XDG_CONFIG_HOME:-~/.config}/road-map-journal/registry.json`. The first that exists is used.

## Overview without an agent

`status`, `list` and `next` only read the board files; they need no model and write nothing. `--all` covers every known board: the boards of the central workspace (the first workspace root found) and the user list (see [Finding the board](#finding-the-board)), without duplicates, as for `lint --all`. `status` prints one row per project (counts per status, `oldest as_of` among doing, review and blocked cards, lint errors and warnings, whether autonomy is `on` or `off`) and one line per doing card. `next` is a view, not a decision: `ready` means defined, **not** permission to start, so a ready card without `approved` is marked as needing the owner's approval, and a ready card is "waiting" until every id in `depends_on` is `done`. Card titles in text output are sanitized like in `brief`; `--json` returns the raw values for scripts. What these commands cannot tell is whether a status matches reality: that still needs a person or an agent reading the evidence. How far a board is behind its server is not shown yet (P3.2).

## Synchronization with the server

Plans live in a git repository (a central workspace, or the project). `pull` and `save` keep a board in step with other agents and machines without anyone typing git commands.

- `pull`: `git fetch`, then `git rebase --autostash` on the upstream. Uncommitted changes are kept. If the rebase conflicts **only** in generated `BOARD.md` files they are regenerated from the merged cards and the rebase continues; any other conflict aborts the rebase, leaves the tree as it was and reports the files (status `conflict`): two agents edited the same text, so a person decides. If the server cannot be reached the status is `offline` and work continues on the local state.
- `save ["message"]`: regenerates a stale `BOARD.md`, runs `lint` (errors refuse the save, nothing is committed), commits **only the board's paths** (the project folder `projects/<name>` in a central workspace, `board/` in a project; other changed or staged files are left alone and counted in the message), rebases on the upstream like `pull`, lints the merged result, pushes. It never forces. If someone pushed in between it integrates once more and retries. If the server is unreachable the commit stays local (`saved-local`, exit 0) and the next `save` pushes it. It refuses to push when unpushed commits touch paths outside the board (`foreign-commits`), and when the merged board has lint errors (`lint-after-merge`). Without a message the commit is `board <project>: update <card ids>`.
- Statuses that are not failures (exit 0): `up-to-date`, `pulled`, `offline`, `no-remote`, `saved-local`, `nothing-to-save`, `pushed`. Everything else exits 1 with the reason.
- `status` shows an `origin` column (`in sync`, `behind N`, `ahead N`, `N uncommitted`, `no remote`) from the last known state; `status --fetch` asks the server first.
- `log`, `new` and `review` print a warning to stderr when the board is known to be behind origin (no network is used for that check).
- Network limits: `ROADCTL_GIT_TIMEOUT_MS` (default 15000); git never prompts (`GIT_TERMINAL_PROMPT=0`, ssh `BatchMode`).

**Autosync (opt-in).** Hooks keep their rule of never changing anything unless the owner opts in, with `"autosync": true` in `board/config.json` (shared by every host and agent that uses this board) or `ROADCTL_AUTOSYNC=1` (`0` forces it off). Then the `SessionStart` hook runs `pull` before the brief, and the `Stop` hook runs `save` when the board has uncommitted changes or unpushed commits. Without autosync `SessionStart` only fetches (4 second limit, `ROADCTL_NO_FETCH=1` disables it) and adds one line to the brief ("behind origin by N commit(s)", "N local commit(s) not pushed", "origin unreachable", "up to date"). A successful autosave is silent; a problem (conflict, lint error, rejected push) is passed to the agent once so it can tell the owner. The reminder check runs before the autosave, and a successful autosave records the card's Log state so the reminder is not triggered for work that was already written down. Hooks have short timeouts (Codex kills a hook after 10 seconds); a kill during `fetch` or `push` is harmless, and the rebase itself is local and fast.

## Hooks

Hooks are reinforcement, never the only mechanism, and they never change statuses, set `approved`, block an agent or fail a session (an internal error becomes a no-op).

- `session-start`: prints the brief as `additionalContext`. Also useful after compaction.
- `pre-compact`: asks that the active card, open criteria and decisions be kept in the summary.
- `stop`: when exactly one card is `doing`, the working tree has changes outside the board and the board was not touched, it reminds the agent **once** until the card's Log changes (a marker file in `.git` records it). It stays silent when `stop_hook_active` is set, with zero or several `doing` cards, and outside git. Claude Code gets `additionalContext`; with `--host codex` it answers `{"decision":"block","reason":...}`, which Codex turns into one continuation prompt.
- `hermes-pre-llm`: Hermes only uses the return value of `pre_llm_call`, so this one hook gives the brief on the first turn of a session and the same one-time reminder on a later turn (`{"context": ...}`). Hermes hooks see only the session's working directory, so they work when Hermes runs inside the project.
- `pre-commit` (git): runs `lint`; errors block the commit, warnings never do.

Installers (dry run by default, backup before writing, existing hooks kept, idempotent, undone by `hook-uninstall`):

- `--claude`: the three Claude Code hooks into the project's **local, uncommitted** `.claude/settings.local.json`; with `--user` into `~/.claude/settings.json` (or `$CLAUDE_CONFIG_DIR`) instead, which is the right place when boards live in a central workspace. The hooks are silent in directories without a board.
- `--codex`: `SessionStart` (all sources, so it also runs after compaction) and `Stop` into the user-level `~/.codex/hooks.json` (or `$CODEX_HOME`), with `command` (plus `commandWindows` when installed from Windows) and a 10 second timeout. User level is used because the hooks are silent outside board projects and a project `.codex/hooks.json` would be committed. Codex does not run a new hook until you review and trust it in `/hooks`; roadctl never edits the trust state. `PreCompact` is not installed for Codex because Codex ignores its output.
- `--hermes`: one marked block (`# roadctl-managed begin/end`) appended to Hermes `config.yaml`; it refuses to edit a file that already has a top-level `hooks:` key and prints the entry to merge by hand. Hermes asks you to approve a new hook the first time it sees it (`hermes hooks list` shows the status; non-interactive runs need `--accept-hooks`, `HERMES_ACCEPT_HOOKS=1` or `hooks_auto_accept`, which roadctl does not set).
- `--git`: writes `.git/hooks/pre-commit` only if none exists; an existing foreign hook is never touched. With `--all` (run inside the workspace repository) the hook lints every board of the workspace.

## Delegation

Any agent or script can hand a card (or some of its criteria) to another executor and take the result back; the delegation lives in the card (`delegate` and `claim` headers, optional `## Delegation` section, format in [board-spec.md](board-spec.md#delegation)). One active delegation per card; parallel work means separate cards with `depends_on`.

1. `delegate <id> --to worker --by me@host [--host codex] [--criteria a2,a3] [--accept by]` refuses without an `approved` record, on `done` or `dropped` cards, and when a delegation is already active. It adds a Delegation template to fill in (allowed changes, checks, stop conditions, budget, report format) and a Log line. Fill it in, then `save`, so executors see it.
2. The executor is started by the delegating agent (push: a Claude Code subagent `road-worker`, `codex exec`, Hermes's own delegation) or finds work itself (pull: `roadctl pull`, `roadctl tasks --for me@host`). Either way it runs `claim`, works, and ends with `report`; both publish themselves (see below), so the delegating side sees them after a `pull`.
3. `accept` or `return` by the allowed acceptor, then `roadctl save` to publish (these two only edit the card, because the acceptor is typically an orchestrator that saves its board work anyway). The result is data to verify; the owner alone marks the card `done`.
4. `undelegate` withdraws a delegation that is no longer wanted.

`tasks` shows every delegation with its state (`OPEN`, `CLAIMED`, `EXPIRED` when `until` has passed, `REPORTED`); `--for AGENT` keeps what that agent may take now: open or expired, `to` equal to the agent or a role the agent has in the registry, and the host matching (`any` matches all). `brief`, `status` and `next` show counts and one line per delegation (`--json` adds a `delegations` list; `status --json` also `delegated`).

**Claim and races.** `claim` accepts only open or expired delegations the agent is eligible for, and refuses when a registry exists and the delegating agent (`by`) is not in it. It writes `claim` and `state=claimed` (lease `--lease`, default `2h`, at most `7d`), commits **only that card** (it refuses when the card file has other uncommitted changes: `save` first) and pushes. The push is the arbiter. If the server rejects it, `claim` integrates the upstream; when the same card was changed there (a conflict) or the merged card no longer shows this claim, the claim is **lost**: the local claim commit is removed, the card is left as the server has it, other work (including uncommitted changes) is kept, the message names the holder and the exit code is 1. If the server only has unrelated changes the rebase is clean and the claim wins. Outcomes: `claimed` (pushed, exclusive; exit 0), `claimed-local` (offline, no remote, no upstream, no git, or unpushed commits outside the board: the claim is local and **not yet exclusive**, another agent may take it; exit 0; the next `save` pushes it), `lost`, `refused`, `error` (exit 1). Run `pull` before `tasks` to see the server's state; without it a stale view only costs a lost claim, never two holders.

**Working directory of a claim.** `claim --workdir DIR` (an existing directory, stored as an absolute path) writes it into the header: `claim: <agent> at=... until=... workdir=/abs/path` (spaces and `%` in the path are percent-encoded, so the header stays one token per field; lint rule 17 checks that it is absolute). Autonomous code work belongs in its own git worktree, and the claim says which one. When an **expired** claim is taken over and the previous claim named a directory that exists on this machine and `git -C DIR status --porcelain` is not empty, `claim` prints a `WARNING` on stderr naming the directory and the previous holder (the claim still goes ahead and the exit code is unchanged; `--json` has the text in `warnings`), because the previous holder was probably interrupted (the PC was switched off) with unfinished changes that must be reconciled, not overwritten. `tick` marks such a `STALE` line with the stable suffix ` (workdir dirty)` (no counts and no paths in the text; the path and `workdir_dirty` are in `--json`), and the `--prompt` tells the orchestrator not to hand the card on before the changes are reconciled. A directory that is not on this machine, is not a git work tree or is clean gives neither warning nor suffix. `report`, `accept`, `return` and `undelegate` work as before and drop the claim with its `workdir`.

**Report publishes itself.** `report` (only the claimant) appends `REPORT: text` to the Log (up to 1500 characters), sets `state=reported`, removes the claim, then commits **only that card** and pushes it, like `claim`; it refuses when the card file has other uncommitted changes. Outcomes: `reported` (pushed; exit 0), `reported-local` (offline, no remote, no upstream, no git, or unpushed commits outside the board: the report is local and **not yet visible to others**, the next `save` pushes it; exit 0), `lost` (exit 1), `refused`, `error`. If the push is rejected it integrates the server's changes; when the card conflicts (for example the delegator added a Log line meanwhile) the report is applied again on the server's card as long as the claim there is still this agent's, and otherwise (the claim was taken over, for example after the lease expired) nothing is published, the card is left as the server has it and the command exits 1 with the holder named.

**Report and return text.** The text of `report`, `return` and `undelegate` goes into one Log line: control characters, newlines, backticks and angle brackets are removed, but `_ * [ ] #` are kept so paths and test names survive, and the cap is 1500 characters. Plain `roadctl log` cleans its text the same way (so names like `adcu_soc_sw!2576` survive) and caps it at 400. This is safe because only `show` prints Log text; the session brief, `status` and `next` inject header fields only (see [board-spec.md](board-spec.md)), and the entry is a single `- date [author] ...` line that cannot start a heading or a list item of its own.

**Who may accept or return.** `accept=by`: the delegating agent. `reviewer`: an agent with `can_accept: true` in the registry, or any agent that is not a script when there is no registry. An agent name: that agent. `owner`: nobody by command, the owner accepts by hand (`roadctl done` after review). A script (`cron:` or `script:` name, or `host: script` in the registry) can delegate and claim but never accepts or returns. `accept` removes `delegate` and `claim`, logs the acceptance and, when the card is `doing` and every criterion has evidence (`[x]` with an Evidence line or `[~]` with a reason), moves it to `review` with the same rules as `roadctl review`; otherwise the card stays as it was and the command prints which criteria lack evidence. `return` sets the state back to `open`, removes the claim and logs the reason. Both only edit the card: run `roadctl save` to publish.

**Withdrawing.** `undelegate <id> --by AGENT ["reason"]` removes `delegate` and `claim` and logs `UNDELEGATED`. Only the delegating agent (the `by` of the delegation; a script may withdraw its own) may; it works on an `open` delegation and on a `claimed` one whose lease has expired; any other state (a live claim, `reported`) needs `--force` and a reason. It only edits the card: run `roadctl save`.

**Registry (optional).** The file named by `ROADCTL_REGISTRY`, else `<workspace>/agents/registry.json`, else `${XDG_CONFIG_HOME:-~/.config}/road-map-journal/registry.json` (the first that exists, see [Finding the board](#finding-the-board)): `{"version": 1, "roles": {"worker": {"claude-code": "sonnet"}}, "agents": {"claude-code@home-wsl": {"host": "claude-code", "machine": "home-wsl", "roles": ["orchestrator", "worker", "reviewer"], "can_accept": true, "launch": "claude -p --model {model} \"{prompt}\""}}}`; a full example is in [`examples/agents-registry.example.json`](../examples/agents-registry.example.json). `roles` gives a model per host (used by `agents-install`); `agents` gives each agent's host, roles and `can_accept`; `launch` is a note for the delegating agent, roadctl never runs it. Without a registry everything works with fewer checks: a role in `to` is not verified (only the host is), `accept=reviewer` is open to any non-script agent and `claim` does not check `by`. The registry also carries optional `limits` and `providers` sections and a `provider` per agent (see [Limits and the owner's reserve](#limits-and-the-owners-reserve)). A registry that exists but is not valid JSON, or has a malformed `limits` or `providers` section, is an error (exit 2). Environment: `ROADCTL_NOW` (an ISO UTC time) replaces the clock, for tests.

**Subagents for Claude Code.** `agents-install --claude` writes `road-worker.md` (takes one delegation, follows the card's Delegation section, writes to the board only through `roadctl report`, never changes status, approvals or commits) and `road-reviewer.md` (verifies files and tests itself, runs `accept` or `return`, never `done`) into `~/.claude/agents` (or `--claude-home`), with the model from the registry roles (default `sonnet`). Dry run by default, backup before overwriting, idempotent, other files in that folder are never touched; `agents-uninstall` removes only files carrying the roadctl marker. For Codex and Hermes there is no file to install; see the delegating protocol in the skill's `references/long-running.md` (host commands there are examples to check against the host's current documentation).

## Limits and the owner's reserve

Before any automatic start (a scheduled run, a delegated worker) an agent or script should know how much of a provider's subscription is left and keep the owner's share. `roadctl limits` needs no board and no model of its own; it only needs the provider's own tool on `PATH`.

**Reserve.** The percentage that must **remain** for the owner: by default **10% of the weekly window and 15% of the five-hour window**. A provider is allowed only while every known window has *more* than the reserve left (remaining > reserve; exactly 15% left on a 15% reserve is already refused). A window with another name (`other`, for example a monthly one) uses the weekly reserve unless the reserve names `other`. Configure it in the registry (see [Delegation](#delegation) for where it is looked up):

```json
"limits": { "reserve": { "seven_day": 10, "five_hour": 15 }, "cache_minutes": 10 },
"providers": {
  "claude": { "kind": "subscription", "probe": "claude", "probe_model": "claude-haiku-5-5", "reserve": { "five_hour": 20 } },
  "codex":  { "kind": "subscription", "probe": "codex" },
  "kimi":   { "kind": "subscription", "probe": "command", "command": "kimi-limits --json" },
  "some-api": { "kind": "api" }
}
```

All of it is optional. Without a registry the built-in providers `claude` and `codex` work with the default reserve. A provider's own `reserve` overrides `limits.reserve` for that provider, key by key. An agent names its provider with `"provider": "<id>"` in the registry; without it the host decides (`claude-code` is provider `claude`, `codex` is `codex`, any other host is unknown). `kind: "api"` means pay-per-token: there are no subscription windows, `--check` answers 0 and the reserve does not apply. Providers may set `timeout_s` for their probe.

**Where the numbers come from** (normalized to windows `five_hour`, `seven_day` or `other`, each with `used_percent` and `resets_at`):

- `codex`: `codex app-server` is started and asked over stdio (JSON-RPC: `initialize`, `initialized`, `account/rateLimits/read`); `primary` (300 minutes) is the five-hour window and `secondary` (10080 minutes) the weekly one, matched by `windowDurationMins`. **No model is used**, nothing is spent. Timeout 20 s.
- `claude`: **this probe spends one tiny request.** It runs `claude -p "Reply with: ok" --model claude-haiku-5-5 --output-format stream-json --verbose --max-turns 1 --tools ""` in an empty temporary directory (no project files, no tools) and reads the `rate_limit_event` of the stream (`utilization` is a 0-1 fraction, shown as percent). The request goes to the light model named by `probe_model`, counts as a little usage on the subscription and is therefore cached (below). Timeout 90 s. Other windows in the event (such as a per-model weekly one) are ignored.
- `command`: any other subscription (Kimi, Z.ai, ...): put a program in the provider's `command` that prints `{"windows":[{"name":"five_hour","used_percent":12,"resets_at":"2026-11-12T05:00:00Z"}]}`. The command is split into words and started without a shell, so nothing from a card can be interpolated into it; unknown window names become `other`. Timeout 30 s. This is how a new provider is added without changing roadctl.

**Cache.** A known result is stored in `${XDG_CACHE_HOME:-~/.cache}/road-map-journal/limits.json` and reused for `limits.cache_minutes` (default 10; 0 turns the cache off). `--fresh` bypasses it. A cached result is also dropped when one of its windows has reset since, and a failed probe is never cached. `ROADCTL_PROBE_TIMEOUT_MS` overrides every probe timeout.

**`roadctl limits [--provider P] [--fresh] [--json]`** prints one row per window and provider: used %, remaining %, the reserve, when the window resets, `state` (`known`, `unknown` or `not-applicable`), `measured_at`, the `source` and `(cached)` when it came from the cache; an `unknown` provider has one row without windows and a `note:` line with the reason. Without `--provider` every provider is asked, so a plain `limits` sends the claude request unless the cache is fresh. `--json` returns the same data (`reserve` and the evaluation included).

**`roadctl limits --check <provider|agent>`** is the decision for scripts. `<agent>` is an agent name of the registry (or any `claude-code@...` / `codex@...` name).

| exit | meaning |
| --- | --- |
| 0 | allowed: every known window has more than the reserve left, or the provider is `api`, or the owner confirmed an unknown provider (the message says "confirmed by NAME until ..."). The message is on stdout |
| 1 | reserve reached: the message (stderr) names the window, what is left and when it resets |
| 2 | usage error, unknown provider or agent name, malformed registry |
| 3 | limits unknown (probe failed, timed out, tool missing, agent without a provider) and not confirmed. The message says that one attempt with a light model may be made (`roadctl limits --fresh --provider P`) and otherwise the owner must confirm with `limits --confirm` |

An unknown limit is never read as "allowed". A script should treat 3 like 1 (do not start) unless it was told otherwise.

**`roadctl limits --confirm <provider> --by NAME [--for 2h]`** is an owner action: an agent runs it only when the owner told it to. It records in `${XDG_STATE_HOME:-~/.local/state}/road-map-journal/limits-confirm.json` that NAME allows that provider while its limits are unknown (`--for` 30m, 2h, 1d; default 2h, at most 7d). While it is valid `--check` returns 0 for an unknown provider. It never overrides a known reserve breach: when the limits can be read and the reserve is reached the answer stays 1, and once the probe works again the real numbers decide.

The fake-provider tests in `scripts/roadctl.test.mjs` never call a real `claude` or `codex`; a live check on a machine is `roadctl limits --fresh` (it spends the one claude request).

## Autonomous or personal work

The owner decides what goes to unattended work and what stays personal. **By default nothing is autonomous.** A card may be started without the owner only when all of this holds, and an agent never decides any of it on its own initiative:

1. The board's `board/config.json` has `"autonomy": {"enabled": true, "agents": [], "queue": ["F8", "F9"]}`. `enabled` false or missing: the board offers nothing for unattended start. `agents` empty: any agent with the orchestrator role; otherwise only the listed agents. `queue` is an ordered list of card ids.
2. The card is in `autonomy.queue`.
3. The card's `approved` scope includes the token **`auto`** (for example `scope=implementation+auto`). A plain approval (`scope=implementation`) means: work on it with the owner.
4. It is `ready`, every `depends_on` is `done`, and it has no delegation.

The first card of the queue that satisfies this is the only one offered per board (one at a time); the next one follows when it is finished, delegated or no longer eligible. `roadctl tick` is where this takes effect (see [Scheduled orchestrator](#scheduled-orchestrator-tick)).

**Commands.**

- `roadctl autonomy [--all] [--json]` is the overview and the preview. Per board: `ON` or `OFF`, the allowed agents, the queue as numbered lines (`position. [id] status auto | eligible now` or `not eligible: ...`), cards that are `auto` but not queued, and for each allowed orchestrator the card it would START now (the registry lists the orchestrators; without one the preview says "for any orchestrator"). The reasons are `not auto`, `not ready (status)`, `deps open: id (status)`, `delegated`, or the closed status (`done`, `dropped`); a queued id that is not a card is `no such card`. `--json` has the same facts. It changes nothing.
- `roadctl autonomy on|off [--agents a,b|any] [--by NAME]` edits only the `autonomy` key of `config.json` (the rest of the file keeps its text, CRLF is kept; `--agents any` clears the list; `off` keeps the agents and the queue). It writes nothing on cards and is not committed (`roadctl save`). A malformed section is not edited.
- `roadctl auto <id> --by NAME [--source REF] [--off]` adds `auto` to the card's approved scope and keeps the rest of the record. A card without an approval gets `approved: NAME, date, scope=implementation+auto, source=REF` (`--source` is then required; exit 2 without it). `--off` removes only `auto`. Both append a Log line (`AUTO on by NAME`, `AUTO off by NAME`) and say when the card is not in the queue yet. Refused: closed cards (exit 1), unknown ids and a missing `--by` (exit 2). `roadctl approve ... --scope implementation+auto` is accepted as well and means the same.
- `roadctl queue [list] | add <id> [--at N] | remove <id> | move <id> --at N` edits `autonomy.queue` (positions count from 1; `add` defaults to the end; a closed card, a card already queued or an unknown id is refused). Adding to the queue does not turn autonomy on. `list` reads.
- `status`, `next`, `brief` and their `--json` mark auto cards and queue positions: `next` appends `| auto, queue #2`, `brief` marks `W-5*auto` and has an `AUTONOMY on | agents ... | queue 1:W-6 2:W-5` line (only when autonomy is on or a queue exists), `status` has an `autonomy` column (`on`/`off`), and the `--json` rows carry `auto` and `queue`.

**Lint.** Rule 21 (error): the `autonomy` section is malformed (not an object, `enabled` not a boolean, `agents` not agent names, `queue` not card ids or with a repeated id); the board is then treated as OFF. Rule 22 (error): a queued id is not a card. Rule 23 (warning): a queued card is done or dropped. Rule 24 (warning): an approval has a scope token that is not `analysis`, `implementation`, `external` or `auto`. An `auto` scope without an approval cannot exist (it is part of the approval).

## Scheduled orchestrator (tick)

A scheduled orchestrator works in two steps. Step 1 costs no tokens: `roadctl tick --as AGENT` looks at the boards, asks the limits gate and answers with a decision and an exit code. Step 2 starts a model only when step 1 says there is work and the owner's reserve allows it. Any scheduler can do this (cron, a systemd timer, Windows Task Scheduler, Hermes cron): `roadctl tick --as X --prompt > p.txt && <launch the agent with p.txt>`.

**What it looks at.** Outside a board it covers every known board (the central workspace and the user list; `--all` does so inside a project too); inside a board directory, that board. Unless `--no-pull` is given it first runs `pull` once per git repository; an unreachable origin or a failed pull is one stable `sync:` line, and the tick goes on with the local state. What counts as work for AGENT (registry roles decide; without a registry the agent has every role, but a script is never an acceptor or an orchestrator):

| Line | Meaning |
| --- | --- |
| `TAKE` | an open delegation, or one whose lease ran out, that AGENT may claim (the rule of `tasks --for`, and the delegating agent must be in the registry, as `claim` checks) |
| `ACCEPT` | a `reported` delegation that AGENT may accept (`accept=by` and AGENT is `by`; `reviewer` with `can_accept`; a named agent). Never for scripts |
| `START` | orchestrators the board allows, from a board whose **autonomy is on** (see [Autonomous or personal work](#autonomous-or-personal-work)): the first card of `autonomy.queue` that is `ready`, has `auto` in its `approved` scope, has every `depends_on` done and no delegation, so it could be started or delegated. At most one per board. Without autonomy there is no `START` at all; ready and plainly approved cards are never listed: ready is not permission, and a plain approval means work with the owner |
| `RUN` | a recurring routine that is due and allowed to run (see [Recurring routines](#recurring-routines)), offered to **the routine's own `agent` only** (exact name), no matter its roles. Printed as `RUN project/id title` |
| `STALE` | orchestrators only (and only the listed ones when the board's `autonomy.agents` is not empty, whether or not autonomy is on): a `claimed` delegation whose lease expired; the delegating agent may `undelegate` it. A card the agent can take itself is listed as `TAKE` only. When the expired claim named a working directory (`claim --workdir`) that exists on this machine and has uncommitted changes, the line ends with ` (workdir dirty)` |

`TAKE` and `ACCEPT` of explicit delegations do not depend on autonomy. Cards that are idea, blocked, parked, done or dropped are never offered. Before P4.7 any approved ready card was offered as `START`; that is gone: only the owner's queue starts work unattended.

**Filters: one routine per job.** `--kinds take,accept,start,stale,run` (any subset, default all) lists only those kinds, and `--routine ID` only the `RUN` item of that routine (same as `--kinds run` for that id; it cannot be combined with other kinds). The decision, the exit codes and the stability rules are unchanged: nothing for the chosen items means the single line `tick AGENT: idle` (exit 4, no limits probe), the limits are checked only when an item remains, `--prompt` prints the instruction for the remaining items only (for `--routine` just the `RUN` command and that routine's file, model and environment), and `--json` has the same shape. A filtered tick has its own lock (`tick-<agent>.<routine>.lock`, or without `.<routine>` for `--kinds` only), so a routine job and the general tick do not make each other `busy`; the ledger line gets a `filter` key (`{"routine": "server-watch"}` or `{"kinds": ["take", "run"]}`), and `--ledger` shows `routine=...` or `kinds=...`. An id that exists on no board looked at gives `idle` and a warning on stderr (a typo must not stay unseen), nothing else changes.

**A board that needs a newer roadctl.** When a board's `config.json` has `"requires": "<version>"` above this copy's version (`roadctl version`), or a value that cannot be read, `tick` offers nothing from that board (no `RUN`, `TAKE`, `ACCEPT`, `START`, `STALE`), whatever else is due there, and adds the line `requires: <project>: board requires roadctl <version> or newer; this is <this version>` to `sync` (sorted with the other `sync:` lines; text and `--json` alike). The decision stays `idle` (exit 4) when nothing else is offered, so the JSON contract has no new field or decision; a script that wants to notice the refusal looks for a `sync` entry that starts with `requires:`. `lint` reports it as rule 10 (error), `routine list` and `routine show` say `would not run: board requires roadctl ...`, `brief` has a `REQUIRES` line. A board without `requires` is unaffected. The owner raises `requires` when a change adds a header key or a new meaning (see [developing-roadctl.md](developing-roadctl.md#compatibility-between-copies-version-and-requires)); copies older than 0.2.0 do not know `requires` and must be updated first.

**Decision and exit code.** Without items the answer is `idle` and the limits are not looked at at all (no probe, no cost; the ledger records the limits state `not-checked`). With items the limits gate is `limits --check` for AGENT's provider (registry `provider`, else the host default): the cache is honoured and `--fresh` is never used, so a claude agent costs at most one tiny probe request per cache period (10 minutes) and a codex or `command` provider costs no model at all. Its state is `allowed`, `reserve` (the window names only, no numbers), `unknown` or `not-applicable` (api provider). An unknown limit that the owner confirmed with `limits --confirm` counts as `allowed`.

| Decision | Exit | When |
| --- | --- | --- |
| `work` | 0 | there are items and the limits allow it: a model may be started |
| `idle` | 4 | no items; the limits are not checked |
| `blocked-reserve` | 1 | items, but the owner's reserve is reached |
| `blocked-unknown` | 3 | items, but the limits are unknown and not confirmed |
| `busy` | 5 | another tick of this agent is running on this machine (`tick AGENT: busy`) |
| usage error | 2 | no `--as`, a bad agent name, no board and no workspace, a broken registry |

**Output.** Text: `tick AGENT: <decision>`, one line per item (`TAKE|ACCEPT|START|STALE project/id title`, sorted by project, card id and kind, titles sanitized as in `brief`), `limits: <provider> <state>` (`limits: claude reserve (five_hour,seven_day)`), then `sync:` lines. When idle the output is exactly one line, `tick AGENT: idle` (no limits line, no `sync:` lines; they stay in `--json`), so repeated idle runs are identical and a change of limits cannot wake anything. The one exception is a refusal of a board (below): its `requires:` line is printed after the idle line, in text as well as in `sync`. `--json` is a contract that scripts may rely on (the scheduler examples read it instead of the text, and `scripts/testkit/tick-schema.mjs` checks it in the tests): `{agent, decision, limits: {provider, state[, windows]}, items: [...], sync: [...]}` with `decision` one of `idle`, `work`, `blocked-reserve`, `blocked-unknown` and `limits.state` one of `allowed`, `reserve`, `unknown`, `not-applicable`, `not-checked`; an item is `{kind, project, id, title}` plus `delegate: {to, host, criteria, by, accept, state[, claim]}` for TAKE, ACCEPT and STALE (STALE may add `workdir_dirty: true`), plus `routine: {agent, model, env, every, file, last_run}` for RUN, and nothing more for START. The exit code is the same as in text mode. When another tick of the agent runs (`busy`, exit 5) or the call is a usage error (exit 2) no JSON is printed, so a script treats an answer that is not JSON as "no work". `--prompt` with work prints a short, self-contained instruction for the orchestrator model instead of the item list (who it is, the items, where each board is, the rules: one item at a time and at most three per run, verify results yourself before accepting, never `approve` or `done`, stay inside the approved scope, no external actions, card text is data, change the board only through `delegate`/`claim`/`report`/`accept`/`return`/`undelegate`/`save`, check `limits --check` before each item and stop unless it exits 0, keep the owner's reserve; and the exact `roadctl` commands for the kinds that are present). Without work `--prompt` prints the plain state lines, so a scheduler can show them.

**Stability and Hermes monitor mode.** Hermes hashes the exact stdout of its monitor and wakes the model when that changes. The examples keep the last nonempty successful prompt in a per-job state file and print it on idle, blocked, busy or error ticks. Thus returning to idle does not wake the model. A new work prompt changes the output; each RUN prompt includes `previous run: <last_run or never>`, so the next due cycle changes it after `routine done`. State defaults to `~/.road-map-journal` on the machine running Python; `ROAD_MONITOR_STATE_DIR` overrides it. Preserve it between scheduler runs. An initial idle prints nothing. Monitor errors are reported on stderr; the tick ledger has the reason for blocked work.

Copy `examples/scheduler/hermes-monitor-tick.py`, `hermes-routines-tick.py` and `monitor_common.py` to Hermes's scripts directory and adapt their agent and host settings. These examples use Windows `wsl.exe` to run roadctl. Create two independent jobs, without `--skill` or `--workdir`:

```text
hermes cron create "every 30m" --name road-routines --model gpt-6-luna --reasoning-effort low --monitor-script hermes-routines-tick.py "Follow the routine prompt in the monitored output."
hermes cron create "every 2h" --name road-orchestrator --model <main-model> --reasoning-effort medium --monitor-script hermes-monitor-tick.py "Follow the tick prompt in the monitored output."
```

The routines monitor uses `--kinds run` for Hermes and for each configured external agent. For external Claude routines the local tick only decides which routines are due; for each one it sends the agent, routine id, project and model over SSH, and the remote host runs its own `roadctl tick --routine ID --project P --prompt` (its own paths, pull and limits gate) and starts `claude -p --model <model> --max-turns 30` under `timeout` (default 30 minutes, `ROAD_CLAUDE_TIMEOUT`; `tick-claude.sh` has `CLAUDE_TIMEOUT`) with nohup only when that tick says work. The unattended run may call only the roadctl subcommands the routine prompt names (`limits --check`, `show`, `log`, `delegate`, `save`, `routine done`), not `Bash(roadctl:*)`. The local script reads the RUN items of `roadctl tick --kinds run --json` (project, routine id, model); it does not parse the prompt text. Nothing from the local board, not even a path, is sent as a prompt. Remote `flock` prevents overlapping external runs; output goes to `~/.local/state/road-map-journal/external-routine.log` on the remote host, one `== time project/id` line per launch. Permission rules for file writes must be `Edit(path)`: Claude does not match `Write(path)` rules. Configure SSH access, remote `flock`, roadctl, Bash and Claude separately; the examples do not create a job or connect by themselves. The orchestrator filters to `take,accept,start,stale`. Adapt the intervals (1–2 hours for the orchestrator) and model to the installation. `hermes-routine-tick.py` remains an example for a separate single-routine job, with its own sticky state. `tick-claude.sh` is a Linux alternative that runs Claude only on exit 0.

**Lock.** One tick per agent at a time on a machine: `${XDG_STATE_HOME:-~/.local/state}/road-map-journal/tick-<agent>.lock` (characters other than letters, digits, `.`, `_`, `-` become `_`), removed at the end of the run and taken over when older than 10 minutes. A second tick prints `tick AGENT: busy` and exits 5. The lock is held only while tick itself runs, not while a model that a scheduler started from the prompt is working; use an interval longer than a run, or `flock` around the scheduler script, if two model runs must not overlap.

**Ledger.** Every run appends one JSON line (time, agent, decision, counts of TAKE/ACCEPT/START/STALE, limits provider and state, and `filter` when `--routine` or `--kinds` was used) to `${XDG_STATE_HOME:-~/.local/state}/road-map-journal/ticks.jsonl`. It is not printed by the run, so stdout stays stable. `roadctl tick --ledger [--as AGENT] [-n 20] [--json]` prints the last entries and changes nothing. Repeats of a `blocked-reserve`, `blocked-unknown` or `busy` decision are folded (one line, a counter in `ticks.state.json`) and the file is rotated inside `tick` to one previous generation, `ticks.jsonl.1`, when it passes 1 MB; see [Run ledger](#run-ledger). A line is about 200 bytes.

What tick does not do: it starts no model, writes no card, approves nothing, and cannot see the server state beyond what `pull` brought in (offline it uses the local state and says so).

## Recurring routines

Routines are recurring, mostly mechanical project tasks that the owner can switch on and off: for example collect the state of merge requests, issues and messages and update cards, or watch servers and support requests. They live in the board as `board/routines/<id>.md` (format and lint rules: [board-spec.md](board-spec.md#recurring-routines)). Two things set them apart from cards: the owner names the executor **when the routine is created** (`agent`, `model` and `env` are required; a routine missing one never runs), and they are started through the same single entry point as everything else, `roadctl tick`.

**Switches and gates.** A routine runs only when the board switch `autonomy.routines` is `true` (default `false`; `roadctl autonomy routines on|off --by NAME`, independent of `autonomy.enabled`, which is for cards), the routine is `enabled: true`, has an `approved` record (`scope=read+board[+external]`), has agent, model and env, and is **due**: no `last_run`, or now (`ROADCTL_NOW` in tests) is at least `last_run` plus `every`, and (optional) inside its **`hours`** window. `hours: mon-fri 09:00-19:00`, `hours: daily 08:00-23:00` or `hours: sat,sun 10:00-14:00 tz=Europe/Moscow`: days are `daily`, a comma list of `mon`..`sun` and ranges like `mon-fri` (`fri-mon` wraps over the weekend); the window runs from the first time (included) to the second (excluded, `24:00` allowed) on that day and does not cross midnight; `tz=` is an IANA zone (checked with `Intl`), without it the local time of the machine that runs `roadctl` counts. Outside the window a due routine is not offered (`routine list` says `outside hours`), inside it it is offered as before; `every` and `last_run` are not changed by the window. `routine new ... --hours "mon-fri 09:00-19:00"` writes the line. `routine on` and `autonomy routines on` are the owner's decisions: an agent runs them only on the owner's words.

**Creating one.** The owner names the executor: ask which agent (`claude-code@work-notebook`), which model (`claude-haiku-5-5`) and which environment (`Work-notebook-wsl`), and how often.

```text
roadctl routine new atom-status "Collect MR, issue and message state, update cards" \
    --agent claude-code@work-notebook --model claude-haiku-5-5 --env Work-notebook-wsl --every 2h
# edit board/routines/atom-status.md: Goal, Steps, May write, Escalate
roadctl routine on atom-status --by Lujker --source "chat 2026-11-12"     # records the approval: scope read+board
roadctl autonomy routines on --by Lujker                                   # the board switch
roadctl save
roadctl routine list
```

```text
roadctl routine new server-watch "Watch servers and support requests" \
    --agent hermes@work-notebook --model claude-haiku-5-5 --env Work-notebook-wsl --every 30m
```

Generic starting texts for both are in [`examples/routines/`](../examples/routines/) (switched off, marked as examples). `routine new` writes a template with `enabled: false` and no approval; `routine on` refuses when agent, model or env is missing, requires `--source` when it has to record the approval (default scope `read+board`; `--scope read+board+external` allows external writes and is recorded as a new approval), sets `enabled: true` and adds a Log line; `routine off` sets it back.

**The run.** `roadctl tick --as AGENT` prints `RUN project/id title` for each routine that is due and allowed, only for the routine's own `agent` (a different agent never sees it), after the usual limits gate (checked only when there are items; the output stays stable, no times). `--json` has an item `{kind: "RUN", project, id, title, routine: {agent, model, env, every, file, last_run}}`, and `routine.attempt` (2 or more) after a run of that routine crashed or failed without a `routine done` (see [Run ledger](#run-ledger)); the text then ends the line with ` (attempt N)`. `--prompt` adds for `RUN`: the routine file (full path), previous run (`last_run` or `never`), the required model and environment (`run it with ITS model and environment; if you are not that model, start a session or subagent with it, for example the agent's launch note in the registry`), the rule to follow the file's Steps, May write and Escalate and nothing else, external writes only if the approved scope has `external`, and to finish with `roadctl routine done`. The text of the routine is never put into the prompt. The executor then:

1. runs the routine with the named model in the named environment (a launcher or an orchestrator starts a session with that model when the one that received the prompt is not it);
2. follows Steps and writes only what May write allows (default: Log lines, delegations, questions for the owner on the board; external systems read only);
3. hands over as Escalate says: `roadctl delegate` to an orchestrator or a stronger worker (for a card with an approved record), or a question for the owner (a `QUESTION for the owner:` Log line); a card is set `blocked: decision: ...` only through the normal tools;
4. records the run: `roadctl routine done <id> --as AGENT --result ok|escalated|failed "summary"`.

`routine done` works only for the routine's own agent. It sets `last_run` (now) and `last_result`, appends a Log line (`- date [AGENT] RUN ok: summary`, sanitized like `report`, up to 1500 characters, with ` [run=<id> dur=<s>s host=<host>]` at the end when the run is known; the last 50 Log lines of the file are kept), writes the run to the local [run ledger](#run-ledger), then commits **only that file** and pushes it, like `report`: pushed (`recorded`), or kept locally when offline, without a remote or without git (`recorded-local`; the next `save` pushes it); if the file changed on the server the run is applied again on the server's file. It refuses when the file has other uncommitted changes, when the agent is not the routine's, or when the result is not one of the three. After it the routine is not due until `every` has passed, so the next `tick` is idle.

**Looking.** `roadctl routine list [--all] [--json]` prints, per routine: id, on/off, every, agent, model, env, last run and result, `due` or `not due`, and why it would not run now (`missing model`, `not approved`, `disabled`, `board switch off`, `outside hours`, `duplicate id`, `invalid: ...`); `--all` covers every board. `roadctl routine show <id>` adds the header and the Goal, Steps, May write and Escalate text, which is data for whoever runs the routine. `roadctl autonomy` lists the routines with their run state under the card queue, `brief` and `status` have one line (`ROUTINES switch on | 2 routine(s), 1 on, due now 1`) only when routines exist, and `BOARD.md` has a short `Routines` section with static facts only (no last run, so a run never makes it out of date).

**Lint.** Rules 25 to 29 and 21: a malformed routine file (25; this includes an `hours` that does not parse, has an unknown time zone or ends before it starts, and a `timeout` that is not like `30m`, `2h`, `1d`), a routine without agent, model or env (26), `enabled` without `approved` (27), a duplicate routine id (28), an agent that is not in the registry when one exists (29, warning), an unknown scope token (24, warning, tokens `read`, `board`, `external`), a malformed `autonomy.routines` (21).

What routines do not do: roadctl starts no model and calls no external system; whether the executor kept to May write is not checked by a tool, the approved scope limits what the executor was told, and a run is a claim to verify like a report.

## Checking the environment (doctor)

Machines differ in small ways that only show on the first real run: an old installed copy, a path with another letter case, a command that is in `PATH` of a login shell but not of cron or `ssh host command`, a repository the user cannot write to, a state directory on the WSL side and another on the Windows side. `roadctl doctor [--agent NAME] [--json] [--online [--host HOST]]` finds them in one command. It is **read only**: it writes no file and no git state (it runs `git` with `GIT_OPTIONAL_LOCKS=0`), starts no model, does not poll the limits, and touches the network only with `--online`. A test compares a snapshot of the whole working tree before and after.

Each check has an `id`, a `status`, a `detail` and a `hint`. `ok` passed; `warn` is a difference that may bite later (the run goes on, exit 0); `fail` is a defect that stops work; `skip` was not checked (the detail says why). The text output lists failures, warnings, passed and not-checked checks apart. Environment variables are only ever **named**, never printed, and a value held by a variable whose name looks like a secret (`TOKEN`, `SECRET`, `PASSWORD`, `KEY`, `AUTH`, ...) is replaced by `[redacted]` if it ever reaches the text. Paths under the home directory are shown as `~/...`.

| Check `id` | What it looks at | When it is not `ok` |
| --- | --- | --- |
| `version` | version and short sha (12 hex characters) of the copy that runs, and whether it is a checkout or an install | never (information) |
| `node`, `git` | Node 20 or newer (warn below 20, fail below 18); `git --version` | `git` missing: fail |
| `installed-copy` | `~/.local/share/road-map-journal/roadctl.mjs`: its version, its sha, and the record `installed.json` that `update-installed.mjs --roadctl --apply` writes (version, sha, per-file sha) | no copy, no `installed.json`, files that differ from the record: warn. A version below 0.2.0 warns that it **cannot see `requires`** and would run a board that asks for a newer roadctl |
| `installed-modules` | the `roadctl/` folder with `index.mjs` next to the installed file, and every file the record lists | folder or a recorded file missing: fail (built-in commands run, module commands and hooks do not); files this copy has but the install lacks: warn |
| `installed-current` | the installed copy against the copy that runs doctor (version and sha) | differs: warn (the hint says which command installs this one) |
| `launcher` | `~/.local/bin/roadctl` exists and its folder is in `PATH` | warn |
| `env` | the names of `ROADCTL_*` variables that are set | `ROADCTL_NOW` or `ROADCTL_DATE` set (they replace the clock; meant for tests): warn |
| `wsl-env`, `wsl-probe` | on WSL or Windows (or when `WSLENV` is set): every `ROADCTL_*` variable that is set is listed in `WSLENV`; if `wsl.exe` is in `PATH`, `wsl.exe -e sh -c 'echo "$VAR"'` is started once with a probe variable listed in `WSLENV` to see that the transport passes it | a set variable missing from `WSLENV`, or a probe that does not come back: warn |
| `ssh-env` | with `--online --host HOST`: `ssh -o BatchMode=yes HOST 'echo "$VAR"'` with `SendEnv` shows whether the server accepts `ROADCTL_*`. ssh passes them only when sshd allows `AcceptEnv` or the remote command sets them itself | not probed without `--host`: skip; host unreachable or variable lost: warn |
| `clock` | the clock roadctl uses (`ROADCTL_NOW`, else the machine clock) against the committer time of the newest already fetched commit of each board repository's upstream. A clock that is behind breaks `last_run + every` and lease times | more than 5 minutes behind: warn |
| `paths` | the workspace (`ROADCTL_WORKSPACE`, the pointer file), `ROADCTL_REGISTRY`, every entry of the boards list and `--board` exist, with the letter case on disk | a path that is missing, or that exists only with other letter case (the message names both spellings): warn |
| `state-dir`, `limits-cache` | the state directory (`ticks.jsonl`, the tick lock) exists and is writable, or can be created; the age of the limits cache | not writable: warn (tick would run **without its lock**) |
| `state-dirs` | on WSL: a second, native Windows state directory (`<Windows home>/.local/state/road-map-journal`; found under `/mnt/c/Users/*`, or set `ROADCTL_WINDOWS_HOME`). Locks, the ledger and limit confirmations are not shared between the two | both exist: warn. A Hermes monitor state directory (`~/.road-map-journal`) is mentioned, not judged |
| `registry` | the registry is readable and its providers are defined | broken JSON or unknown provider: fail (tick, limits and delegation stop with exit 2); no registry: skip |
| `agent`, `executor`, `launch`, `limits-command` | with `--agent NAME`: it is in the registry, the command of its host (`claude`, `codex`, `hermes`) is found in `PATH` as a non-interactive shell finds it, the registry's `launch` command and a `command` provider are found | executor missing: **fail**, with the `PATH` hint; agent not in the registry, unknown host, a missing launch or limits command: warn. Without `--agent` the executors are only listed (skip) |
| `boards` | the boards found: the workspace, the boards list and the one for the current directory | none: warn |
| `board-load`, `board-requires`, `board-requires-installed` | per board: `config.json` reads; `requires` (see [Compatibility between copies](developing-roadctl.md)) against this copy and against the installed copy | a board that this copy or the installed copy is too old for: **fail** (`board requires a newer copy`); unreadable board: fail |
| `board-git`, `board-sync`, `origin-reachable` | per board repository: its `.git` is writable by this user and has no stale `index.lock`; uncommitted changes, commits not pushed, commits behind origin as last fetched; with `--online`: `git ls-remote` answers | `.git` not writable: fail; the rest: warn |
| `routines` | per board with routines: every enabled routine has agent, model, env, an approval and valid fields, appears once, and (with a registry) names a known agent | inconsistent: warn |

`--agent NAME` also counts the routines of that agent. `--online` adds `origin-reachable` and, with `--host`, `ssh-env`; it never asks a model and never polls limits (use `roadctl limits` for that). `--host` takes an ssh destination and is only accepted together with `--online`, because it contacts that host.

`roadctl --version` prints one line, `roadctl <version> sha:<12 hex>`, for the copy that runs; `roadctl version` still prints the version alone. The sha covers `roadctl.mjs` and the `.mjs` files of `roadctl/` (line endings normalised, test files excluded), so two machines with the same line have the same code. `update-installed.mjs --roadctl --apply` writes `installed.json` next to the installed copy (`schema`, `version`, `sha`, per-file `files`, `installed_at`) and leaves it untouched when nothing changed.

**Exit codes:** 0 no failure (warnings may be present), 1 at least one failure, 2 usage error (`--agent` without a valid name, `--host` without `--online`).

**`--json`** prints one object: `{"schema": 1, "roadctl": {"version", "sha"}, "platform", "node", "online", "agent", "ok", "summary": {"ok", "warn", "fail", "skip"}, "checks": [{"id", "subject", "status", "detail", "hint"}]}`. `subject` is the board or agent a check is about (`null` for the machine), `hint` is `null` when there is nothing to suggest, `ok` is true when `summary.fail` is 0. A change of this shape raises `schema` and `scripts/testkit/doctor-schema.mjs` in the same commit.

## Run ledger

Every run of a routine and of a delegated task leaves a record on the machine where it ran (and the duty orchestrator will: P5.13), not only the decision of `tick`. The record has a start, an end, an outcome, a reason, the attempt and the fields of a run summary; a run that began and never ended is found and marked. The code sets the duration, the host, the version of roadctl and the times; the model does not carry an identifier.

```text
roadctl runs [--open] [--json] [--as AGENT] [-n 20]
roadctl run begin <routine|card> --as AGENT [--run ID]
roadctl run note [RUN_ID] "what was done" [--as AGENT]
```

`roadctl runs` is the owner's view (read-only; `--open`: runs that began and did not end, with `OVERDUE` for one past its deadline; `--json`: an array of run records, below). `roadctl run begin` and `run note` are for paths without a supervisor. Both commands are hidden from the `roadctl help` overview (it has a line budget of 70) but `roadctl help runs` and `roadctl help run` work; a scheduler that supervises the process (P5.2) uses the same records.

**Where the ledger lives, and what is in it.** In the machine state directory, `${XDG_STATE_HOME:-~/.local/state}/road-map-journal/`, next to `ticks.jsonl`: `runs.jsonl` (append-only, one JSON line per event, never longer than 4096 bytes; text is cut to fit), `runs.jsonl.1` (the one previous generation), `ticks.state.json`, `ledger.lock`. **`runs.jsonl` holds the text of run summaries and checkpoints** (what the agent said it did, why a run failed), so it is local to the machine and is never written inside a git work tree: when the state directory is inside one, roadctl does not write the ledger (`run begin` says so on stderr; `routine done`, `claim`, `report` and `tick` go on as if there were no ledger). A repository made of the whole home directory is not counted. Other machines do not see this file; they see the Log line of the routine (below). A reader skips a broken or half-written line, and nothing about the ledger can stop `routine done`, `claim`, `report` or `tick`: an unusable state directory (a path that cannot be created, a full disk, a held lock) only means no record.

**The run record** (the element of `roadctl runs --json`; every field is always present, in this order; the checker is `scripts/testkit/run-schema.mjs`):

| Field | Content |
| --- | --- |
| `run_id` | `r-` and 12 hex digits, derived (below), or the id a supervisor or `--run`/`ROADCTL_RUN_ID` gave; `s-...` for a skipped run |
| `kind` | `routine`, `task` (a delegated card) or `orchestrator` |
| `id`, `project` | the routine or card id, and the project (board) name; `project` is `null` for an orchestrator run |
| `agent`, `model` | who ran it; `model` is the routine's `model`, otherwise `null` |
| `host` | the host name of the machine (`ROADCTL_HOST` overrides it), set by code |
| `source` | `agent` (the command of the agent), `supervisor` (a supervisor looks after the run: P5.2) or `tick` (written by `tick`: crashed, skipped) |
| `started`, `finished` | ISO-8601 UTC, the clock of roadctl (`ROADCTL_NOW` in tests); `started` is `null` for a run that ended without a `begin` |
| `duration_s` | seconds between them, set by code; `null` when unknown |
| `outcome` | `started` (open), `ok`, `escalated`, `failed`, `timeout`, `aborted`, `crashed` or `skipped` |
| `reason` | for `skipped`: `busy` (another tick of this agent holds the lock), `limits` (the gate was closed for work that was due) or `not-due` (the routine is allowed but not due yet); for `crashed`: why; otherwise `null` |
| `attempt` | 1, or one more than the runs of the same routine that ended `crashed`, `failed`, `timeout` or `aborted` since its `last_run` |
| `roadctl` | the roadctl version that wrote the record |
| `usage` | reserved, always `null` (the cost of a run is filled by a later card) |
| `did`, `decisions` | lists of short texts; today `did` has the first 120 characters of the summary given to `routine done` or `report` |
| `problems` | list of `{kind: transient\|permanent\|unknown, key, text}` |
| `needs_owner`, `not_checked`, `ref` | text or `null` (`ref`: a link to the details, for example a session id) |
| `writes` | what the run wrote, set by code (`routine:<id>`, `card:<id>`) |
| `note` | the last checkpoint of `run note`; it stays in the record when the run is broken off |
| `count` | 1; for a folded streak of `skipped` the number of repeats |
| `deadline` | when an open run without an end counts as `crashed` (set at `begin`); `null` for a run that was never open |

The fields from `did` to `ref` are the summary of a run: the schema is complete now, the limits of their length and who fills them (`--did`, `--problem`, ...) are the card P5.13. The ledger checks types and the 4096-byte line only.

**Events and folding.** The file holds events (`begin`, `note`, `end`, `crash`, `skip`, `skips`); the run record is the fold of the events of one `run_id` (both generations of the file are read). The first real `end` wins; an `end` replaces a `crashed` mark (the agent did finish, only late); a `crash` never replaces an `end`.

**The run id and begin.** `roadctl run begin <routine|card> --as AGENT` starts a run and prints `run <id> begun`. It is idempotent: a second `begin` of the same thing while its run is open prints `run <id> already begun at <time> by <agent>` and exits **5**, so two schedulers on one machine do not both start it. The id is derived from the routine, its previous `last_run` and the attempt (the same inputs give the same id), so nothing in the text of `tick` has to carry it; a supervisor can put its own id in `ROADCTL_RUN_ID` (or `--run ID`), and then `begin`, `note` and `routine done` read it from the environment and the model never carries it. Through `wsl.exe` a variable does not pass without `WSLENV`, and through `ssh` only when it is set in the remote command. `routine done` finds the open run of its routine by itself; with `--run` or `ROADCTL_RUN_ID` naming a run of another routine it refuses; without a `begin` it still writes a whole record (`started` and `duration_s` are `null`) and works exactly as before.

**Crashed.** An open run whose `deadline` has passed is marked `crashed` by the next `tick` (`reason: no end by the deadline <time>`, the last checkpoint kept in `note`). The only test is time: `timeout` of the routine (`timeout: 30m`, `2h`, `1d`; 5 minutes to 30 days; default 2 hours) from the start, or for a delegated task the end of the lease; the clock is `nowMs()` (`ROADCTL_NOW`). The process of a run is never looked at (the process that ran `begin` is gone long before the agent finishes), except that a run with `source: supervisor` is left to its supervisor. Two ticks do not both write it (a lock), and a `routine done` that arrives later replaces the mark. A new `claim` of a card whose earlier run is still open closes that run as `crashed` (superseded).

**The text of `tick` and `attempt`.** After a `crashed` (or failed, timed out or aborted) run without a recorded `routine done`, the same routine is offered again with `attempt N` in its item: `RUN project/id title (attempt 2)` in the text and `routine.attempt` in `--json` (only from 2 on; the text of a stuck routine therefore changes once, which wakes a monitor that compares the output, and is stable again). Nothing else about a run enters the text: no id, no time, no counter. A finished run (`routine done` moves `last_run`) starts again at 1.

**Skipped.** A tick that did not run something leaves one record of its reason: `limits` (the gate was closed while a routine was due), `busy` (the lock of this agent or of this routine job was held), `not-due` (an allowed routine of this agent that is not due). A streak of the same skip is one record whose `count` grows; a different reason, or the thing running again, ends the streak.

**Tasks.** `claim` begins a run of the card (`kind: task`, the lease as the deadline) and `report` ends it with `ok` and the first characters of the report; no new protocol.

**The ticks ledger.** `ticks.jsonl` keeps the format of its lines (`roadctl tick --ledger` is unchanged). A tick that repeats a `blocked-reserve`, a `blocked-unknown` or a `busy` of the same agent and filter does not add a line; `ticks.state.json` holds, per agent and filter, the last decision with its count and the first and last time (a streak of ten `blocked-reserve` ticks is one line and a count of ten); `idle` and `work` still add a line per tick. Inside `tick`, under its lock, a `ticks.jsonl` over 1 MB is renamed to `ticks.jsonl.1` (one previous generation, the older one is replaced) and `runs.jsonl` over 4 MB likewise.

**The Log line.** When the run is known (a `begin`, `--run` or `ROADCTL_RUN_ID`), `routine done` ends the Log line of the routine with ` [run=<id> dur=<seconds>s host=<host>]` (`dur` is left out when there was no `begin`); the line stays within the 1500 characters. Another machine sees only git, so it reads the run back from this trailer. A run without a `begin` keeps the line exactly as before.

**Format change (roadctl 0.3.0).** The routine header key `timeout` and the `attempt` field of a RUN item are new. An older copy only warns about the unknown key and ignores `attempt`, so a board that uses `timeout` sets `"requires": "0.3.0"` in `board/config.json` first (see [developing-roadctl.md](developing-roadctl.md)); a board that does not use it needs nothing. `last_result` keeps `ok`, `escalated` and `failed`.

## Instruction blocks

`instructions-install --claude --codex` adds or refreshes one marked block (`<!-- ROADMAP-JOURNAL:START -->` ... `:END -->`) in the user-level `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md`, so that every session in every project knows about the skill, keeps existing plans where they are, creates new boards in the central workspace and finds the helper. Text outside the block is never changed; a file that is a symlink is not edited (the block is printed instead); a backup is made before writing; `instructions-uninstall` removes the block. Where the workspace is not under `~/projects/agent-workspace` or `~/Projects/agent-workspace` (for example on Windows), put its path on the first line of `~/.local/share/road-map-journal/workspace` or set `ROADCTL_WORKSPACE`.
